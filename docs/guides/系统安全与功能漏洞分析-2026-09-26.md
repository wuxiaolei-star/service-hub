## 1. 高危（P0，建议立即安排）

### H-1 公网 SSH 允许 root + 口令认证【主机实测】
- **证据**：`sshd -T`：`permitrootlogin yes`、`passwordauthentication yes`；22 端口公网监听；
  近 7 天 auth.log 记录 19 次 Failed password。
- **场景**：root 口令若弱或泄露即整机失守（部署机保管全部数据与 docker 控制权）。
- **修复**：`PasswordAuthentication no` + `PermitRootLogin prohibit-password`（本机已有密钥
  通道 .deploy-tools/id_ed25519），改前确认密钥可登录。10 分钟操作，回滚=改回配置。

### H-2 conda 插件可取得 runner 共享 token → 冒充 runner 协议【S2 E-02】
- **证据**：插件与 conda-runner 同 uid 998（容器 /proc 实测），可读 `/proc/<runner>/environ`
  中的 token；`services/backup.py:30` 排除清单不含 `secrets`，备份档 0664 且组 hub-data 可读
  （第二路径）；`data/db`、全部 `jobs/` 对组可写。
- **影响**：恶意/失控 conda 插件可伪造任意 job 完成、翻转作业状态、触发 reconcile 级联——
  "conda 无容器隔离"的已知风险实际暴露**大于文档记载**。
- **修复**：备份排除 `secrets` + 备份档 chmod 600（一行级）；中期为 runner 协议引入按 job
  一次性凭据。conda 侧沙箱强度欠账据此应优先排期 B10/容器化议题的重新评估。

### H-3 资源声明无服务端钳制，B7 平台 cap 可被插件作者单方面取消【S2 E-01】
- **证据**：`plugin_manifest.py:204-207`（memory_mb/cpus 仅 gt=0 无上界）；
  `internal_runner.py:292-311` manifest 显式值直接胜出无 clamp。
- **场景**：publisher 上传声明 `memory_mb: 999999` 的插件即可绕过保护共享机的默认 cap。
- **修复**：`_resolve_resource_limits` 增加 `min(declared, platform_ceiling)` 钳制或超限 422。

## 4. 已澄清/关闭

- **E-13"supervisord 全 root"存疑 → 关闭**：容器 /proc 实测各进程按配置降权（hub-api=999、
  conda-runner=998、docker-runner=997、service-mgr=996），镜像内 conf 与仓库 md5 一致；
  仅 supervisord 主进程与 entrypoint 为 root（必要）。文档约束在组层面成立。
- **cs-nginx 归属（O-14 一半）→ 确认**：为 2026-08-20 部署的 code-server 反代（挂载
  /opt/code-server/nginx.conf），其上游容器一周前退出、当前 80/443 返回 502。归属明确后可
  与用户确认处置（回收 1.5G 镜像 + 两个端口，或修复）。
- **web 门 vitest 单次失败** → flake，重跑通过（无前端改动）。
