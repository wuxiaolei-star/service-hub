## 1. 心智模型：一次 5 分钟概览

- 插件 = 一份源码目录（`plugin.yaml` + `src/`）+ 一个运行时声明（conda `environment.yml`
  或 Docker `Dockerfile`）。发布者在**目标 Linux 平台**上把它构建为不可变 `.pypkg`；
  Hub 只校验、安装、调度，绝不联网安装依赖或编译插件代码。
- 同一份源码可以为 `conda-pack` 与 `docker` 两种运行时、`amd64` 与 `arm64` 两种架构
  各出一个 `.pypkg`。每个包（Build）独立安装、独立启用。
- 每次 Job 由 Runner 启动一个一次性进程（conda）或容器（docker），结束后即销毁。
  插件代码必须**在两种运行时下都能正确运行**（§5）。

## 2. 快速开始：从模板到第一个 `.pypkg`

### 2.1 前置条件

构建机要求（发布者侧，非 Hub 侧）：

- Python 3.12（`>=3.12,<3.13`），仓库根目录 `.venv` 中已可执行
  `pip install -e packages/hub-publisher`（提供 `hub-plugin` 命令）；
- `hub-plugin dev` 的 python 模式（默认）还要求 `hub_runner` 可导入
  （同 venv 执行 `pip install -e packages/hub-runner`，仓库 `.venv` 已含）；
- `docker build`：Docker 运行时构建需要本机 Docker daemon；
- `conda` + `conda-pack`：conda-pack 运行时构建需要 Linux 主机（Windows/macOS 上
  `hub-plugin build` 会明确拒绝，见 §6.3），且本机架构必须等于 `--arch` 目标架构。

### 2.2 从脚手架创建最小插件

复制模板（docker 运行时版）并改名：

```bash
cp -r templates/docker-job-plugin /srv/my-plugins/my_tool
cd /srv/my-plugins/my_tool
# 编辑 plugin.yaml：至少改 plugin.id / plugin.name / plugin.version
# 编辑 src/example_plugin/：把包目录改名为你的模块名，并同步修改 plugin.yaml 的 entrypoint.module
```

模板内容（`templates/docker-job-plugin/`）：

```text
my_tool/
├── Dockerfile            # 依赖写在这里（pip/apt），ENTRYPOINT 固定为 hub_runner
├── plugin.yaml           # 源码级静态契约（§3）
└── src/
    └── example_plugin/
        ├── __init__.py
        └── main.py       # run(params, inputs, context) 入口（§4）
```

conda 运行时请复制 `templates/conda-script-plugin/`，依赖写在 `environment.yml`
（模板还要求目录里有 `environment.yml` 或 `conda/environment.yml`；docker 要求
`Dockerfile` 或 `docker/Dockerfile`）。

最小的 `main.py`（模板原样可用）：

```python
from python_hub_sdk import InputFile, OutputFile, PluginContext, PluginResult


def run(
    params: dict[str, object],
    inputs: dict[str, InputFile | list[InputFile]],
    context: PluginContext,
) -> PluginResult:
    message = str(params.get("message", "hello"))
    destination = context.output_file("result.txt", create_parent=True)
    destination.write_text(message + "\n", encoding="utf-8")
    return PluginResult(
        message="处理完成",
        data={"message": message},
        files=[OutputFile(name="result", path="result.txt", format="text/plain")],
    )
```

### 2.3 本地校验

```bash
hub-plugin validate . --runtime docker
```

期望输出（冒烟实录，`templates/docker-job-plugin`）：

```text
plugin: example_script version 1.0.0
project: OK
manifest: OK
runtime docker: OK
```

`validate` 的三种用途（`hub-plugin validate PROJECT [--runtime RUNTIME] [--package PKG]`）：

1. 校验源码项目（`plugin.yaml` 可解析且过契约校验、存在 `src/`、无符号链接）；
2. `--runtime conda-pack|docker`：额外确认对应运行时文件存在（conda 要求
   `environment.yml`，docker 要求 `Dockerfile`）；
3. `--package xxx.pypkg`：离线复验构建产物，规则与服务端安装校验一一对应
   （布局白名单、checksums 覆盖、成员摘要、build.json 与 plugin.yaml 一致性等）。

畸形 `plugin.yaml` 会被逐条列出问题并以非零退出码拒绝（冒烟实录：非法
`plugin.id` 报 `9 validation errors`，退出码 1）。

### 2.4 构建包

```bash
# Docker 运行时（需要本机 Docker；构建 hub 三包 wheel + 插件镜像 + docker save + zstd）
hub-plugin build . --runtime docker --arch amd64 --output dist

# conda-pack 运行时（必须在目标架构的原生 Linux 上执行）
hub-plugin build . --runtime conda-pack --arch amd64 --output dist
```

成功时打印 `.pypkg` 绝对路径与整体 SHA256。产物命名：

```text
<plugin_id>-<version>-linux-<arch>-<conda|docker>.pypkg
```

NC→Shapefile 参考实现（`packages/nc-to-shp-plugin/`）用同一入口构建：

```bash
hub-plugin build packages/nc-to-shp-plugin --runtime conda-pack --arch amd64 \
    --output packages/nc-to-shp-plugin/dist
hub-plugin build packages/nc-to-shp-plugin --runtime docker --arch amd64 \
    --output packages/nc-to-shp-plugin/dist
```

该插件目录里的 `scripts/package_build.py` 是通用发布器的 NC 兼容包装（参数
`--runtime/--arch/--output`，另支持 `--prepared-runtime <env.tar.zst|image.tar.zst>`
与 `--docker-digest` 复用已构建好的运行时产物），历史文档引用它时含义不变；新插件
一律直接使用 `hub-plugin build`。

### 2.5 本地试跑（`hub-plugin dev`，无需 Hub）

在把插件构建成 `.pypkg` 并安装进 Hub 之前，先用 `hub-plugin dev` 在本机把插件入口
放进**真实 Runner 协议**里跑一遍：工具在临时目录合成一个模拟作业（`input/`、
`work/`、`output/`、`logs/` 与合成的 `job.json`，超时取 `execution.timeout`），
按 `manifest.entrypoint` 执行插件，结束后用 job 协议契约校验 `result.json`，
并打印作业状态、`PluginResult.data`、输出文件清单（含 size/SHA256）与 runner.log 尾部。

```bash
# python 模式（默认）：用当前解释器直接驱动 entrypoint（hub_runner 需可导入，见 §2.1）
hub-plugin dev templates/docker-job-plugin --param message="hello dev"

# 带输入：文件按扩展名自动匹配到 manifest inputs 的声明；有歧义时用 NAME=FILE 显式指定
hub-plugin dev packages/nc-to-shp-plugin --input sample.nc

# docker 模式：本地构建镜像（含 hub 三包 wheel 注入，上下文布局同 `hub-plugin build`），
# 再按 docker_executor 的作业容器约束运行（--network none --user 65532:65532
# --read-only --cap-drop ALL，input/job.json 只读挂载，work/output/logs 读写挂载）
hub-plugin dev . --mode docker

# --keep 保留临时作业目录（默认跑完即删），便于检查 job.json / result.json / runner.log
hub-plugin dev . --keep
```

口径与限制：

- `--param NAME=VALUE` 按 manifest 参数类型转换，未传参数按 manifest 默认值补齐、
  未知参数拒绝（与服务端 `_validate_params` 一致）；缺必填参数、`--input` 扩展名
  不符声明、文件缺失等都在**执行前**报错。
- 退出码：插件 SUCCESS = 0；result 契约校验失败或执行异常 = 1；命令行用法错误 = 2。
- python 模式要求插件依赖在本机解释器可导入：缺依赖时作业以 FAILED 结束，
  退出码 1，日志尾部会给出根因（例如 nc 插件缺 h5py），适合先确认"链路通"再补环境。
- **不支持 conda 模式**：conda-only 项目（只有 `environment.yml`）在不显式指定
  `--mode python` 时会被拒绝，提示改用 `--mode python` 直接驱动 entrypoint，
  或在 Linux 构建后经 Hub 安装运行。
- docker 模式需要本机 Docker daemon；容器内以 `65532:65532` 运行、无网络，
  与 §5.1 的作业容器约束一致。

### 2.6 安装与运行（需运行中的 Hub）

以下命令假设 Hub 已按[单容器部署与脚本插件使用](单容器部署与脚本插件使用.md)部署，
且认证已通过（浏览器登录管理台，或 `hubctl login` / API Key，`curl` 场景见 §6.5）：

```bash
HUB_URL=http://127.0.0.1:8000 python3 tools/hubctl plugin install dist/my_tool-1.0.0-linux-amd64-docker.pypkg
HUB_URL=http://127.0.0.1:8000 python3 tools/hubctl plugin list          # 等 Build 到 READY
HUB_URL=http://127.0.0.1:8000 python3 tools/hubctl plugin enable <build_id>
HUB_URL=http://127.0.0.1:8000 python3 tools/hubctl file upload sample.nc
HUB_URL=http://127.0.0.1:8000 python3 tools/hubctl job run my_tool \
    --version 1.0.0 --runtime docker --input source_nc=file_<id> --params params.json
HUB_URL=http://127.0.0.1:8000 python3 tools/hubctl job status job_<id>
HUB_URL=http://127.0.0.1:8000 python3 tools/hubctl job download job_<id> --output ./outputs
```

等价的原始 API 调用与完整生命周期（安装 → READY → 启用 → 作业 → 输出）见 §6.5。

## 3. `plugin.yaml` 规范摘要（spec_version 1.0）

`plugin.yaml` 是平台无关的源码级静态契约：它不绑定 CPU 架构、不含密钥、没有
`targets`。运行时与平台信息只出现在 Build 的 `build.json` 与数据库记录中。

完整可运行的权威示例：`packages/nc-to-shp-plugin/plugin.yaml`；模板示例：
`templates/docker-job-plugin/plugin.yaml`。

### 3.1 字段总表

解析器为 Pydantic 严格模型：**未知字段一律拒绝**，模型冻结不可变。带 ★ 的字段必填。

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| ★ `spec_version` | 字面量 | 只允许 `"1.0"` |
| ★ `plugin.id` | 插件 ID | `^[a-z][a-z0-9_]*$`，3–64 字符 |
| ★ `plugin.name` | 文本 | 1–256 字符（UTF-8 展示名） |
| ★ `plugin.version` | 语义版本 | `主.次.补` 三段数字，≤64 字符，不允许预发布/构建元数据 |
| `plugin.description` | 文本 | ≤4096 字符 |
| `plugin.author` / `plugin.category` | 文本 | ≤256 字符 |
| `plugin.tags` | 文本列表 | ≤64 项，每项 1–256 字符 |
| ★ `sdk.version` | 字面量 | 只允许 `"1.0"` |
| ★ `runtime.type` | 字面量 | 只允许 `process` |
| ★ `runtime.python.version` | 版本 | `主.次` 两段数字，≤64 字符（如 `"3.12"`） |
| ★ `entrypoint.module` | 文本 | ≤256 字符；必须是 `src/` 下顶层包，如 `my_tool.main` |
| ★ `entrypoint.function` | 文本 | ≤256 字符，实际为 `run` |
| `parameters[]` | 参数列表 | ≤64 项；`name` 唯一，匹配 `^[a-z][a-z0-9_]*$`、≤64 字符（同 `inputs`/`outputs` 的名称规则，见 §3.5） |
| `inputs[]` | 输入列表 | ≤64 项；`name` 唯一 |
| `outputs[]` | 输出列表 | ≤64 项；`name` 唯一 |
| ★ `execution.timeout` | 正整数 | 秒，Hub 强制执行（超时 → `TIMED_OUT`） |
| ★ `execution.concurrency` | 正整数 | 同一 Build 最大并发 Job 数，Hub 强制执行（B5 起）：建 Job 时统计该 Build 的 PENDING/PREPARING/RUNNING 作业，达到上限即 409 `PLUGIN_CONCURRENCY_LIMIT`；**对包括调度触发在内的所有来源生效** |
| `execution.memory_mb` | 正整数 | 单个 Job 的内存上限（MiB），Hub 强制执行（B7 起）。**可选**，见下方资源限制说明 |
| `execution.cpus` | 正数 | 单个 Job 的 CPU 配额（核数，如 `1.5`），Hub 强制执行（B7 起）。**可选**，见下方资源限制说明 |
| ★ `environment_variables.required` | 文本列表 | 只声明变量名（≤64 项、唯一、1–256 字符）；值由平台注入；**禁止写入任何密钥** |
| ★ `healthcheck.enabled` | 布尔 | |
| ★ `healthcheck.type` | 字面量 | 只允许 `import`；conda-pack 安装时 Runner 执行 `import hub_runner, python_hub_contracts, python_hub_sdk` 健康检查，docker 安装的健康检查即镜像加载 + digest 校验 |

上限常量（`plugin_manifest.py`）：标识符 64 字符、操作文本 256 字符、描述与 JSON
默认值字符串 4096 字符、列表 64 项、JSON 默认值嵌套 ≤8 层、每个容器 ≤64 项。

**资源限制（B7 起，`execution.memory_mb` / `execution.cpus`）**

生效优先级：**manifest 显式声明 > 平台默认 > 不限制**。两个字段都是可选的：

- 不声明时使用平台默认 cap（服务端 `settings.runner.resource_limits`，当前预置
  memory_mb=2048 / cpus=1.5，针对部署机 2 核 3.4G、同机还跑构建/走查/每小时调度
  的现状保守取值，**待真实样本实测内存峰值后由平台侧校准**，插件作者无需跟随调整）；
- 平台把 `resource_limits` 节点整体置 `null` 关闭默认时，不声明的插件**不带任何
  资源限制**运行（行为同 B7 之前）；
- 声明了的字段覆盖平台默认值（正数，`0`/负数在 validate 即被拒绝）。

运行时语义与超限后果：

- docker 运行时：`mem_limit` = `memswap_limit` = `memory_mb`（禁止 swap 超卖），
  `nano_cpus` = `cpus`；超限被内核 OOM kill 时容器以退出码 137 结束，Job 落
  **FAILED**（不是 `TIMED_OUT`）；
- conda 运行时：`RLIMIT_AS` = `memory_mb`、`RLIMIT_CPU` ≈ `cpus` × `timeout` 秒。
  两处与 docker 语义不同：`RLIMIT_AS` 限制的是虚拟地址空间，GDAL/numpy 的原生
  内存映射使它比 docker 的 `mem_limit`（cgroup 常驻内存口径）更保守；
  `RLIMIT_CPU` 是累计 CPU 秒数预算，不是并发核数份额。超限进程被杀，同样落
  **FAILED**；
- Windows 开发机上 conda 运行时不注入 rlimit（`resource` 模块与 `preexec_fn`
  均为 POSIX 专属），行为与不限流一致；生产 Linux 部署不受影响。

### 3.2 参数（`parameters`）

| `type` | 附加字段与规则 |
| --- | --- |
| `string` / `integer` / `number` / `boolean` / `datetime` | 可带 `min`/`max`（数值边界）；`min` ≤ `max` |
| `enum` | **必须**提供非空且无重复的 `options`；`default` 必须在 `options` 内 |
| `string_list` | `min`/`max` 变为列表长度下限/上限，必须是 ≥1 的整数；`default` 必须是非空、无重复的字符串列表，且在 `options`（若声明）内、满足长度区间 |

通用规则：`required: true` 的参数**不得**定义 `default`；只有 `enum` 允许声明
`options`。`datetime` 类型按 ISO8601 校验（B5 起服务端强制执行）：接受
`datetime.fromisoformat` 能解析的写法——带 `Z`/`z` 后缀（按 UTC 处理）、带
`±HH:MM` 偏移、无时区的本地时刻，以及纯日期（按当天零点解析）；其余写法（如
`25/09/2026`、`yesterday`）在建 Job 时即被 422 `JOB_REQUEST_INVALID` 拒绝。
Hub 原样透传字符串，不做时区归一，插件自行用 `datetime.fromisoformat` 解析。

### 3.3 输入（`inputs`）

| 字段 | 说明 |
| --- | --- |
| `type` | `file`（单文件）或 `files`（文件集） |
| `extensions` | 允许的扩展名列表，如 `[.nc, .h5, .hdf5]`；≤64 项 |
| `min_count` / `max_count` | ≥1；`min` ≤ `max` |
| `max_size` | 字节数（如 `10737418240` = 10 GiB） |

类型、必填、扩展名、大小与存在性由 Hub 在建 Job 前完成校验；插件内只做**跨字段或
业务语义**校验（参考实现还会复核 SHA256 完整性）。

### 3.4 输出（`outputs`）

| `type` | 语义 |
| --- | --- |
| `object` | 小型结构化结果，写在 `PluginResult.data` 中 |
| `file` / `files` | 写入 `output_dir` 的文件，通过 `PluginResult.files` 登记（`OutputFile.path` 相对 `output_dir`） |

required 语义（B5 起 Hub 强制执行）：

- `file`/`files` 型 required 输出按"文件已登记"校验：Runner 上报 SUCCESS 后，
  Hub 对照 manifest 检查每个 required 输出是否在 `PluginResult.files` 中出现；
  缺失则作业置为 FAILED，`error_summary` 以稳定错误码
  `PLUGIN_OUTPUT_MISSING` 开头并列出全部缺失名（例如
  `PLUGIN_OUTPUT_MISSING: result_archive`）。
- `object` 型 required 输出**显式豁免**该校验：它不产生文件，而是
  `PluginResult.data` 中的结构化值；manifest v1.0 尚未定义 `data` 的服务端
  校验契约（结构按插件自报透传），无从按存在性判定，强行校验会让诚实插件
  全部误报 FAILED。该语义留待 B8 之后的契约版本定义；在此之前请勿依赖
  object 输出做下游强依赖。

### 3.5 命名规则速查

- 插件 ID / 参数名 / 输入名 / 输出名：`^[a-z][a-z0-9_]*$`（小写字母开头，只含小写
  字母、数字、下划线），3–64 字符（ID）；名称类 1–64 字符。
- 版本：`主.次.补`（每段 `0` 或非零开头数字）。
- 违反上述规则的清单会在 `hub-plugin validate` 阶段被全部列出。

## 4. SDK 使用（`python-hub-sdk`）

SDK 保持轻量（仅纯 Python，无 Pydantic 依赖），wheel 随运行时环境装入镜像/环境。

### 4.1 入口签名

```python
def run(
    params: dict[str, object],
    inputs: dict[str, InputFile | list[InputFile]],
    context: PluginContext,
) -> PluginResult: ...
```

### 4.2 `PluginContext`

| 成员 | 说明 |
| --- | --- |
| `job_id` / `plugin_id` / `plugin_version` | 本次调用身份 |
| `input_dir` / `work_dir` / `output_dir` | Job 三个目录；docker 下分别是 `/job/input`（只读挂载）、`/job/work`、`/job/output` |
| `logger` | 标准日志协议（debug/info/warning/error）；输出经 Runner 事件流进入作业日志 |
| `progress(percent, message=None)` | 汇报进度；`percent` 必须是 0–100 的 `int`（bool 不行），`message` 提供时必须是非空字符串，违规直接 `ValueError` |
| `is_cancelled()` / `check_cancelled()` | 协作式取消：轮询返回；`check_cancelled()` 在已取消时抛 `PluginCancelledError`。长循环里应周期调用 |
| `output_file(path, create_parent=False)` / `work_file(...)` | 返回被限制在对应目录内的安全路径；拒绝 `..`、绝对路径、盘符、空/`.`/`..` 段，解析后逃逸目录同样报错。`create_parent=True` 自动建父目录 |

### 4.3 结果与文件对象

- `InputFile`（只读，Hub 已填好）：`id`、`name`（位于 `input_dir` 内的文件名）、
  `path`、`size`、`extension`、`sha256`（64 位十六进制）。取真实路径请基于
  `context.input_dir` 与 `name` 自行拼接并复核包含关系（参考实现 `main.py` 的
  `_input_path`），或直接使用 `path` 字段。
- `OutputFile(name, path, format=None)`：`name` 非空；`path` 是相对 `output_dir` 的
  安全相对路径；`format` 提供时为非空字符串（如 `"application/zip"`）。
- `PluginResult(message=None, data={}, files=[])`：`data` 必须是严格 JSON（深度 ≤8、
  容器 ≤64 项、字符串 ≤4096 字符）；`files` 只能包含 `OutputFile`。
- `OutputFile.path` 必须与 `context.output_file(...)` 实际写出的文件一致，作业结束后
  Runner 会对每个文件记录 `size` 与 `sha256` 写入 `result.json`。
- **required 输出必须全部出现在 `files` 中**（B5 起）：manifest 里 `required: true`
  的 `file`/`files` 输出若未随 SUCCESS 上报，Hub 会把作业改判为 FAILED
  （`PLUGIN_OUTPUT_MISSING`）；`object` 型 required 输出豁免（见 §3.4）。

### 4.4 异常与错误码语义

| 异常 | 语义 | 典型用法 |
| --- | --- | --- |
| `PluginError` | 基类。`code` 必须匹配 `^[A-Z][A-Z0-9_]{2,63}$`；`message` 非空；`details` 为可选严格 JSON | 自定义领域错误的父类 |
| `PluginValidationError` | **输入语义不合法**（调用方可通过改参数/换文件修复） | `raise PluginValidationError(code="NC_TIME_RANGE_INVALID", message="end_time 不能小于 start_time")` |
| `PluginExecutionError` | **执行失败**（输入合法但处理中失败：外部库报错、写出失败等） | 转换中途失败时携带稳定 `code` 抛出 |
| `PluginCancelledError` | 协作式取消（由 `context.check_cancelled()` 触发，插件一般不主动抛） | `code`/`message` 有默认值（`PLUGIN_CANCELLED` / "任务已取消"） |

- 错误码是面向调用方的稳定契约：一旦发布就不要改动语义；完整 traceback 只进入
  受控日志，不写入 `result.json`，也不通过 API 暴露给普通调用方。
- 未捕获异常会被 Runner 归一为 FAILED（退出码非零 → `Docker container exited with
  status N` 或 conda runner 的 stderr 摘要）；想要稳定错误码就必须自己抛 SDK 异常。
- 两种运行时的终态语义一致：`SUCCESS` / `FAILED` / `CANCELLED` / `TIMED_OUT`
  （超时统一 `JOB_TIMED_OUT`），与运行时无关。

## 5. 双运行时约束（docker 与 conda-pack）

同一份插件源码必须能在两种运行时下都跑通——这是验收要求（T15 曾以
`nc_to_shp` 双运行时输出字节级一致做过最强验证，见
`docs/guides/系统现状与优化总结-2026-09-25.md`）。

### 5.1 docker 运行时

执行容器由 `docker_executor.py` 以如下方式启动（写死，不由插件声明控制）：

| 约束 | 实现值 | 对插件代码的含义 |
| --- | --- | --- |
| 镜像 digest 钉死 | `image = sha256:<digest>`，加载后校验与 `build.json` 一致，不匹配即 FAILED | 不要期望 tag 漂移；镜像即包 |
| 只读 rootfs | `read_only=True` | 容器内除挂载目录外一律不可写；临时文件写到 `context.work_file()` |
| 非 root | `user=65532:65532` | `/plugin`、解释器与全部数据文件必须 world-readable（模板 `chmod -R a=rX` 已处理） |
| 无网络 | `network_mode="none"` | 任何联网调用（pip、API 回调）都会失败 |
| 最小能力 | `cap_drop=["ALL"]` | 不要依赖特权操作 |
| 挂载 | `input` 只读；`work`/`output`/`logs` 读写；`job.json` 只读 | 只写 `context.output_file()` / `work_file()` 给出的路径 |
| 环境变量 | `HUB_INPUT_DIR`、`HUB_WORK_DIR`、`HUB_OUTPUT_DIR`、`HUB_LOG_DIR`、`PYTHONUNBUFFERED=1`，加 manifest `environment_variables.required` 声明项 | SDK 已消费前四个；插件只需通过 `PluginContext` 访问 |

镜像内必须装有 hub 三包（`hub-contracts`、`hub-sdk`、`hub-runner`）——`hub-plugin
build` 会自动把三包 wheel 注入构建上下文（`COPY wheelhouse/`，见模板 Dockerfile），
插件自带依赖（GDAL/h5py 等）写在 `Dockerfile`。典型体积量级约 1 GB
（含基础镜像与原生库；参考实现 docker 镜像 1.01 GB）。

### 5.2 conda-pack 运行时

- 由 `conda_executor.py` 在**宿主机上**直接解包 `environments/<build_id>` 并裸 exec
  `<env>/bin/python -m hub_runner ...`：**没有容器隔离**（无网络/用户/rootfs 边界），
  隔离只来自 Job 目录布局与 Hub 校验——插件作者应把两种运行时都按"最小权限"写。
- 执行器会按需注入 `GDAL_DATA` / `PROJ_DATA` / `PROJ_LIB`（指向解包环境的
  `share/gdal`、`share/proj`，存在才注入）。这是裸 exec 不跑 conda 激活脚本的补偿
  （首个 conda 作业曾因 `proj.db` 找不到而 `SHAPEFILE_WRITE_FAILED`）。你的插件
  若还依赖其他"激活脚本设置的环境变量"，不能指望它存在——在代码里显式处理。
- 构建必须在目标架构的**原生 Linux** 上执行（跨架构直接拒绝）；conda 依赖写
  `environment.yml`（参考实现使用 conda-forge 通道、锁定 `setuptools<81` 以保证
  `conda-pack` 可用）。
- 环境在安装时执行 `conda-unpack` + import 健康检查，通过才 READY。
- 体积量级：参考实现 conda 包 179 MB，远小于 docker 包，构建也更快。

### 5.3 双运行时验收要求

上线前自查（至少覆盖 §7 清单中的对应项）：

- [ ] 插件不写 `input_dir`；不假设工作目录是当前目录（conda 的 cwd 是 workspace 根，
  docker 的工作目录是 `/`）；
- [ ] 所有中间产物经 `context.work_file()`、结果经 `context.output_file()`；
- [ ] 不联网、不依赖特权、不依赖 `HOME` 可写；
- [ ] 依赖第三方环境变量（除 §5.1/§5.2 列出者）前先判空并给出可读错误；
- [ ] 若可行：同一输入在两种运行时下输出 SHA256 一致（参考实现做法：ZIP 时间戳固定、
  文件排序、字段序列化确定性）。

### 5.4 把插件接入一致性测试套件

一致性测试套件（conformance harness）把"插件经真实 runner 协议跑通、输出可复现"
变成一个参数化用例：一个用例 = （插件项目目录, 输入文件构造, 参数, 断言回调），
内置钩子覆盖 result 契约、输出文件存在非空、两次独立运行的输出一致（ZIP 走平台级
比对器 `hub_publisher.conformance`，含逐文件 SHA256）。接入只需在
`tests/plugins/test_conformance.py` 增加一个 `ConformanceCase`（参考其中的
`docker-job-template` 纯 Python 用例与 `nc-to-shp` 用例）；执行后端与钩子在
`tests/plugins/harness.py`，无需改动 harness 本身。

## 6. 打包与分发

### 6.1 `.pypkg` 结构（zstd 压缩 tar）

`hub-plugin build` 产出的包是一个 zstd 压缩 tar，成员布局白名单（服务端与离线校验
逐一对应，多余成员会被拒绝）：

```text
<plugin_id>-<version>-linux-<arch>-<conda|docker>.pypkg
├── plugin.yaml                 # 源码清单（与项目内文件字节一致）
├── build.json                  # 平台 Build 清单（§6.2）
├── checksums.json              # 除自身外全部成员的 SHA256（路径 -> 摘要）
├── plugin/                     # src/ 打包内容（顶层包目录在此之下）
│   └── my_tool/…
├── image.tar.zst               # docker 运行时：docker save 流 + zstd
└── runtime/env.tar.zst         # conda-pack 运行时：conda-pack 流 + zstd
```

`build.json`（`build_manifest.py`）字段：`schema_version`（`"1.0"`）、`build_id`
（`<id>-<version>-linux-<arch>-<runtime>-<指纹前12位>`）、`plugin_id`、
`plugin_version`、`target`（`{os: linux, arch: amd64|arm64}`）、`python_version`、
`runtime`（docker：`archive: image.tar.zst` + `image` + `digest`；conda-pack：
`archive: runtime/env.tar.zst` + `fingerprint`）、`sdk_version`（`"1.0.0"`）、
`source_sha256`（`src/<顶层包>` 的确定性 SHA256）、`built_at`（必须带时区）。
`build.json` 与 `plugin.yaml` 在 ID、版本、Python 版本、SDK 主版本上一致才被接受。

确定性构建：包内 tar 成员 mtime 取 `SOURCE_DATE_EPOCH`（默认 0），同一源码在同一
环境重建可复现 `source_sha256`；`build_id` 由运行时指纹派生，同一 Build 重复安装
返回 409 而不是覆盖（不可变）。

### 6.2 内容哈希包缓存（docker 构建加速）

docker 构建在"插件源码、Dockerfile、hub 三包源码树、基础镜像 ID、镜像变量、zstd
级别、架构"全部未变时直接复用上次的包。控制变量：

| 变量 | 作用 | 默认 |
| --- | --- | --- |
| `HUB_PLUGIN_CACHE` | `0/false/no/off` 关闭缓存 | 开启 |
| `HUB_PLUGIN_CACHE_DIR` | 缓存目录位置 | `<output>/.pypkg-cache`（保留最近 3 个条目） |
| `HUB_PLUGIN_ZSTD_LEVEL` | 包压缩级别 1–22 | `10`（级别依据实测写死在 `archive.py` 注释） |
| `HUB_PLUGIN_PIP_INDEX_URL` | 传入 Dockerfile `PIP_INDEX_URL` 构建参数（pip 镜像源） | 未设置（官方 PyPI） |
| `HUB_PLUGIN_APT_MIRROR` | 传入 `APT_MIRROR` 构建参数（apt 镜像根） | 未设置 |

缓存条目记录包 SHA256，命中前先校验，撕裂或被篡改的缓存不会冒充构建结果；
conda-pack 构建不走缓存（依赖宿主 conda 状态，无法本地钉死）。

### 6.3 平台与报错速查

| 场景 | 行为 |
| --- | --- |
| Windows/macOS 上构建 conda-pack | 拒绝：`Conda-Pack runtime must be built on Linux`（冒烟实录） |
| 本机架构 ≠ `--arch` 构建 conda-pack | 拒绝：`must be built natively on the target Linux architecture` |
| 无 Dockerfile 构建 docker / 无 environment.yml 构建 conda-pack | `hub-plugin validate --runtime` 阶段即报可读错误 |
| 包内有符号链接 / 越界路径 / 非白名单布局 | `validate --package` 与服务端安装两侧一致拒绝 |
| 畸形 YAML | `hub-plugin validate` 列出全部校验错误；服务端按 HubError 归一为 422（已知缺口见 §8） |

### 6.4 服务端生命周期（状态与 API）

```text
POST /api/v1/plugins/install (multipart file)   → 202，异步安装（INSTALLING）
GET  /api/v1/plugin-builds/{build_key}          → 轮询到 READY（失败 FAILED）
POST /api/v1/plugin-builds/{build_key}/enable   → ENABLED（禁用用 /disable）
POST /api/v1/files (multipart file)             → file_<id>（输入）
POST /api/v1/jobs {plugin_id, version, runtime_type?, inputs, params, callback?}
GET  /api/v1/jobs/{job_key}                     → PENDING → PREPARING → RUNNING → 终态
GET  /api/v1/jobs/{job_key}/logs                → 日志（另支持 /logs/stream）
GET  /api/v1/jobs/{job_key}/outputs             → items[].file_id
GET  /api/v1/files/{file_id}/download           → 下载输出
POST /api/v1/jobs/{job_key}/cancel              → 异步取消请求
```

补充：

- **plugin-builds 分页（B1）**：`GET /api/v1/plugin-builds` 支持 `plugin_id`、
  `runtime_type` 过滤与 `limit`（1–200，默认 100）、`offset`，响应含全量 `total`。
- 只有 `ENABLED` 且运行时环境 READY 的 Build 能建 Job；同一
  （版本，平台，运行时）的 Build 已存在时再装返回 409，发布新版本即可。
- 认证：`POST /api/v1/auth/login` 取 Bearer token，或用管理台签发的 API Key
  （`Authorization: Bearer <key>`）；角色 viewer < operator < publisher < admin，
  安装/启用插件需要 publisher 及以上。
- 定时任务与管道对插件的要求与手动作业相同（Build 必须存在且 ENABLED，缺失时调度
  不推进并记审计）。

### 6.5 纯 `curl` 示例（需运行中的 Hub）

路径与参数已对照 `docs/openapi.json`（§9）核对。`<TOKEN>` 为登录返回的会话 token
或 API Key：

```bash
HUB=http://127.0.0.1:8000/api/v1
AUTH="Authorization: Bearer <TOKEN>"

# 安装包（publisher+）
curl --fail-with-body -X POST -H "$AUTH" -F "file=@dist/my_tool-1.0.0-linux-amd64-docker.pypkg" \
  "$HUB/plugins/install"
# → 202 {"build_id": "...", ...}；随后轮询：
curl -H "$AUTH" "$HUB/plugin-builds/<build_id>"
# READY 后启用：
curl --fail-with-body -X POST -H "$AUTH" "$HUB/plugin-builds/<build_id>/enable"

# 上传输入并创建作业（operator+）
FILE_ID=$(curl --fail-with-body -X POST -H "$AUTH" -F "file=@sample.nc" "$HUB/files" | python3 -c 'import json,sys; print(json.load(sys.stdin)["file_id"])')
curl --fail-with-body -X POST -H "$AUTH" -H 'Content-Type: application/json' \
  -d "{\"plugin_id\":\"my_tool\",\"version\":\"1.0.0\",\"runtime_type\":\"docker\",\"inputs\":{\"source_nc\":\"$FILE_ID\"},\"params\":{}}" \
  "$HUB/jobs"

# 轮询与取输出
curl -H "$AUTH" "$HUB/jobs/<job_id>"
curl -H "$AUTH" "$HUB/jobs/<job_id>/outputs"
curl -fsSL -H "$AUTH" "$HUB/files/<file_id>/download" -o result.zip
```

## 7. 验收清单（上线前自查）

一致性（发布侧）：

- [ ] `hub-plugin validate <dir> --runtime <rt>` 通过；
- [ ] `hub-plugin validate <dir> --package <pypkg>` 通过（与服务端同规则）；
- [ ] `plugin.yaml` 无密钥/Token/绝对路径/`targets`；`environment_variables` 只有变量名；
- [ ] `build.json` 的平台、Python、SDK 版本与实际产物一致；`source_sha256` 与源码一致；
- [ ] `sha256sum <pypkg>` 记录在案（分发对账用）；
- [ ] `spec_version`/`sdk.version` 未改动（1.0 契约只加可选字段，不做破坏性变更）。

行为（运行侧，需运行中的 Hub，或先用 §2.5 的 `hub-plugin dev` 本地试跑）：

- [ ] 安装 → READY → enable → ENABLED 全链成功；重复安装同版本得到 409 而非覆盖；
- [ ] 一个代表输入的作业跑到 SUCCESS，输出文件完整可下载；
- [ ] 声明的 `required` 输出确实被产出并登记在 `PluginResult.files`（B5 后缺失即 FAILED）;
- [ ] 错误路径抛 `PluginValidationError`/`PluginExecutionError` 且 `code` 稳定可辨识；
- [ ] 长循环周期性 `context.check_cancelled()`，取消后终态为 CANCELLED；
- [ ] `execution.timeout` 留有真实余量（超时即 `TIMED_OUT`）；
- [ ] 双运行时均通过（§5.3）；跨架构目标分别在真实架构上构建并验证。

## 8. 已知缺口与规划

- **制品签名（G9，规划中，B9 批次实施）**：方案采用 minisign——发布者本地保存私钥，
  公钥将配置于服务端 `settings.plugins.signature.public_key_path`。密钥生成与保管
  约定（离线保管、私钥不入库、公钥随部署配置分发）将在 B9 落地时并入本节；
  未配置验签前，上传 `.pypkg` 的行为与现状完全一致。
- **畸形 `plugin.yaml` 的服务端状态码**：B1 执行期发现
  `hub_server/services/archives.py` 的 `verify_and_install` 异常捕获集缺
  `yaml.YAMLError`，畸形 YAML 会以 500 而非 422 返回（本指南冒烟已在本地实例现场
  复现：500 `UNEXPECTED_ERROR`；已登记待办，拟并入 B5 批次或单独 hotfix）。
  发布侧用 `hub-plugin validate` 可完全避免触发（对同一畸形包逐条列出问题并拒绝）。
- **conda-pack 运行时的本地试跑**：`hub-plugin dev`（§2.5，B2 批次已落地）不模拟
  conda 运行时；conda-only 插件只能用 `--mode python` 直接驱动 entrypoint
  （依赖需在本机解释器可导入），或在 Linux 构建后经 Hub 安装运行。

## 9. OpenAPI 快照

仓库内 `docs/openapi.json` 是 Hub REST API 的机器可读快照（`json.load` 可直接读取，
57 个 path）。生成方式：在仓库根目录的 Python 3.12 venv 中加载 FastAPI 应用工厂并
导出——

```bash
HUB_CONFIG_PATH=config/hub.yaml.example python -c "
import json
from hub_server.main import app
json.dump(app.openapi(), open('docs/openapi.json', 'w', encoding='utf-8'),
          ensure_ascii=False, indent=1, sort_keys=True)"
```

（导出不连接数据库、不启动服务；`HUB_CONFIG_PATH` 指向任一合法配置文件即可，
`config/hub.yaml.example` 可用。）快照为手工刷新：**接口变更的批次应同步重导**。
本快照最近一次重导于 2026-09-25（B8 批次，`GET /jobs/stats` 新增 `by=plugin`
