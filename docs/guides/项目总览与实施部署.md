# Python Service Hub V1：项目总览与实施部署

> **历史文档（旧拓扑，不再作为部署入口）**：本文描述 hub / hub-conda-runner /
> hub-docker-runner 三个独立 Compose 服务的部署方式，仅作历史参考。当前部署请使用
> [单容器部署与脚本插件使用](单容器部署与脚本插件使用.md)，其中 hubctl 与插件构建
> 流程仍然适用。

本文是首次接手项目时的总入口。它回答四个问题：项目怎样运行、如何在 Linux AMD64
服务器部署 Hub、如何注册 `nc_to_shp` 插件，以及如何完成首次验收。

需要逐条复制生产命令、离线搬运命令、备份恢复或 ARM64 迁移时，请继续阅读
[双运行时插件构建与部署](双运行时插件构建与部署.md)。旧的
[构建部署使用与 NC 插件注册说明](构建部署使用与NC插件注册.md) 保留为设计演进和基础
概念参考；以本文和双运行时手册的实际命令为准。

## 1. 这个项目解决什么问题

Python Service Hub 是一个单机、离线优先的插件调度服务。业务系统不直接启动 Python
脚本或 Docker 容器，而是通过 Hub 完成：

1. 上传输入文件；
2. 注册发布者已构建好的插件包；
3. 选择 Conda 或 Docker Build 创建 Job；
4. 查询 Job 状态与日志；
5. 下载输出文件。

Hub 管理插件 Build、文件、Job、日志和结果；**不执行** `pip install`、`conda install`
或 GDAL/PROJ 编译。插件发布者必须提前为目标平台准备全部业务依赖并生成 `.pypkg`。

插件不是常驻 HTTP 服务。每一个 Job 都是一次性执行：完成后进程或插件容器退出，Hub
保存 `result.json`、日志和输出文件。

## 2. 总体架构

```text
业务系统
  │ HTTPS（建议经 Nginx、TLS、来源网段限制）
  ▼
Nginx ──► 127.0.0.1:8000 ──► hub
                                      │
                       ┌──────────────┴──────────────┐
                       ▼                             ▼
               hub-conda-runner              hub-docker-runner
               无 Docker Socket               唯一有 Docker Socket
               运行 conda-pack                启动一次性插件容器
                       │                             │
                       └──────────────┬──────────────┘
                                      ▼
                               /data 持久化目录
                    SQLite、插件包、环境、输入、Job、输出、日志
```

三个 Compose 服务共享宿主数据目录，但隔离职责：

| 服务 | 对外端口 | Docker Socket | 业务代码执行方式 |
| --- | --- | --- | --- |
| `hub` | 仅 `127.0.0.1:8000` | 无 | 不执行插件 |
| `hub-conda-runner` | 无 | 无 | 预构建 Conda 环境中的一次性子进程 |
| `hub-docker-runner` | 无 | 有 | 一次性 Docker 插件容器 |
| Docker 插件容器 | 无 | 无 | 非 root、无网络、只挂载本 Job 必需目录 |

`/internal/v1` 只供两个 Runner 在 Compose 内部网络调用；Nginx 必须拒绝转发该路径。
V1 暂无调用方认证，因此公开 API 必须保持回环监听，并由 Nginx、TLS、IP 白名单和防火墙
保护。

## 3. 代码和数据目录

```text
packages/
  hub-contracts/       Pydantic 协议：manifest、build、job、result、event
  hub-sdk/             插件 SDK：PluginContext、InputFile、PluginResult、稳定错误码
  hub-server/          FastAPI、SQLite 模型、文件/插件/Job API、工作目录管理
  hub-runner/          公共 CLI、Conda Executor、Docker Executor
  nc-to-shp-plugin/    示例业务插件、Conda/Docker 构建定义和打包脚本
deploy/
  runner/              两类 Runner 的镜像和轮询服务
  nginx/               外部反向代理示例
config/hub.yaml        Hub 配置；生产环境使用 root:65532、0640
compose.yaml           三服务本地编排
data/                  运行时持久化数据；生产中位于宿主绝对路径
```

Hub 的持久化数据关系如下：

```text
Plugin → PluginVersion → PluginBuild → Environment
                                  │
                                  └───────────────→ Job → JobFile/File
```

- `PluginVersion` 是源码/插件描述版本；
- `PluginBuild` 是某个 `linux/amd64` 或 `linux/arm64`、某个运行时的不可变发布包；
- `Environment` 是 Build 的 Conda 环境或 Docker 镜像登记信息；
- `Job` 固化输入、参数、运行时与 Build 指纹，输出再登记为 `File`。

同一个 `nc_to_shp:1.0.0` 可以同时有 `conda-pack` 和 `docker` 两个 AMD64 Build；创建
Job 时必须显式选择 `runtime_type`。省略时 API 默认选择 Docker Build。

## 4. 一次完整 Job 的数据流

```text
上传 NC 文件
  → POST /api/v1/files
  → 得到 file_id
  → POST /api/v1/jobs（选择已 ENABLED 的 Build）
  → PENDING → PREPARING → RUNNING
  → SUCCESS / FAILED / CANCELLED / TIMED_OUT
  → GET /jobs/{id}/logs、/outputs
  → GET /files/{file_id}/download
```

取消请求只会设置 `cancel_requested`；真正停止由对应 Runner 执行。超过插件定义的时限时，
Job 进入 `TIMED_OUT`，稳定错误码为 `JOB_TIMED_OUT`。Runner 重启会把自己中断的 Job 或
安装操作标为 `HUB_RESTARTED`，不会让其他运行时的任务被领取或误处理。

## 5. Linux AMD64 首次部署

### 5.1 前置条件

推荐 Ubuntu 22.04/24.04 AMD64。运行 Hub 需要 Docker Engine、Compose v2、`curl`、`jq`
和 `openssl`；构建插件还需要 Python 3.12、Conda/Mamba 和可访问依赖源的构建网络。

```bash
uname -m                 # 预期 x86_64
docker version
docker compose version
```

不要把 Docker Socket 给 Hub 或 Conda Runner；只有 Docker Runner 有该高权限能力。

### 5.2 创建目录、配置和共享内部令牌

以下以 `/srv/python-service-hub` 为例。源码目录归当前发布者账号，方便生成构建虚拟环境
和插件产物；配置与数据单独受限。

```bash
sudo install -d -o "$(id -u)" -g "$(id -g)" -m 0755 /srv/python-service-hub
git clone <你的仓库地址> /srv/python-service-hub
cd /srv/python-service-hub

sudo install -d -o root -g 65532 -m 0750 config
sudo install -d -m 0750 /srv/python-service-hub/data
sudo install -o root -g 65532 -m 0640 config/hub.yaml.example config/hub.yaml

sudo install -o root -g root -m 0600 /dev/null .env
RUNNER_TOKEN="$(openssl rand -hex 32)" || exit 1
printf 'HUB_RUNNER_TOKEN=%s\n' "${RUNNER_TOKEN}" | sudo tee .env >/dev/null
unset RUNNER_TOKEN
```

`.env` 是 Hub 与两个 Runner 的**唯一**内部令牌来源。不要用 `sed` 修改 `compose.yaml`，
也不要把构建机的 `.env` 复制到离线目标机。若数据目录不是默认值，追加一个宿主绝对路径：

```bash
printf 'HUB_DATA_DIR=/absolute/path/service-hub-data\n' | sudo tee -a .env >/dev/null
sudo install -d -m 0750 /absolute/path/service-hub-data
```

### 5.3 启动与最小检查

```bash
sudo docker compose config --quiet
sudo docker compose up -d --build
sudo docker compose ps
curl -fsS http://127.0.0.1:8000/api/v1/system/health | jq .
```

预期健康状态为 `UP`。检查隔离边界：Hub 是唯一发布 `127.0.0.1:8000` 的服务；Docker
Socket 只能出现在 `hub-docker-runner` 的挂载中。

## 6. 注册插件的流程

插件注册分为发布者和 Hub 两个阶段。

### 6.1 发布者：同一源码生成两个独立 Build

`packages/nc-to-shp-plugin/plugin.yaml` 描述插件的输入和参数，但不写死架构。平台、运行时
和环境归属每个 `.pypkg` 的 `build.json`。

在原生 Linux AMD64 构建机执行：

```bash
cd /srv/python-service-hub
python3.12 -m venv .venv-publisher
source .venv-publisher/bin/activate
python -m pip install --upgrade pip build hatchling
python -m pip install -e packages/hub-contracts zstandard
mkdir -p packages/nc-to-shp-plugin/dist

python packages/nc-to-shp-plugin/scripts/package_build.py \
  --runtime conda-pack --arch amd64 \
  --output packages/nc-to-shp-plugin/dist

python packages/nc-to-shp-plugin/scripts/package_build.py \
  --runtime docker --arch amd64 \
  --output packages/nc-to-shp-plugin/dist
```

预期得到：

```text
nc_to_shp-1.0.0-linux-amd64-conda.pypkg
nc_to_shp-1.0.0-linux-amd64-docker.pypkg
```

Conda 包包含预构建 `conda-pack` 环境；Docker 包包含已保存的插件镜像。Hub 会校验上传包、
平台、运行时、成员路径与校验和，但不会联网补装缺失依赖。任一依赖问题都应回到发布者
环境重新构建，而不是在 Hub 服务器修补。

### 6.2 Hub：安装、等待 READY、启用

```bash
HUB_URL=http://127.0.0.1:8000
PACKAGE_DIR=/srv/python-service-hub/packages/nc-to-shp-plugin/dist

CONDA_JSON="$(curl -fsS -F "file=@${PACKAGE_DIR}/nc_to_shp-1.0.0-linux-amd64-conda.pypkg" \
  "${HUB_URL}/api/v1/plugins/install")"
CONDA_BUILD_ID="$(printf '%s' "${CONDA_JSON}" | jq -r .build_id)"

DOCKER_JSON="$(curl -fsS -F "file=@${PACKAGE_DIR}/nc_to_shp-1.0.0-linux-amd64-docker.pypkg" \
  "${HUB_URL}/api/v1/plugins/install")"
DOCKER_BUILD_ID="$(printf '%s' "${DOCKER_JSON}" | jq -r .build_id)"

watch -n 2 "curl -fsS ${HUB_URL}/api/v1/plugin-builds/${CONDA_BUILD_ID} | jq ."
# 看到 READY 后按 Ctrl+C；Docker Build 同样轮询。

curl -fsS -X POST "${HUB_URL}/api/v1/plugin-builds/${CONDA_BUILD_ID}/enable" | jq .
curl -fsS -X POST "${HUB_URL}/api/v1/plugin-builds/${DOCKER_BUILD_ID}/enable" | jq .
```

`POST /api/v1/plugins/install` 返回 `202`，因为安装由匹配的 Runner 异步执行。只有
`READY` Build 能启用；启用后状态为 `ENABLED`。

## 7. 使用 NC→SHP 插件

`nc_to_shp` 读取 HDF5/NC 中指定 Group（默认示例为 `"1"`）、网格坐标、拓扑和指标，
把单元指标映射为顶点值，并输出包含 PointZ Shapefile 组件和 `manifest.json` 的 ZIP。

输入与参数：

| 字段 | 含义 | 示例 |
| --- | --- | --- |
| `source_nc` | 已上传 NC 文件的 `file_id` | `file_...` |
| `group_name` | HDF5 Group | `"1"` |
| `metrics` | 非空指标数组 | `["depth", "stage"]` |
| `start_time` / `end_time` | 时间索引，含首尾 | `1` / `20` |
| `target_crs` | 可选 CRS | `null` 或 `EPSG:4490` |

上传并创建 Docker Job（Conda 只需把 `runtime_type` 换成 `conda-pack`）：

```bash
NC_PATH=/absolute/path/20260828213102_生成hdf5结果详情信息.nc
FILE_ID="$(curl -fsS -F "file=@${NC_PATH}" "${HUB_URL}/api/v1/files" | jq -r .file_id)"

JOB_JSON="$(curl -fsS -X POST "${HUB_URL}/api/v1/jobs" \
  -H 'Content-Type: application/json' \
  -d "{\"plugin_id\":\"nc_to_shp\",\"version\":\"1.0.0\",\"runtime_type\":\"docker\",\"inputs\":{\"source_nc\":\"${FILE_ID}\"},\"params\":{\"group_name\":\"1\",\"metrics\":[\"depth\",\"stage\"],\"start_time\":1,\"end_time\":20,\"target_crs\":null}}")"
JOB_ID="$(printf '%s' "${JOB_JSON}" | jq -r .job_id)"

watch -n 2 "curl -fsS ${HUB_URL}/api/v1/jobs/${JOB_ID} | jq ."
curl -fsS "${HUB_URL}/api/v1/jobs/${JOB_ID}/logs?cursor=0&limit=500" | jq .
```

成功后下载输出：

```bash
OUTPUT_ID="$(curl -fsS "${HUB_URL}/api/v1/jobs/${JOB_ID}/outputs" | jq -r '.items[0].file_id')"
curl -fsSL "${HUB_URL}/api/v1/files/${OUTPUT_ID}/download" -o nc-to-shp-result.zip
unzip -l nc-to-shp-result.zip
```

失败时按顺序检查 Job 的 `error_summary`、`/logs`，再检查相应 Runner：

```bash
sudo docker compose logs --tail=300 hub-conda-runner
sudo docker compose logs --tail=300 hub-docker-runner
```

## 8. 验收、备份和平台迁移

首次 AMD64 发布必须在真实 Linux Docker 主机完成双运行时验收；当前 Windows 开发机只验证
代码、配置和可跳过的集成测试。

```bash
HUB_NC_SAMPLE_PATH=/absolute/path/20260828213102_生成hdf5结果详情信息.nc \
HUB_PLUGIN_PACKAGE_DIR=/srv/python-service-hub/packages/nc-to-shp-plugin/dist \
HUB_BASE_URL=http://127.0.0.1:8000 \
python -m pytest -m integration tests/integration/test_dual_runtime_nc_to_shp.py -v
```

验收应确认两个 Build 均安装、两个 Job 均 `SUCCESS`，并且两份 ZIP 的 PointZ Shapefile
语义一致。该真实 NC 预期包含 39,464 个要素。

备份和恢复需要停掉服务，并连同实际数据目录、`.env`、`hub.yaml` 和 `compose.yaml` 一起
保存；不要把 `.env` 上传到普通制品库。完整命令见双运行时手册第 10 节。

迁移到 Linux ARM64 时，Hub 三个镜像、Conda 环境、Docker 插件镜像和 `.pypkg` 都必须重新
构建。源码和 `plugin.yaml` 保持不变；在 ARM64 配置中显式设置：

```yaml
platform_arch: arm64
```

AMD64 二进制环境不能复制到 ARM64。完成重新部署后，重复本节的注册与双运行时验收。

## 9. V1 边界与下一步

- V1 不提供应用层认证；外部访问安全由 Nginx、TLS、来源限制和防火墙承担。
- V1 不构建插件依赖；发布者对 Conda/Docker 运行环境负责。
- 包 SHA256、包内成员校验和、目标平台与运行时匹配在 V1 中强制执行。
- 源码、环境归档和镜像身份的交叉证明属于后续 V1.1 供应链加固项。

开始部署时，建议先在 AMD64 测试服务器只跑 Docker Build，再跑 Conda Build；两者都成功后
再迁移到离线 ARM64 生产环境。
