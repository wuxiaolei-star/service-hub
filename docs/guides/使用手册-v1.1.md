# Service Hub 使用手册（v1.1.0）

> 适用版本：`main` 分支 2026-09-26 起（B1–B9 插件成熟度批次上线后）。
> 本手册聚焦 v1.0 之后**新增与变化**的能力（插件生命周期、作业契约、失败分类、
> 统计与运维观测）。登录、角色权限、文件管理、定时任务、API Key 等**基础功能
> 未变**，请继续参考《[使用手册-v1.0](使用手册-v1.0.md)》。
>
> 全部行为均对照源码与 `docs/openapi.json`（57 个 path）核实，未凭空描写。

## 1. 控制台访问

| 项 | 值 |
|---|---|
| 控制台地址 | `https://${HUB_HOST}:8443`（8443 是**唯一**对外端口） |
| 传输 | HTTPS（自签证书，有效期至 2028-12） |
| 认证 | 用户名 + 密码（浏览器会话）；机器客户端用 API Key |
| API 前缀 | `https://${HUB_HOST}:8443/api/v1/` |

**自签证书信任说明**：首次访问浏览器会提示「您的连接不是专用连接」，内网可信
环境下点「继续前往」即可进入登录页；管理员也可以把服务器上的自签证书导入
客户端/办公终端的受信任根证书存储，消除该提示。替换为受信任 CA 签发的证书
时，edge 网关的挂载点不变。

基础操作（登录、改密、登录限流 429、API Key 创建与吊销）与 v1.0 完全一致，
见《使用手册-v1.0》§3 与 §8。

## 2. 插件浏览（所有角色可见）

入口：左侧「插件」/「仓库」。

### 2.1 插件与版本

- 「插件」页列出已安装插件（id、名称、描述、分类、最新版本号）。版本号按
  **数值**比较（`1.10.0` 排在 `1.9.0` 之后，不做字符串排序）。
- 点击插件可查看每个版本的公开 manifest（输入、参数、输出、执行约束）。

### 2.2 Build 状态及其含义

一次安装（一个 `.pypkg`）产生一个不可变的 **Build**（构建）。Build 有五种状态：

| 状态 | 含义 | 对用户意味着什么 |
|---|---|---|
| `INSTALLING` | 安装中（校验、落盘） | 尚不可用 |
| `READY` | 就绪，未启用 | 可被发布者显式启用 |
| `ENABLED` | 已启用 | **唯一能承接新作业的状态** |
| `FAILED` | 安装失败 | 查看构建错误信息后需重新上传修复包 |
| `DEPRECATED` | 已废弃 | **单向终态**，见下 |

**DEPRECATED（废弃）语义**（v1.1 新增）：

- 发布者通过「废弃」操作把 READY/ENABLED 的 Build 标记为废弃，含义是
  "停止服务、等待未来清理"，但注册表中**仍可见**，存储与环境目录暂不删除；
- 废弃后该 Build **不能承接新作业**（发起作业会得到 404 `PLUGIN_BUILD_NOT_ENABLED`），
  已在运行的作业不受影响；
- **废弃是单向的，没有复活端点**：`enable` 会拒绝废弃状态（409）。若要恢复该
  插件版本的服务，唯一途径是**以新版本号安装新包并启用新 Build**——同版本号
  重新安装会被唯一性约束拒绝（409 `PLUGIN_BUILD_ALREADY_EXISTS`）。

### 2.3 构建列表（API，分页）

`GET /api/v1/plugin-builds` 返回按创建时间**从新到旧**的 Build 列表，支持：

| 参数 | 说明 |
|---|---|
| `plugin_id` | 按插件 id 过滤（如 `nc_to_shp`） |
| `runtime_type` | 按运行时过滤（`docker` / `conda-pack`） |
| `limit` | 每页条数，1–200，默认 100（与历史行为兼容：不带参数仍返回最新 100 条） |
| `offset` | 翻页偏移量，默认 0 |

响应带 `total` 字段（命中过滤条件的**全量**条数），供分页计算：

```bash
curl -sk "https://${HUB_HOST}:8443/api/v1/plugin-builds?plugin_id=nc_to_shp&limit=50&offset=0" \
  -H "Authorization: Bearer <TOKEN>"
```

## 3. 发起作业（operator 及以上）

创建作业的入口与流程与 v1.0 一致（选插件/版本/运行时 → 填输入与参数 → 提交）。
v1.1 起作业契约有以下**强制语义**，填写前请确认：

### 3.1 datetime 参数必须是 ISO8601 格式

插件声明为 `datetime` 类型的参数，值必须是可解析的 **ISO8601** 字符串，例如：

- `2026-09-26T08:30:00`（本地时间，无时区）
- `2026-09-26T08:30:00+08:00`（带时区偏移）
- `2026-09-26T00:30:00Z`（UTC，`Z` 结尾）
- `2026-09-26`（仅日期，等价当天零点——合法 ISO8601）

格式不合法（如 `2026/09/26 8:30`、`昨天`）在**创建作业时**即被 422 拒绝：
`插件 datetime 参数不是合法的 ISO8601 时间`。这是 v1.1 的改进：此前错误会
推迟到插件运行时才暴露。

### 3.2 必填输出的语义（required）

插件 manifest 可把某个输出声明为 `required`。v1.1 起，平台在作业完成时
**强制校验**：

- 声明为 `required` 的 `file` / `files` 型输出，若插件没有实际产出并登记，
  作业即使自报成功也会被平台**改判为 `FAILED`**，错误码
  `PLUGIN_OUTPUT_MISSING`，错误信息列出缺失的输出名；
- `object` 型输出（结构化数据，不产生文件）**明确豁免**该校验——manifest v1.0
  没有为其定义服务端校验契约。

对使用者的含义：作业 `FAILED` 且错误码是 `PLUGIN_OUTPUT_MISSING` 时，说明
**插件本身没交齐它承诺的产物**（不是你的输入问题），请把作业链接反馈给插件
作者，排查动作见 §5。

### 3.3 并发限制（409 PLUGIN_CONCURRENCY_LIMIT）

每个插件 Build 在 manifest 里声明了 `execution.concurrency`（**必填字段**，
最小 1），即该构建最多同时承载多少个非终态作业（排队 PENDING / 准备
PREPARING / 运行 RUNNING 都计入）。超限的创建请求得到：

> 409 `PLUGIN_CONCURRENCY_LIMIT` "插件 Build 并发作业数已达上限"
> （details 携带 `build_key`、`active` 当前活跃数、`limit` 上限）

**含义与处置**：

- 这是平台的**防过载闸**，适用于所有人，**包括定时调度触发**——同一构建上
  挂了慢作业时，每小时的调度也可能被 409 拒一次，下一轮调度窗口会自动恢复，
  无需人工干预；
- 手动发起被 409 时：稍等现有作业跑完再试；如确需更高吞吐，找插件作者评估
  后由发布者安装更高 `concurrency` 的新版本；
- 注意与**每用户并发配额**区分：那是按用户计的反滥用配额（默认
  `max_concurrent_jobs: 8`），错误码为 `QUOTA_EXCEEDED`。

## 4. 调度与统计

### 4.1 定时调度

定时任务的创建/停用/删除与 v1.0 一致。v1.1 的一项行为变化：调度触发的作业
**同样受 §3.3 的单构建并发闸约束**（被 409 拒后下一轮自动重试）。

### 4.2 作业统计（按插件聚合，v1.1 新增）

`GET /api/v1/jobs/stats?by=plugin` 返回每个插件在窗口期内的聚合：

| 字段 | 含义 |
|---|---|
| `total / success / failed / cancelled / timed_out` | 各终态计数 |
| `failure_classes` | 五类失败分布（见 §5），键恒全 |
| `p50_ms / p95_ms` | 作业耗时中位数与 95 分位 |

参数：`days`（回看天数，1–90，默认 14）。

```bash
curl -sk "https://${HUB_HOST}:8443/api/v1/jobs/stats?by=plugin&days=30" \
  -H "Authorization: Bearer <TOKEN>"
```

不带 `by` 参数时仍返回 v1.0 的逐日统计（完全向后兼容）。

管理员还可以抓取 Prometheus 指标 `GET /api/v1/system/metrics`（**仅 admin**），
其中与本手册相关的两条：`hub_job_duration_seconds`（作业耗时直方图）与
`hub_jobs_total{plugin,runtime,status}`（按插件/运行时/状态分组的作业计数）。
接入与抓取说明见《[运维手册](运维手册.md)》。

## 5. 作业失败排查（failure_class 五分类，v1.1 新增）

平台把每个失败终态作业归入**五类之一**（作业错误摘要前缀 + 终态推导，零存储
迁移、对历史作业同样生效）：

| failure_class | 判定 | 典型场景 | 第一排查动作 |
|---|---|---|---|
| `plugin` | 错误码为 `PLUGIN_*`（含 `PLUGIN_OUTPUT_MISSING`），或来自插件 SDK 的自定义错误码 | 插件逻辑失败、必填输出未产出、插件校验拒绝输入 | 看 `GET /jobs/{id}/logs` 末尾的插件日志与错误码；`PLUGIN_OUTPUT_MISSING` = 插件没交齐承诺产物，反馈插件作者；确认输入文件内容合法（v1.0 的空 NC 文件案例即此类） |
| `timeout` | 终态 `TIMED_OUT`，或错误码 `JOB_TIMED_OUT` | 作业超过 manifest `execution.timeout` 被终止 | 确认输入数据规模是否异常增大；由插件作者评估放宽超时或优化插件 |
| `cancelled` | 终态 `CANCELLED` | 有人取消，或平台重挂在途作业 | 属预期行为，无需排查；确认是否本人/同事操作 |
| `runner` | 错误码 `RUNNER_FAILED` / `HUB_RESTARTED` | 运行器/容器层故障（如镜像缺失、Hub 重启打断） | 典型症状是作业**秒败**（毫秒级 FAILED）。联系运维（《运维手册》§8 事故卡①：插件镜像缺失的恢复）；`HUB_RESTARTED` 说明作业被服务重启打断，重新发起即可 |
| `system` | 失败但无错误码前缀，或来自平台内部 | 存储配额、数据库、平台内部错误 | 记录作业 id 与时间，联系运维查 `journalctl` 与审计日志 |

**速记**：先看 `GET /jobs/{id}` 返回的 `status` 与 `error_summary`——
`错误码: 消息` 前缀即分类依据；统计口径的分布直接用 §4.2 的 `by=plugin`
聚合里的 `failure_classes`。

> 已知边界：插件进程未写 result.json 即死亡（如内存超限被杀，退出码 137）时，
> 平台只能归入 `runner`（无插件裁决可引用）。

## 6. 面向插件作者：一页速查

完整开发流程（脚手架 → plugin.yaml 规范 → SDK → 双运行时约束 → 构建 →
上架 → 验收清单）见《**[插件开发者指南](插件开发者指南.md)**》，本节只是命令速查。

命令行工具 `hub-plugin`（随 `python-hub-publisher` 包提供；签名子命令需
`pip install 'python-hub-publisher[signing]'`）：

| 命令 | 用途 | 关键参数 |
|---|---|---|
| `hub-plugin validate <project>` | 发布前三级校验：项目 / 运行时 / 构建产物，任一问题以非零退出并列出，服务端安装用同一套规则 | `--runtime conda-pack\|docker`（校验指定运行时布局）；`--package <pypkg>`（按服务端同规则校验构建产物） |
| `hub-plugin dev <project>` | **零 Hub 本地试跑**：合成一次性作业工作区（input/work/output/logs + job.json），走真实 runner 协议并按契约校验 result.json | `--input NAME=FILE`（可重复；省略 NAME 时按扩展名自动匹配 manifest 输入）；`--param NAME=VALUE`（可重复，按 manifest 类型自动转型并校验）；`--mode python\|docker`（默认 python；docker 模式需本机 Docker，并按作业容器同款约束运行：无网络、非 root、只读根文件系统）；`--keep`（保留临时工作区以便检查） |
| `hub-plugin build <project>` | 构建不可变 `.pypkg` | `--runtime conda-pack\|docker`、`--arch amd64\|arm64`、`--output <dir>`（均必填；conda-pack 必须在目标架构原生 Linux 上构建） |
| `hub-plugin keygen` | 生成 Ed25519 签名密钥对（B9） | `--out-prefix <prefix>`（默认 `./hub-plugin-key`，产出 `<prefix>.sec` / `<prefix>.pub`；已存在则拒绝覆盖；私钥离线保管，绝不入 git/CI/服务端） |
| `hub-plugin sign <pkg>` | 给构建产物签名（B9） | `--key <sec>`（默认 `./hub-plugin-key.sec`）；`--out <sig>`（默认 `<pkg>.sig`）；上传时 multipart 同时带 `file` + `signature` 两个字段 |

服务端验签（部署方配置，`config/hub.yaml`）：

```yaml
plugins:
  signature:
    public_keys:        # <prefix>.pub 第二行的 base64 原样粘贴；多把并存，任一验过即通过
      - "<base64 公钥>"
    require_signed: false   # true = 未附有效签名的包 422 拒收（须至少登记一把公钥）
```

行为矩阵：**未配置公钥 = 与既往完全一致**（附签也忽略）；配置公钥后，带签
必验、失败 422 `PLUGIN_PACKAGE_SIGNATURE_INVALID`，不带签放行（渐进过渡）；
`require_signed: true` 后不带签 422 `PLUGIN_PACKAGE_SIGNATURE_REQUIRED`。
篡改过的包会被 422 拒收。轮换公钥：**先加新钥、确认新包验过后再删旧钥**。

> `hub-plugin dev` 的边界：不模拟 conda-pack 运行时（conda-only 项目会得到
> 可读的拒绝提示，请用 `--mode python` 直接驱动入口或在 Linux 构建后经 Hub
> 安装运行）；无法为 manifest 声明的必需环境变量提供真实值（会给出警告）。

### 插件作者上线前自查（浓缩版，完整版见开发者指南 §7）

- `validate`（项目 + `--runtime` + `--package`）三关全过；
- `required` 的 `file`/`files` 输出确实会被产出（B5 后缺失即 FAILED）；
- datetime 类参数在文档中写明期望格式（ISO8601）；
- 两种运行时都能跑通（双运行时输出一致性由平台 harness 钉住，接入方式见
  开发者指南 §5.4）；
- 如部署启用了验签：公钥已登记、附签上传返回 202、篡改包被 422 拒。
