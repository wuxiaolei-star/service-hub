# 部署与脚本插件使用

本指南覆盖 Python Service Hub 的标准部署与使用流程（V3.0 口径）。核心是一个
`service-hub` 后端容器（内含 hub-api、conda-runner、docker-runner、cleaner、
scheduler、service-manager 六个受管进程）加一个 `service-hub-web` 控制台容器；
生产环境另加一个 edge TLS 终止容器对外服务。插件依赖仍由发布者提前在目标平台
构建，Hub 不执行在线依赖安装或编译。

- 目标平台：原生 Linux AMD64（x86_64）
- 运行镜像：`python-service-hub:1.0.0-linux-amd64` + `python-service-hub-web:1.0.0-linux-amd64`
- 唯一必填部署变量：`HUB_HOST_DATA_DIR`（宿主机数据绝对路径，容器内固定为 `/data`）
- 容器内仅 docker-runner 与 service-manager 进程获得 Docker Socket 访问权限

## 1. 安装 Docker

宿主机需要 Docker Engine 和 Docker Compose v2 插件：

```bash
docker version --format '{{.Server.Version}}'
docker compose version
```

离线环境可先在联网机器下载 `.deb`/`.rpm` 安装包与 compose 插件二进制后按发行版手册
安装；能访问外网时使用 `get.docker.com` 脚本或发行版仓库即可。

## 2. 导入离线镜像或从源码构建

方式 A：导入离线发布包内的镜像（发布包用 `deploy/release/build-release.sh` 制作）：

```bash
docker load -i service-hub-image.tar
docker image inspect python-service-hub:1.0.0-linux-amd64
```

方式 B：在已放置源码的宿主机直接构建：

```bash
cd /srv/python-service-hub
sudo docker build -t python-service-hub:1.0.0-linux-amd64 .
```

## 3. 设置数据绝对路径

`HUB_HOST_DATA_DIR` 必须是宿主机绝对路径，不能是 `./data` 之类的相对路径：Docker
Runner 会把该值交给宿主 Docker daemon 作为插件 Job 容器的 bind source，相对路径会让
插件容器挂载失败。路径至少两级，且不得使用 `/`、`/srv`、`/tmp`、`/var`、`/data`。

```bash
sudo install -d -m 0750 /srv/service-hub-data
```

## 4. 一条 Compose 命令启动

在仓库根目录（含 `compose.yaml`）执行：

```bash
sudo HUB_HOST_DATA_DIR=/srv/service-hub-data docker compose up -d
```

`compose.yaml` 声明 `service-hub` 与 `service-hub-web` 两个长期运行服务：后端监听
`127.0.0.1:8000`（数据目录与 `/var/run/docker.sock` 挂入容器），控制台监听
`127.0.0.1:8080`。对外暴露建议再加一个 edge TLS 终止容器（参见
`docs/guides/Web管理台构建部署与使用.md`）。等待健康检查通过：

```bash
watch -n 5 "docker compose ps"
```

容器健康后验证 Hub API：

```bash
curl http://127.0.0.1:8000/api/v1/system/health
# 期望输出：{"status":"UP"}
```

## 5. 日常运维：health、logs、stop、restart

```bash
docker compose ps                                   # 容器与健康状态
docker compose logs -f service-hub                  # 六个受管进程的聚合日志
docker compose stop                                 # 停止（保留容器）
docker compose restart                              # 重启（数据在 HUB_HOST_DATA_DIR 中持久化）
docker compose up -d                                # 启动已停止的容器
docker exec service-hub python -m deploy.service_hub.healthcheck   # 容器内自检
```

容器内由 supervisord 管理 `hub-api`、`conda-runner`、`docker-runner`、`cleaner`、
`scheduler`、`service-manager` 六个降权进程，单个进程崩溃会自动重启，容器停止时收到
SIGTERM 并优雅结束当前插件进程。健康门要求这六个进程全部处于 RUNNING。

## 6. 使用 hubctl 注册和运行插件

`tools/hubctl` 是基于 Python 标准库的宿主机管理客户端（Python 3 即可运行，无需安装
第三方依赖），通过 `HUB_URL` 指向 Hub，默认 `http://127.0.0.1:8000`。

```bash
# 查看健康与已安装插件
HUB_URL=http://127.0.0.1:8000 python tools/hubctl health
HUB_URL=http://127.0.0.1:8000 python tools/hubctl plugin list

# 安装发布者构建好的 .pypkg（conda 与 docker 包都走同一入口）
HUB_URL=http://127.0.0.1:8000 python tools/hubctl plugin install \
    packages/nc-to-shp-plugin/dist/nc_to_shp-1.0.0-linux-amd64-conda.pypkg
HUB_URL=http://127.0.0.1:8000 python tools/hubctl plugin install \
    packages/nc-to-shp-plugin/dist/nc_to_shp-1.0.0-linux-amd64-docker.pypkg

# 上传输入文件并创建 Job
HUB_URL=http://127.0.0.1:8000 python tools/hubctl file upload sample.nc
HUB_URL=http://127.0.0.1:8000 python tools/hubctl job run nc_to_shp \
    --version 1.0.0 --runtime conda-pack --input source_nc=file_<id> \
    --params params.json
HUB_URL=http://127.0.0.1:8000 python tools/hubctl job status job_<id>
HUB_URL=http://127.0.0.1:8000 python tools/hubctl job logs job_<id>
HUB_URL=http://127.0.0.1:8000 python tools/hubctl job cancel job_<id>

# 下载 Job 输出
HUB_URL=http://127.0.0.1:8000 python tools/hubctl job download job_<id> --output ./outputs
```

`job run --params` 接受一个 JSON 文件；`--input` 以 `输入名=file_<id>` 形式重复传入。
命令成功时向 stdout 输出格式化 JSON，失败时向 stderr 输出 Hub 的 code/message 并返回
非零退出码。

## 7. 使用 hub-plugin 创建两种脚本插件

`packages/hub-publisher` 提供通用的 `hub-plugin build` 命令，把任意符合目录约定的插件
项目构建为 `.pypkg`。新建业务脚本时直接复制模板改名：

- `templates/conda-script-plugin/`：conda-pack 运行时（依赖写进 `environment.yml`）
- `templates/docker-job-plugin/`：Docker 运行时（依赖写进 `Dockerfile`）

```bash
cp -r templates/conda-script-plugin /srv/my-plugins/my_tool
cd /srv/my-plugins/my_tool
# 修改 plugin.yaml 中的 plugin.id/name/version，编辑 src/<包名>/main.py 实现 run()
```

插件入口保持 `run(params, inputs, context)` 三参数签名，通过 `context.output_file()`
写出结果并返回 `PluginResult`。构建必须在目标 Linux 平台执行（conda-pack 要求本机
架构与目标一致；Docker 构建显式传 `--platform`）：

```bash
# conda-pack 构建（需要本机 conda 与 conda-pack）
hub-plugin build . --runtime conda-pack --arch amd64 --output dist

# Docker 构建（需要本机 docker）
hub-plugin build . --runtime docker --arch amd64 --output dist
```

构建成功会打印 `.pypkg` 绝对路径与 SHA256；随后按第 6 节 `hubctl plugin install`
注册。NC→Shapefile 示例插件同样使用这一入口：

```bash
hub-plugin build packages/nc-to-shp-plugin --runtime conda-pack --arch amd64 \
    --output packages/nc-to-shp-plugin/dist
hub-plugin build packages/nc-to-shp-plugin --runtime docker --arch amd64 \
    --output packages/nc-to-shp-plugin/dist
```

## 8. 认证与用户管理（V2.0）

Hub V2.0 起默认启用应用层认证（`HUB_AUTH_MODE=required`）：

- 首次启动时在数据目录生成 `bootstrap-admin.json`（0600），内含初始 admin 用户名与
  一次性口令；登录后请立即修改口令；
- 浏览器访问 8080 管理台登录后即可操作；`hubctl login` 保存凭证到
  `~/.hubctl/credentials`，业务系统使用管理台签发的 API Key（`HUB_TOKEN` 环境变量）；
- 角色分四级：viewer（只读）、operator（上传/建任务/下载）、publisher（安装插件/
  启停 Build）、admin（用户与 Key 管理、审计查询）；
- 临时关闭认证：hub.yaml 的 `auth.mode: off` 或环境变量 `HUB_AUTH_MODE=off`；
- 全部写操作（含登录失败）记录于审计日志，管理台"审计"页可查。

## 9. 配额、清理与备份（V2.1）

- **配额**：hub.yaml `quotas` 节控制全局与每用户默认（总存储/文件数/并发 Job）；
  用户级覆盖在"用户管理"中通过数据库列调整，超限返回 409 `QUOTA_EXCEEDED`（含
  used/limit 详情）；admin 角色不受限，`enabled: false` 全部直通；
- **清理**：supervisord 第四个受管进程 `cleaner` 每 30 分钟扫描一次，删除超过
  `input_ttl_hours` 且未被任何 Job 引用的输入文件（OUTPUT 与被引用文件永不清理），
  删除动作写入审计日志；
- **指标**：`GET /api/v1/system/metrics`（admin，Prometheus 文本）暴露 Job 状态分布、
  存储字节、用户/会话数、配额上限与进程运行时长；
- **备份**：`POST /api/v1/system/backup`（admin）或 `hubctl backup create` 在数据目录
  `backups/` 下生成 `backup-<时间戳>.tar.gz`（SQLite 快照 + 数据文件，排除
  environments/logs），自动保留最近 `backup_keep` 份；`hubctl backup restore --file`
  打印人工恢复步骤清单（不自动执行破坏性操作）；每次备份写审计。

## 10. 自动化闭环（V2.2）

- **Webhook 回调**：创建 Job 时在请求体加可选
  `"callback": {"url": "https://...", "secret": "可选"}`；Job 终态后由 scheduler 进程
  POST 通知，头 `X-Hub-Signature: sha256=<HMAC>`，失败自动重试 3 次（60s×次数退避）；
  投递状态在任务详情页"Webhook 回调"卡查看；
- **回调地址出站策略（安全默认拒绝）**：回调由容器内的 scheduler 发起，而 Hub API（8001）与
  service-manager 都监听回环，因此回调地址默认只允许**公网**目标——注册期内网/回环/链路本地
  （含云元数据 `169.254.169.254`）以及 `localhost`、整型混淆写法（`2130706433`）一律返回
  `422 WEBHOOK_URL_FORBIDDEN`，投递前还会再解析一次 DNS 复核（防 DNS 重绑定）；
  需要回调到内网服务时，在 `config/hub.yaml` 显式开启：
  ```yaml
  webhooks:
    allow_private_networks: true   # 允许回调打到内网/回环（关闭地址维度的拦截）
    allowed_hosts: []              # 可选：非空时只允许这些主机，如 ["hooks.corp.example", "*.corp.example"]
  ```
  注意 `allowed_hosts` 是在地址守卫之上**继续收紧**，不能用来放行内网地址；
- **定时任务**：管理台"定时任务"页或 `POST /api/v1/schedules` 创建周期规则
  （插件/版本/运行时/输入/参数/间隔分钟），scheduler 到点自动建 Job，`next_run_at`
  自动推进，Build 缺失时审计 denied 且不推进；
- **线性管道**：`POST /api/v1/pipelines` 定义步骤链（下一步输入用
  `"$prev.<上一步输出名>"` 引用上一步产物），`POST /pipelines/{id}/execute` 启动；
  步进由 scheduler 自动完成，任一步失败整条 FAILED；管理台"管道"页可执行并查看
  运行进度；
- scheduler 是 supervisord 第五个受管进程，崩溃自动重启，全部状态落库可续。

## 11. 仓库、秒传与实时日志（V2.3）

- **插件仓库**：管理台"仓库"页（或 `GET /api/v1/registry/plugins`）列出全部已安装
  Build；publisher+ 可下载对应 `.pypkg`（审计 registry.download）；
  `hubctl registry list|pull <build_key> --output <目录>|sync --output <目录>` 在多台
  Hub 间同步插件（sync 全量拉取 ENABLED 包并打印 SHA256）；
- **秒传查重**：上传前调 `GET /api/v1/files/by-sha256/<64位哈希>`（operator+），
  命中直接复用既有 file_id 跳过传输；管理台文件页已内置查重入口；
- **SSE 实时日志**：`GET /api/v1/jobs/{key}/logs/stream`（viewer，text/event-stream）
  游标增量推送、终态发 `end`；管理台任务详情页活跃任务自动切换 SSE（轮询兜底）。

## 12. Nginx 边界

Hub V1 没有应用层认证，必须保持只监听 `127.0.0.1:8000`，由 Nginx 提供 TLS、来源网段
限制并代理业务流量；主机防火墙禁止外部直接访问 8000 端口，禁止外部访问
`/internal/v1`。参考 `deploy/nginx` 中的边界配置。

需要浏览器图形界面时，部署 Web 管理台（服务 `service-hub-web`，镜像
`python-service-hub-web:1.0.0-linux-amd64`，监听 `127.0.0.1:8080`）：它会通过 Nginx
代理 `/api/v1` 到本后端并拒绝 `/internal/v1`。构建、部署与页面操作见
[Web管理台构建部署与使用](Web管理台构建部署与使用.md)。

## 旧数据迁移、备份与升级

- 备份：停止写入后直接归档数据目录即可，`sudo tar -czf /backup/service-hub-data-$(date +%F).tar.gz -C /srv service-hub-data`。
  恢复前先 `docker compose stop`，恢复数据目录后重新启动。
- 迁移到新服务器：备份并恢复 `HUB_HOST_DATA_DIR` 指向的目录，在新机导入同一镜像并
  以同一数据路径启动；SQLite、文件、插件 Build 与 Job 记录全部在数据目录内。
- 升级镜像：`docker compose stop` → 导入新版本镜像（或重新 build）→ `docker compose up -d`；
  数据库结构变更由容器启动时的 Alembic 迁移自动完成，升级前务必先完成备份。
- 禁止执行 `docker compose down -v`：本项目数据在宿主机 bind 目录中，虽然 Compose
  没有命名卷，但 `down -v` 一类清理习惯会连带删除容器和未知状态，日常生命周期只使用
  `stop`/`restart`/`up -d`。
- 旧三容器部署的数据目录（`/srv/python-service-hub/data`）可直接作为
  `HUB_HOST_DATA_DIR` 指向的目录复用；首次启动时 entrypoint 会执行一次版本化权限迁移
  （生成 `/data/.permissions-single-container-v1` 标记）。

## 常见错误

| 现象 | 检查命令 | 说明 |
| --- | --- | --- |
| 容器一直 unhealthy | `docker compose logs service-hub` | 查看六个受管进程哪个 FATAL；常见原因是数据目录权限或 Token 文件缺失 |
| `HUB_HOST_DATA_DIR must be set` | `docker compose config` | Compose 启动时未设置数据目录变量，按第 4 节重新执行 |
| 插件容器挂载失败 | `docker compose exec service-hub env \| grep HUB_HOST_DATA_DIR` | 数据路径不是宿主机绝对路径，Docker daemon 无法作为 bind source |
| `plugin install` 返回 4xx | `python tools/hubctl plugin list` | 同 id+version 已有不同 source_sha256 的 Build，或包损坏；核对发布包 SHA256 |
| Job 一直 PENDING/RUNNING | `docker compose logs service-hub \| grep -i runner` | 对应运行时 Runner 进程未接管；确认容器健康后再重试 |
| Docker Runner 报 permission denied | `docker compose exec service-hub id docker-runner` | Socket 组权限未注入，确认宿主机 `/var/run/docker.sock` 存在并重启容器 |
| 8000 端口无法访问 | `curl http://127.0.0.1:8000/api/v1/system/health` | Hub 只监听回环地址；确认是从宿主机本机访问，外部流量应走 Nginx |
