## 一、缺陷（已确认，建议修）

### D-1 上传配额可被绕过，且失败后残留已落盘文件与已提交记录

**位置**：`routers/files.py:77-85`、`services/files.py:59-74`、`services/quotas.py:47-85`

**问题**：上传的配额检查存在三段缝隙。

1. **预检可被绕过**（`files.py:78`）：
   ```python
   quota.enforce_upload(actor, int(request.headers.get("content-length", "0") or 0))
   ```
   使用 `Transfer-Encoding: chunked` 时没有 `Content-Length`，默认取 `"0"` → 预检恒通过，无法在上传开始前拒绝任何超配额请求。

2. **补检发生得太晚**（`files.py:85`）：
   ```python
   quota.enforce_upload(actor, record.size_bytes, exclude_file_id=record.id)
   ```
   该调用在 `_stream_multipart_file` 返回之后，此时 `store_installed_upload`（`files.py:199`）内部已执行 `session.commit()`，**文件已落盘、FileRecord 已入库**。此刻若抛 `QUOTA_EXCEEDED`（409），实际结果是：数据已永久写入、HTTP 却报失败，调用方无法获知 file_key，形成不可管理的孤儿文件。

3. **并发竞态**（`quotas.py:47-85`）：`enforce_upload` 是「先查后写」，没有任何行锁或事务隔离保证。N 个并发上传可同时读到相同的 `used_bytes` 并一起通过检查，总占用突破 `max_total_bytes`。

**影响**：全局磁盘配额（`max_total_bytes`）与单用户配额均不可靠；超配额上传会先污染磁盘再报错；无上限的 chunked 上传可直接打满磁盘。

**建议**：
- 预检改为基于 `Content-Length` 的**硬前置拒绝**（缺失即拒绝或按 `uploads.max_size_bytes` 兜底），避免默认 `"0"` 静默通过；
- 将配额校验**下沉到流式写入过程中**（`StreamingUpload.write` 已有 `max_size_bytes` 计数，可扩展为叠加用户/全局已用量的动态上限），做到「边写边算、超限即 abort」，而不是等落盘后再判；
- 落盘后的补检若失败，必须**补偿删除文件并回滚记录**（现有 `storage.remove_upload` 可复用），不能只返回 409；
- 全局配额改为在同一个 `BEGIN IMMEDIATE` 事务内「校验 + 插入」，或对 `file_records` 加应用级互斥，消除竞态。

### D-2 `list_files` 无所有者过滤，viewer 可读取全部用户文件元数据

**位置**：`routers/files.py:100-111`

**问题**：
```python
records = session.scalars(
    select(FileRecord)
    .where(FileRecord.status == "AVAILABLE")
    .order_by(FileRecord.created_at.desc())
    .limit(100)
).all()
```
查询只按状态过滤，**没有 `owner_user_id` 条件**。任何具备 `viewer` 角色的账号都能列出所有用户上传文件的 `name` / `size` / `sha256` / `extension` / `created_at`。同时 `get_file_metadata`（`files.py:245-254`）与 `download_file`（`files.py:218-242`）也只按 `file_key` 查找，同样缺少归属校验——**知道 file_key 即可下载他人文件**。

**影响**：多用户场景下的横向越权（信息泄露 + 文件越权下载）。若系统设计为「团队共享文件池」则属预期行为，但当前代码与文档均未说明这一点。

**建议**：明确语义并在代码中体现——若非共享设计，则给 `list_files` 加 `FileRecord.owner_user_id == actor.id` 过滤（admin 除外），并在下载/元数据端点补归属校验，返回 404 而非 403 以避免泄露存在性。

### D-3 全部列表端点固定 `limit(100)`，无分页

**位置**：`routers/files.py:109`、`routers/jobs.py:88`、`routers/plugins.py:131`（其余列表端点同构）

**问题**：`limit(100)` 硬编码，无 `limit`/`offset` 或游标参数。数据量超过 100 后，**更早的记录对 API 与 Web 控制台永久不可见**，且没有任何「还有更多」的信号（无 `total`、无 `next_cursor`）。Job 日志端点（`jobs.py:145-146`）已实现游标分页，说明团队具备该模式，只是未推广。

**影响**：审计/排查场景下历史记录不可达；控制台列表会「静默截断」，用户误以为数据丢失。

**建议**：为列表端点统一引入 `limit + cursor`（沿用 `JobLogResponse.next_cursor` 的既有模式），或在响应中至少返回 `total` 与 `truncated` 标志。

### D-4 `list_jobs` 存在 N+1 查询

**位置**：`routers/jobs.py:88` 与 `_job_response`（`jobs.py:169-183`）

**问题**：
```python
# 查询只 select(Job)，未 eager load
jobs = session.scalars(select(Job).order_by(Job.created_at.desc()).limit(100)).all()
# 序列化时逐条触发惰性加载
plugin_version = job.plugin_build.plugin_version   # 2 次查询/条
plugin_id=plugin_version.plugin.plugin_key         # 1 次查询/条
```
单次请求最坏产生 1 + 100×3 = **301 次 SQL**。

**对照**：`routers/plugins.py` 处理得很好（第 80、95、129 行均显式 `selectinload`），说明这是遗漏而非设计取舍。

**建议**：
```python
.options(
    selectinload(Job.plugin_build)
    .selectinload(PluginBuild.plugin_version)
    .selectinload(PluginVersion.plugin)
)
```
降到固定 4 次查询。

### D-5 认证端点无登录限流与账户锁定

**位置**：`routers/auth.py`（全文件）、`services/auth.py`

**问题**：全文件检索 `rate` / `attempt` / `lock` / `throttle` 均无实现，仅在失败时写一条审计 `auth.login_failed`（`auth.py:84`）。密码校验无失败计数、无指数退避、无临时锁定。

**影响**：在线暴力破解无任何阻力。虽然部署定位为内网/离线环境，但 Web 控制台若经反向代理暴露，风险显著上升。

### D-6 SQLite 未启用 WAL，多进程并发写有 `database is locked` 风险

**位置**：`db.py:13-25`

**问题**：
```python
engine = create_engine(url, connect_args={"check_same_thread": False})
# 仅设置了 PRAGMA foreign_keys=ON
```
本架构下**至少 5 个进程同时写同一个 SQLite 文件**：`hub-api`（请求写入）、`cleaner`（清理）、`scheduler`（触发计划并推进 `next_run_at` + 写审计）、`conda-runner` / `docker-runner`（回报 Job 状态）。SQLite 默认使用 rollback journal 且 `busy_timeout` 为 0——一旦发生写冲突**立即抛 `database is locked`**，上层没有任何重试逻辑，会直接冒泡为 500。

**影响**：并发稍高（例如调度触发与用户请求重叠）即出现随机 500；随数据量增长概率上升。这是当前架构下最可能在生产触发的一类故障。

**建议**（零成本、收益最高）：
```python
engine = create_engine(
    url, connect_args={"check_same_thread": False, "timeout": 30}
)
# connect 事件内追加：
cursor.execute("PRAGMA journal_mode=WAL")
cursor.execute("PRAGMA busy_timeout=30000")
cursor.execute("PRAGMA synchronous=NORMAL")
```
WAL 允许读写并发，`busy_timeout` 让写冲突排队重试而非立即失败。注意 WAL 依赖共享内存，`/data/db` 若挂在不支持 mmap 的网络文件系统上则不适用（离线单机部署通常无此问题）。

### D-7 `lifespan` 每次启动执行 `alembic upgrade head`，无并发保护与降级保护

**位置**：`main.py:64-76`（`command.upgrade(..., "head")` 在第 67 行）

**问题**：
1. 迁移在**每次应用启动**时执行，而非部署阶段一次性执行。若 `hub-api` 配多 worker 或进程快速重启，存在并发跑迁移的窗口（Alembic 在 SQLite 上无跨进程迁移锁）。
2. 没有「数据库 schema 版本高于代码期望版本」的检测。**回滚部署（旧镜像 + 新数据库）会直接崩**，且错误发生在启动阶段，容器反复重启。

**建议**：将迁移移到 `docker-entrypoint.sh`（单次执行后再 `exec supervisord`），或在 `lifespan` 内先取 Alembic 文件锁 + 比对当前 revision 与 `head`，高于则拒绝启动并给出明确日志。

### D-8 健康检查中的 Docker 探针身份存疑

**位置**：`deploy/service_hub/healthcheck.py:124-135`、`Dockerfile:41-42`

**问题**：`HEALTHCHECK` 以**镜像默认用户（root）**执行 `python -m deploy.service_hub.healthcheck`，其中 `_docker_is_up()` 调用 `docker.from_env().ping()`。探针用户是 root，root 通常可访问 `/var/run/docker.sock`，因此检查本身能通。但这里存在两点不一致：

- `_docker_is_up()` **捕获了所有异常并返回 False**（`healthcheck.py:133-134`），所以任何权限、路径、SDK 问题都会被误报为「Docker Engine 不可用」，排查时具有误导性；
- 该探针**使用 root 权限做 Docker API 调用**，与「降权运行」的整体安全设计不一致——虽然只是 `ping`，但扩大了攻击面（容器内进程被控即持有 socket 访问权）。

**建议**：把探针做成显式降权（或在 `_docker_is_up` 中以 `service-mgr` 之外的专用身份执行），并把 `except Exception` 收窄为具体异常类型，同时在 stderr 输出失败原因分类，避免「一律报 Docker 不可用」。

### D-10 `scheduler` 注册的扫描任务签名不匹配，定时任务与管道推进从未真正执行（本轮新增）

**位置**：`deploy/service_hub/scheduler_service.py:22-32`（`_register_default_tasks`）+ `services/schedules.py:20-25`、`services/pipelines.py:62-67`

**问题**：任务注册表约定「一个任务只接收一个 `session`」（`main()` 的循环写作 `worked = task(session)`），
但注册进去的是三个**原始服务函数**：

```python
register_task(deliver_due)    # (session, now=None)                      → 恰好可调用
register_task(trigger_due)    # (session, storage, settings, now=None)   → 缺 2 个必填参数
register_task(advance_runs)   # (session, storage, settings, now=None)   → 缺 2 个必填参数
```

`trigger_due` 与 `advance_runs` 都需要 `storage`（建 Job 要准备 workspace）与 `settings`，注册时没有任何地方补齐。
而 `main()` 的扫描循环用 `except Exception` 做了**任务级异常隔离**（`scheduler_service.py:54-61`），
于是每 30 秒一次的 `TypeError: trigger_due() missing 2 required positional arguments` 只写进日志，
supervisord、健康检查、`/api/v1/system/metrics` 全部照常显示健康。

**后果**（两条 V2.2 能力在部署形态下完全失效，且静默）：

- **定时任务永不触发**：`schedules.next_run_at` 永不推进，管理台「定时任务」页看到的规则永远不会产生 Job；
- **管道永不推进**：`pipeline_runs` 永远停在第一步的 `RUNNING`，第二步及以后永不创建。

**为什么此前没被发现**：唯一可调用的 `deliver_due` 恰好不需要额外参数，所以 webhook 回调（集成测试唯一断言的那条自动化链路）
一直是通的，容易反推「自动化整体正常」；单元测试直接调用 `trigger_due(session, storage, settings)`，
绕过了调度器的注册层，签名不匹配落在测试盲区里。

**修复**（已实施）：`_register_default_tasks(settings)` 在启动时构造三个只接收 `session` 的适配器，
把 `LocalStorage(settings.storage.root)`、`settings`、`settings.webhooks` 绑定进去；`_TASKS` 的类型由
`Callable[[object], int]` 收紧为 `Callable[[Session], int]`，让同类错误在类型检查阶段就暴露。
新增 `tests/deploy/test_scheduler_process.py` 锁定行为：

- 注册表必须恰好是 `deliver_callbacks / trigger_schedules / advance_pipelines`，且每个任务都能**只用一个 `session`** 调用；
- 在预置「已到期 Schedule」的库上执行 `main(once=True)` 后，必须出现一条 `schedule.trigger` 审计记录——
  证明扫描真的走到了业务服务内部，而不是抛异常被吞之后再返回 0。

### D-11 审计与限流的来源地址在双层代理下退化为容器网关（自托管部署准备中发现，编号对照 V-5）

**位置**：`web/nginx.conf:41`（`proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for`）+
`packages/hub-server/src/hub_server/dependencies_auth.py`（`actor_ip()`）

**问题**：`actor_ip()` 取 `X-Forwarded-For` 最右侧条目——这对**单跳**代理是防伪造的正确做法。但实际拓扑是两跳：

```text
浏览器 ──► Web 容器内 Nginx ──► hub-api
```

Web 容器经 Docker 端口发布（`127.0.0.1:8080`）接收连接时，`$remote_addr` 是 **Docker 网关地址**
（如 `172.17.0.1`）而非真实客户端；`$proxy_add_x_forwarded_for` 把该网关地址追加到末尾，
于是 hub-api 读到的最右侧条目恒为网关地址。

**后果**：审计日志的来源地址失去取证价值；登录限流的 `(用户名, 来源地址)` 分桶退化为「用户名」单维度——
同一账号在不同来源共享同一桶（仍能防暴力破解，但攻击者可借错误口令**锁定指定账号**）。
**不构成越权**，也不影响其余安全不变量。自托管部署在宿主再加一跳 Nginx 后，两跳同在可信网段内，结论不变。

**修复**（已实施）：`web/nginx.conf` 的 `server` 块信任内网跳并还原真实来源：

```nginx
set_real_ip_from 10.0.0.0/8;
set_real_ip_from 172.16.0.0/12;
set_real_ip_from 192.168.0.0/16;
real_ip_header X-Forwarded-For;
real_ip_recursive on;
```

其后 `$remote_addr` 即客户端地址，注入上游的末位条目随之正确；`real_ip_recursive` 由右向左跳过可信地址，
客户端伪造的前导条目被丢弃。官方 `nginx:1.27-alpine` 已编译 `http_realip_module`，无需改基础层。
`tests/deploy/test_web_container_files.py` 增加三条断言锁定该配置（被移除即质量门失败）。
若日后引入可信范围之外的代理跳，需把该跳补进 `set_real_ip_from`。

### D-12 `hub-server` 未声明 `httpx` 运行时依赖，生产容器启动即崩（首次 Linux 部署中发现）

**位置**：`packages/hub-server/src/hub_server/services/service_manager.py:7`（`import httpx`）
对照 `packages/hub-server/pyproject.toml` 的 `dependencies`

**问题**：`httpx` 只声明在**根** `pyproject.toml` 的 `dev` 可选依赖里，而生产镜像仅安装各
workspace 包（`pip install ./packages/hub-contracts ./packages/hub-sdk ./packages/hub-runner ./packages/hub-server`），
不装 `dev` 额外项。`service_manager.py` 是 `routers/services.py` 的传递导入，因此
`uvicorn` 加载 `hub_server.main:app` 时直接抛 `ModuleNotFoundError: No module named 'httpx'`。

**后果**：容器内 `hub-api` 反复 exit 1，端口 8000 从未监听，镜像 `HEALTHCHECK` 恒为 `unhealthy`，
`depends_on: condition: service_healthy` 使得 Web 容器与 edge 容器**始终不创建**——整套栈无法启动。
**本机质量门无法发现**：开发 venv 的 `dev` 额外项恰好提供 `httpx`（测试客户端也要用），
`mypy`/`pytest` 全部通过。

**修复**（已实施）：向 `hub-server` 显式声明 `httpx>=0.27,<1`；同时把代码中**直接导入**的
`pydantic` 与 `starlette` 从「依赖 fastapi 隐式带入」改为显式声明，避免同类问题复发。

**排查方法**（可复用）：用 `ast` 解析每个包的 `src/**/*.py` 顶层导入，过滤标准库与本地包，
与 `pyproject.toml` 的 `dependencies` 求差集。本次扫描结果：`hub-server` 有 3 项未声明
（`httpx` 致命，`pydantic`/`starlette` 为隐式依赖），其余四个包干净。

### D-13 `.gitattributes` 的 LF 约束不完整，容器入口脚本被 CRLF 污染（首次 Linux 部署中发现）

**位置**：`.gitattributes`（原内容仅一行 `deploy/release/*.sh text eol=lf`）

**问题**：该规则只覆盖 `deploy/release/*.sh`，`docker-entrypoint.sh` 与 `tools/hubctl` 落入
`core.autocrlf` 的管辖。本机是 Windows 且 **`D:/soft/Git/etc/gitconfig` 里 `core.autocrlf=true`（system 级）**，
于是 `git archive` 输出 tar 时把这两个文件写成 CRLF（提交内的 blob 本身仍是 LF，`git ls-files --eol`
显示 152 个文件为 `i/lf` / `w/crlf`）。

**后果**：`docker-entrypoint.sh` 的 shebang 变成 `#!/bin/sh\r`，内核按 `/bin/sh\r` 查找解释器失败，
`tini` 报 `exec /usr/local/bin/service-hub-entrypoint failed: No such file or directory`，
容器 `Restarting (127)` 无限重启——而镜像内文件**存在且权限正确**，极易误判为 COPY 漏了文件。
`tools/hubctl` 在任意 Linux 主机上同样会以 `$'\r': command not found` 失败。

**修复**（已实施）：把规则放宽到所有会在 Linux 上执行的文件：

```gitattributes
*.sh          text eol=lf
tools/hubctl  text eol=lf
Dockerfile    text eol=lf
```

属性优先于 `core.autocrlf`，因此 `git archive` 从此无论本机配置如何都输出 LF。
`tests/deploy/test_release_scripts.py` 的断言同步改为按**形状**校验（原先断言一个过窄的字面串，
规则变强反而让它失败）。

**排查方法**（可复用）：`git ls-files --eol` 找 `w/crlf`；`git config --list --show-origin | grep crlf`
定位自动转换的来源（本机为 **system 级** `gitconfig`，`local`/`global` 均为空，容易漏看）。

### D-14 `supervisord.conf` 缺少 `[supervisorctl]` 段，运维无法查询进程状态（首次 Linux 部署中发现）

**位置**：`deploy/service_hub/supervisord.conf`

**问题**：配置里有 `[unix_http_server]`（socket 路径与权限）与 `[rpcinterface:supervisor]`，
但没有 `[supervisorctl]`，于是 `supervisorctl -c /etc/service-hub/supervisord.conf status`
直接报 `Error: .ini file does not include supervisorctl section` 并退出。

**后果**：不致命（`supervisord` 本身照常管理 6 个进程），但**运维与验收无法用命令确认进程状态**——
`docs/guides/服务器部署实施清单.md` 的健康门要求「6 个 supervisord 进程全 RUNNING」，
`tests/integration/test_web_console_lifecycle.py` 也直接调用 `supervisorctl`。二者都会因此失效，
只能改走 Unix socket 自行解析（`test_single_container_lifecycle.py` 即如此，所以单容器集成测试掩盖了该缺口）。

**修复**（已实施）：补上

```ini
[supervisorctl]
serverurl=unix:///run/service-hub/supervisor.sock
```

## 二、可优化点（非缺陷，按收益排序）

### O-1 Web 边界缺少安全响应头

**位置**：`web/nginx.conf:9-51`

**现状**：配置整体很干净——`/internal/v1/` 已显式 404 阻断（第 33-35 行）、大文件关闭缓冲（第 44-45 行）、超时已放宽到 3700s。

**缺口**：没有任何安全响应头（`X-Content-Type-Options`、`Referrer-Policy`、`X-Frame-Options`/`Content-Security-Policy`）。同时 `client_max_body_size 10g`（第 15 行）与后端 `uploads.max_size_bytes` 是两个独立上限，缺少注释说明两者关系，调参时容易只改一边。

**建议**：加最小集合的安全头（`nosniff` + `SAMEORIGIN` + 一个适配 SPA 的 CSP），并补注释说明两个体积上限的层级关系。

### O-2 同步 DB 会话与 `async def` 路由混用

**位置**：`dependencies.py:23-30`、`routers/files.py:67`（`async def upload_file`）

**现状**：`get_session` 提供同步 `Session`，但上传路由是 `async def`，其内的同步 DB 调用会**阻塞事件循环**。当前低并发下可接受。

**建议**：两条路选一——把纯 DB 端点改回 `def`（FastAPI 自动丢线程池，零改动成本），或整体迁移 async 驱动。不要长期停留在混用状态。

### O-3 上传「先落盘后写库」崩溃窗口会残留孤儿目录

**位置**：`services/files.py:59-74`、`storage.py:73-89`

**现状**：`store_installed_upload` 的失败补偿做得很扎实（失败时回滚并 `remove_upload`）。但它是「先 `os.replace` 安装、再 commit 元数据」——若进程在两步之间被 kill，磁盘上会留下**没有对应 FileRecord 的 `uploads/<key>/` 目录**，永远不会被清理。

**建议**：`cleaner` 服务已存在（`supervisord.conf:54-65`），增加一条孤儿扫描：对 `uploads/` 下每个目录，若在 `file_records` 中无匹配且创建时间超过阈值，则删除。同理可覆盖 `.tmp-*` 残留。

### O-4 上传体积检查为「先写后判」

**位置**：`storage.py:55-71`

**现状**：`StreamingUpload.write` 在每次写入前检查 `self._size_bytes + len(chunk) > self._max_size_bytes`，超限即 `abort()`。逻辑正确，但**超大文件会先占用磁盘直到触限**（最坏写入 `max_size_bytes` 字节才失败）。

**建议**：结合 D-1 的修复——在写入前先按 `Content-Length` 与实际剩余配额算出动态上限，做到尽早在字节流开头拒绝。

### O-5 supervisord 缺少 `startretries` / `startsecs` 显式配置

**位置**：`deploy/service_hub/supervisord.conf`（各 program 段）

**现状**：各进程均设了 `autorestart=true` + `stopasgroup/killasgroup`，但未显式声明 `startretries`（默认 3）与 `startsecs`（默认 1）。依赖默认值时，若某进程因配置错误反复崩溃，supervisord 会在 3 次后进入 `FATAL` 而不再重启；`startsecs=1` 对启动较慢的 `service-manager` 也可能偏短。

**建议**：显式写出这两个值并在注释中说明取值理由，让重启行为可预期、可审计。

### O-6 `_bootstrap_admin` 每次启动都新建引擎与会话

**位置**：`main.py:123-147`

**现状**：`_bootstrap_admin` 内部**再次调用** `create_engine_and_session_factory`（第 131 行），与 `lifespan` 中已创建的 engine（第 68 行）重复。虽然 bootstrap 完成后即 `dispose()`，但在检查 `UserRecord.count() > 0` 之外，每次启动都会为一个通常无操作的检查重复建连。

**建议**：复用 `lifespan` 已建立的 `session_factory`，避免重复建连；同时把「首次初始化」逻辑与「常规启动」在代码结构上分开。

### O-7 `runner-token` 通过环境变量传递

**位置**：`docker-entrypoint.sh:9-10`

**现状**：`HUB_RUNNER_TOKEN` 通过 `export` 注入，随后 supervisord 启动的每个子进程都能在自身环境中读到，且可能经 `/proc/<pid>/environ` 被同容器内其他降权进程读取。

**说明**：容器内已经是隔离环境，风险有限；`hmac.compare_digest` 常量时间比较（`internal_runner.py`）与 token 文件 0600 权限都做得正确。

**建议**：若追求更严格边界，可为每个 runner 单独下发 token、或改为启动时从受保护文件按需读取，避免长期驻留环境变量。
