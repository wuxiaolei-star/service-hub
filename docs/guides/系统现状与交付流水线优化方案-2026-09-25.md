## 0. 一页速览

**「镜像打包慢」的定性结论：主因不是网络，是插件打包阶段的 zstd 压缩等级。**

`hub_publisher/archive.py` 用 `ZstdCompressor(level=19, threads=0)` 压缩 `docker save`
产出的 ~1 GB 镜像 tar。

**全尺寸实测（2026-09-25 01:05，部署机 2 核 3.5 G，1,027,345,408 字节真实 `nc_to_shp` 镜像 tar）**：

| 压缩等级 | 耗时 | 产物体积 | 压缩比 |
|---|---|---|---|
| 19（原默认） | **502.6 s（8.4 min）** | 238.5 MB | 0.232 |
| **10（现默认）** | **74.4 s（1.2 min）** | 269.3 MB | 0.262 |
| 3 | **24.0 s** | 304.8 MB | 0.297 |

即：**每次插件打包省 428 秒（7.1 分钟），代价是体积 +30.8 MB（+12.9%）**。
这是**每次改插件都要付的固定成本**（插件镜像本身有 docker 层缓存，重建只要 4 秒）。

> 先前的 300 MB 切片推算（L3 5.4s / L10 18.5s / L19 134.0s）与全尺寸实测结论一致，
> 线性外推偏差在 10% 以内，已被上表取代。
>
> 该优化**已落地**（commit `9d16d7d`）：`DEFAULT_ZSTD_LEVEL = 10`，可用
> `HUB_PLUGIN_ZSTD_LEVEL`（1~22）覆盖，不可用取值一律静默回落默认值。

三档改进：

- **P0（半天内，纯收益）**：zstd 等级 → 10；BuildKit 缓存挂载；产物按内容哈希复用；质量门搬到 Linux 一次跑完
- **P1（1~2 天）**：建真正远端仓库 + 服务端 `post-receive` 钩子流水线（无需外部 CI SaaS），或 self-hosted runner
- **P2（中长期）**：镜像仓库/registry、conda-pack 运行时瘦身、制品签名、蓝绿发布

## 二、为什么慢：全流程耗时分解

### 2.1 现状流水线（手工、串行）

```
① 本地改码 → ② 本地质量门（分片 pytest ~15min + ruff/mypy + 前端）
   → ③ redeploy.py upload（git archive 打包 + 上传 + 服务端解包 ~1~2 min）
   → ④ build.sh 构建主镜像（后端 + 前端）
   → ⑤ package_build.py 构建插件镜像 + zstd 打包
   → ⑥ redeploy.py up（compose 重建、Alembic 自动迁移）
   → ⑦ push_install.py 上传安装插件（227 MB）→ 等待 READY → enable
   → ⑧ walkthrough 走查验收
```

### 2.2 各环节实测耗时

| 环节 | 冷（无缓存/默认源） | 温（有缓存/镜像源） | 备注 |
|---|---|---|---|
| 源码打包 + 上传 + 解包 | ~2 min | ~2 min | tar 体积小 |
| 主镜像构建 | **26 min**（默认源，未完成）→ **9 min**（镜像源） | **4.5 min** | 实测 00:12 → 00:16:52 |
| 插件镜像构建 | **~25 min**（pip 13 kB/s + apt 慢） | **~1~2 min** | 本次 docker build 出镜像仅 4 s |
| **插件 zstd 打包** | **8.4 min**（L19） | **1.2 min**（L10，已生效） | ⚠️ 与缓存无关；换默认等级后每次固定付 1.2 min |
| 插件安装 + 启用 | ~30 s | ~30 s | 269 MB（L10 产物）上传 + 校验 + docker load |
| 走查验收 | ~3 min | ~3 min | |

**结论**：改一次插件原本 ≈ **50 分钟**，其中 **8.4 分钟是 zstd L19 压缩**，
而插件镜像本身的 docker 构建已经只要几秒——**瓶颈完全在打包算法参数上**。
P0-1 落地后该环节降到 **1.2 分钟**，全流程约 **43 分钟**（温缓存场景可到 ~10 分钟）。

### 2.3 次级瓶颈

1. **远端源极慢**：该机 pypi 22 kB/s、npmjs 298 kB/s、deb.debian.org ~350 s/包。
   已在 `build.sh` 固定传阿里云 + npmmirror（冷构建 26 min → 9 min），
   但**插件 Dockerfile 内的 apt 没有镜像参数**（`Dockerfile` 只有 `APT_MIRROR` 给主镜像用）。
2. **无 BuildKit 缓存挂载**：pip / apt / npm 缓存不跨构建复用，冷路径每次重下。
3. **无产物复用**：即使插件源码与基础镜像都没变，也会重新 `docker save` + 压缩一次。
4. **质量门在本机跑**：Windows 沙箱限制导致必须人工分片，~15 min 且易被杀。
5. **全链路串行**：④ 与 ⑤ 完全可以并行（2 核机器上收益有限，但至少不用人盯着）。

## 三、优化方案

### 3.1 P0：立即可做（预计 0.5 人日）

| # | 改动 | 位置 | 收益 | 风险 |
|---|---|---|---|---|
| ~~P0-1~~ ✅ | zstd 压缩等级 19 → **10**，并支持 `HUB_PLUGIN_ZSTD_LEVEL` 覆盖 | `packages/hub-publisher/src/hub_publisher/archive.py` | **实测每次打包 502.6s → 74.4s（省 7.1 min）**，体积 +12.9% | 极低（仅压缩参数） |
| P0-2 | `docker save` 直连 zstd（`docker save | zstd` 管道），避免落中间 tar | 同上（builder.py） | 省 1 GB 写盘 + 读盘，约 1~2 min | 低 |
| P0-3 | 产物按**内容哈希**复用：`sha256(源码摘要 + 基础镜像 digest)` 命中则跳过打包 | `package_build.py` | 源码未变时打包耗时 → 0 | 低 |
| P0-4 | 质量门迁到 Linux（服务器容器或 itest-venv）一条命令跑完，Windows 只做前端门 | CI 脚本 | 省 ~15 min 人工分片 | 低 |
| P0-5 | 插件 Dockerfile 支持 `APT_MIRROR` / `PIP_INDEX_URL` build-arg（与主镜像对齐） | `packages/nc-to-shp-plugin/docker/Dockerfile` | 冷构建从 ~25 min 降到 ~10 min | 低 |
| P0-6 | Dockerfile 加 BuildKit `RUN --mount=type=cache` 缓存 pip/apt/npm | 三个 Dockerfile | 冷/温构建都更快 | 低（需 `DOCKER_BUILDKIT=1`） |

> P0-1 是**单点最大收益**，已于 commit `9d16d7d` 落地并经全尺寸实测验证（502.6s → 74.4s）。
> 选 10 不选 3 的理由：全尺寸下 L3 只再省 50 s，却多出 35.5 MB（比 L10 大 13.2%）；
> 在「上传带宽也慢」的场景下，L10 是更好的平衡点。

### 3.2 P1：流水线与 CI/CD（预计 1~2 人日）

#### 前置条件（**必须先解决，否则任何 CI 都无从谈起**）

```
$ git remote -v
origin  C:\Users\Administrator\Documents\Codex\...\python-service-hub (fetch)
```

**当前 `origin` 是本机的一个本地目录**，没有真正的远端仓库 —— 服务端 CI 无处拉取代码。
第一步必须建一个可达的远端（Gitee / GitHub / CNB / 自建 Gitea 均可），把 `main` 推上去。

#### 方案 A（推荐）：服务端 bare repo + `post-receive` 钩子，**零外部依赖**

在部署机上放一个 bare repo，本地 `git push deploy main` 即触发全流程。
不依赖任何 SaaS、不需要公网镜像仓库、**在哪里构建就在哪里部署**（避开该机跨境拉镜像的龟速）。

```
本地 push ──▶ 服务器 bare repo (post-receive)
                ├─ 1. checkout 到 /opt/service-hub/releases/<commit>
                ├─ 2. 质量门（容器内 pytest + ruff + mypy；前端 tsc/eslint/build）
                ├─ 3. 备份 data/（热备 + 冷备，校验 tar -tzf）
                ├─ 4. 构建镜像（复用 build.sh，带镜像源）
                ├─ 5. compose up -d（Alembic 自动迁移）
                ├─ 6. 健康检查（3 端点 200 + 容器 healthy）
                ├─ 7. 失败 → 自动回滚（恢复 data + 重建旧镜像）
                └─ 8. 成功 → 走查脚本 + 写回 deploy 日志
```

落地文件（本轮已产出，见 §5）：
- `deploy/ci/deploy-pipeline.sh`：上述 8 步的可执行实现（含自动回滚）
- `deploy/ci/post-receive`：钩子入口（调用 pipeline，输出 tee 到日志）

安装方式：

```bash
# 服务器上（一次性）
git init --bare /opt/service-hub/repo.git
ln -s /opt/service-hub/repo.git/hooks/post-receive deploy/ci/post-receive   # 或用模板
# 本地
git remote add deploy ssh://root@${HUB_HOST}/opt/service-hub/repo.git
git push deploy main     # 之后每次发布只需这一条
```

#### 方案 B：GitHub Actions / Gitee Go / CNB + self-hosted runner

更规范（有 PR 门禁、状态徽章、并发控制），但**必须先有远端仓库**，且 GitHub 托管 runner
拉/推 1 GB 插件镜像在该机网络下不现实 → runner 必须 self-hosted 部署在这台机器上。
流水线阶段与方案 A 相同，只是触发器换成 `on: push: branches: [main]`。

**建议**：先落地方案 A（当天可用），再视需要迁移到方案 B。

#### 流水线必备的非功能项

- **自动回滚**：健康检查失败 → 停容器 → 用冷备恢复 `data/` → 重建旧 commit 镜像 → 再健康检查
- **备份轮换**：保留最近 3 份（`retention.backup_keep: 3`），自动清理更老的
- **并发锁**：`flock` 防止两条流水线同时跑（本机 2 核扛不住并行构建）
- **通知**：失败时输出明确的失败阶段 + 日志路径（可接企业微信/邮件 webhook）
- **审计**：每次发布写一行到 `deploy/ci/releases.log`（commit、时间、耗时、结果）

## 六、约束与风险（不要回退）

1. **唯一对外端口 8443**；`cs-nginx` 占用 80/443，不要动。
2. **Alembic 无降级保护**：启动即 upgrade head，回滚 = 代码镜像重建 + data 整体回滚。
3. **2 核 3.4 G 内存敏感**：不要并行跑多个 docker build；zstd 高等级 + 大 window 可能触发 OOM。
4. 仅 `docker-runner` 与 `service-mgr` 在 docker socket 组；`hub-api` / `conda-runner` 永不接触。
5. compose 端口只绑 `127.0.0.1`（唯一例外 edge `8443`）。
6. `hub-api` 日志走 supervisord → `log_prefix` → stdout，**Python 侧块缓冲**，
   排查 500 时 `docker logs` 可能看不到 traceback；**更快的方法是在容器内直接复现**
   （如 `docker exec ... python -c` 调同一段服务代码），本轮定位版本冲突即用此法。

## 附录：主要实测命令

```bash
# 线上健康
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:18000/api/v1/system/health

# 任务耗时趋势（新端点）
TOKEN=$(curl -s -X POST http://127.0.0.1:18000/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"<见 .deploy-tools>"}' \
  | sed -n 's/.*"token":"\([^"]*\)".*/\1/p')
curl -s -H "Authorization: Bearer $TOKEN" 'http://127.0.0.1:18000/api/v1/jobs/stats?days=14'

# 插件构建（服务端，带镜像源）
HUB_PLUGIN_PIP_INDEX_URL=https://mirrors.aliyun.com/pypi/simple/ \
  python packages/nc-to-shp-plugin/scripts/package_build.py \
  --runtime docker --arch amd64 --output /opt/service-hub/plugin-out

# 需要极致压缩率时临时提级（不建议常设，会多花 7 分钟）
HUB_PLUGIN_ZSTD_LEVEL=19 python .../package_build.py ...

# zstd 等级基准（全尺寸，真实 1.03 GB 插件镜像 tar）
docker save nc_to_shp:1.0.1-linux-amd64 -o /tmp/full.tar
python - <<'PY'
import os, pathlib, time
from hub_publisher.archive import compress_zstd, zstd_level
src, out = pathlib.Path('/tmp/full.tar'), pathlib.Path('/tmp/out.zst')
print('default level:', zstd_level())
for level in (19, 10, 3):
    os.environ['HUB_PLUGIN_ZSTD_LEVEL'] = str(level)
    t0 = time.time(); compress_zstd(src, out)
    print(f"level={level} time={time.time()-t0:.1f}s size={out.stat().st_size/1e6:.1f}MB")
PY
```
