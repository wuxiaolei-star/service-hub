# 后端架构优化清单（2026-09 勘察）

- 勘察范围：`packages/hub-server`（含 `deploy/` 侧车进程），只读核查，关键论断已抽查验证
- 基线：930 后端测试全绿、ruff/mypy 干净——以下为**结构性/性能/可维护性优化点**，非缺陷修复
- 总体印象：分层意图清晰（routers → services → repositories/storage），错误信封统一（`HubError` 全局 handler），上传走流式分块+配额双检。优化空间集中在：SQLite 写锁窗口、事件循环阻塞、N+1、配置散落

---

## 立即做（小成本高收益）

### 1. list_jobs N+1 懒加载（高频端点）
- 证据：`services/jobs.py:100-128` 无 `joinedload`；`routers/jobs.py:322-337` `_job_response` 逐条访问 `job.plugin_build.plugin_version.plugin` 三层懒加载（对比同文件 CSV 导出路径 149-160 行反而正确用了 joinedload）
- 影响：每页 100 条触发约 300 次额外 SELECT，列表页主要延迟来源
- 改法：`list_jobs` 加 `joinedload(Job.plugin_build).joinedload(PluginBuild.plugin_version).joinedload(PluginVersion.plugin)`，与导出路径对齐。**工作量：小**

### 2. 每请求认证解析两次、最多 3 个 Session
- 证据：router 级 `Depends(require_role(...))` + 端点内 `Depends(get_actor)` 各自调 `resolve_actor`（`dependencies_auth.py:53,101,110`），各自 `get_session` 拿独立 Session
- 影响：认证查询翻倍，SQLite 连接池与日志噪音增加
- 改法：`require_role` 把 Actor 存入 `request.state`，`get_actor` 优先读取。**工作量：小**

### 3. JobService.logs 整文件读入内存
- 证据：`services/jobs.py:136-147` `read_text().splitlines()` 全量读 `events.jsonl` 后切片，长任务日志无上限
- 影响：GB 级日志单请求可占数百 MB 内存（2核3.4G 机器敏感）
- 改法：复用 `logs_stream.py:51-102` 已有的字节偏移 tail 方案。**工作量：小**

### 4. session_ttl_hours 配置项被硬编码架空（配置假开关）
- 证据：`settings.py:45` 提供 `session_ttl_hours`，但 `models.py:31` `_SESSION_TTL = timedelta(hours=24)` 硬编码，配置从未接入
- 影响：运维改配置不生效，误导排障
- 改法：会话创建路径显式按 settings 计算 `expires_at`。**工作量：小**

### 5. 缺少量复合索引（调度热路径）
- 证据：领队查询按 `runtime_type + status='PENDING' order by created_at`（`repositories.py:189-194`）但 `models.py:189` 仅 status 单列索引；`schedules.next_run_at`（`models.py:407`）每 30s 全扫；`job_callbacks.next_attempt_at`（`models.py:382-384`）无索引
- 改法：加 `(runtime_type, status, created_at)` 复合索引 + `next_run_at`、`next_attempt_at` 单列索引，走 Alembic 迁移。**工作量：小**

### 6. deliver_due 全部投递完才一次性 commit
- 证据：`services/webhooks.py:107-121` 循环内逐个 HTTP 投递，`commit()` 只在循环后一次
- 影响：中途崩溃丢失已投递回调的 attempts 与审计，可能超次数重发
- 改法：每个回调投递后立即 commit（与 `schedules.py` 逐条 commit 风格一致）。**工作量：小**

## 短期规划

### 7. async 端点内同步磁盘写，阻塞事件循环
- 证据：`routers/files.py:123` `upload_file` 为 async，`_stream_multipart_file` 在 `async for` 内调 `upload.write()` 同步写盘+SHA256（`storage.py:55-71` 纯阻塞）；`upload_chunk`（568-596）同样
- 影响：大文件上传期间事件循环被反复阻塞，2 核机上全站并发请求排队
- 改法：写盘/摘要移入 `run_in_threadpool`，或端点改 `def` 走 threadpool。**工作量：中**

### 8. SSE 日志流占住 threadpool 线程 + DB 会话最长 300 秒
- 证据：`routers/logs_stream.py:30-42,63-102` 同步生成器 `time.sleep(1)` 轮询、session 全程保活
- 影响：几人同时看日志即可耗尽 threadpool（默认 40 槽），SQLite 连接被长期占用
- 改法：改 async 生成器 + `asyncio.sleep`，会话短借短还。**工作量：中**

### 9. JobService.create 持有 SQLite 写锁期间复制输入文件
- 证据：`services/jobs.py:63-67` flush（已取写锁）→ `JobWorkspaceService.prepare` 复制 NC 文件 → commit；该库被 5 个进程共写（WAL + 30s busy_timeout 正为争用设计）
- 影响：大文件复制越慢，全局写排队越久
- 改法：两阶段——事务外 stage 输入文件到临时区 → 事务内原子改名+commit，缩小锁窗口。**工作量：中**

### 10. 配置读取散落：环境变量绕过 HubSettings、URL 硬编码
- 证据：`routers/services.py:45` 请求处理器内读 `os.environ["HUB_DOCKER_HOST_DATA_ROOT"]`；`service_manager.py:12,122` manager URL 硬编码；`main.py:102` `HUB_CONFIG_PATH` 缺失抛裸 KeyError
- 改法：`HubSettings` 增加 `service_manager.base_url` 与 `docker.host_data_root` 字段；缺失给明确报错。**工作量：小**

## 中期演进

### 11. list_services 对 service-manager 串行 N+1 HTTP 调用
- 证据：`routers/services.py:86-88` 逐个调 `_safe_status`；`service_manager.py:15,36-37` 每次读超时 5s、每次新建 `httpx.Client`
- 影响：10 个服务 + manager 卡死时最坏 50 秒响应
- 改法：manager 加 `/statuses` 批量端点；httpx.Client 按应用生命周期复用。**工作量：中**

### 12. 调度进程 30s 串行轮询 8 任务，阻塞式 webhook 拖慢全部自动化
- 证据：`deploy/service_hub/scheduler_service.py:106-117` 串行执行；`services/webhooks.py:212-220` 同步 urllib、单次 10s、3 次重试，与 trigger_schedules/advance_pipelines 同循环；`hub_events` outbox 表已建但未用于事件驱动（`models.py:516-529`）
- 影响：一个慢回调目标可让整轮调度延迟 30s+
- 改法：短期——webhook 投递拆独立线程/每回调独立 commit；中期——Job 终态写 outbox，scheduler 消费 due 事件，轮询间隔任务级配置。**工作量：中～大**

### 13. 分层不一致：部分 router 直接操作 DB 绕过 service 层
- 证据：`routers/services.py` 整文件无 service 层（87, 108, 254 行直接 query）；`routers/jobs.py:245-256` `get_job` 绕过 `JobService._get_job` 重复实现查询+404；`routers/schedules.py:36-80` 创建校验全在 router
- 影响：同一领域逻辑两处维护，事务边界口径不一
- 改法：抽 `ScheduleService`、`ServiceDefService`；统一 `select()` 2.0 风格。**工作量：中**

### 14. 测试 fixture 粒度单一：每测试全量建应用+跑迁移
- 证据：`tests/server/conftest.py:25-38` 唯一 `session` fixture 每测试 `create_app`（含 Alembic upgrade + bootstrap admin）
- 影响：930 测试全绿但套件偏慢，service 层单测被迫背 ASGI 启动成本
- 改法：增加轻量 `service_session` fixture（只建 engine），可叠加「每测试事务回滚」模式。**工作量：中**
