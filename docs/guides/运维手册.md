## 1. 日常操作

### 1.1 常规部署：自动，无操作

`git push origin main` → GitHub Actions 质量门（密钥扫描 / 后端 / 前端 / 镜像
构建）→ 服务器 timer 每 3 分钟比对远端 tip → **绿灯才部署**，黄/红扣住。
常规部署（服务器侧质量门默认关闭）实测 157–358 s；流水线各阶段与耗时见
CI-CD 文档 §1/§5。部署收尾自动执行业务走查（上传真实 NC 样本跑一个作业等
SUCCESS），走查凭据缺失时跳过（不算失败）。

**平时不需要任何动作**；下面只列需要人介入的场景。

### 1.2 立即部署（不等轮询）

```bash
# 只看有无待部署
bash /opt/service-hub/deploy/ci/pull-deploy.sh --check

# 立即拉取部署
bash /opt/service-hub/deploy/ci/pull-deploy.sh

# 需要服务器本地补跑容器内质量门时（默认信任 Actions 绿灯）
HUB_PIPELINE_GATE=1 bash /opt/service-hub/deploy/ci/pull-deploy.sh --force
```

### 1.3 部署"扣住"时的诊断

绿灯才部署是设计行为（`HUB_CI_GATE=wait` 默认；`strict` 时 API 失败也扣住）。
扣住时按顺序看三处：

1. **journalctl**：`journalctl -u service-hub-deploy.service --since -30min`——
   看本轮是"yellow/in progress 等待"还是"check-runs 查询失败"；
2. **releases.log**：`tail -50 /opt/service-hub/deploy/ci/releases.log`——每次
   上线的 commit / 耗时 / 结果（含 `SUCCESS-LIGHTWEIGHT`）都在这里；
3. **CI gate 记录**：到 GitHub Actions 页看对应 commit 的 check-runs 是否有红；
   `pull-deploy.sh --check` 也会打印门禁状态。

`another deployment holds lock`（退出码 3）不是故障：上一次部署还在跑（flock），
等它结束即可（systemd 已把 2/3 视为正常退出）。

### 1.4 回滚

**代码回滚——切 tag（秒级，作业数据不动）**：流水线把上一版镜像保留为
`:rollback-target`，回滚只需重指移动 tag 并重建容器：

```bash
docker tag python-service-hub:rollback-target python-service-hub:1.0.0-linux-amd64
docker tag python-service-hub-web:rollback-target python-service-hub-web:1.0.0-linux-amd64
docker compose -p service-hub --project-directory /opt/service-hub/src \
  -f compose.yaml -f /opt/service-hub/compose.override.yaml up -d
```

compose 只认 `1.0.0-linux-amd64` 移动 tag——**不要**在 compose 里直接引用
commit tag。`data/plugins/` 下的插件归档与 DB 中的作业/构建记录都不受主镜像
回滚影响。

**代码回滚——revert 流程（来源治理，优先用这个纠正坏提交）**：

```bash
git revert <批次commit> && git push origin main   # 3 分钟内自动部署回滚
```

各批次与 commit 的对照见审查方案文档"执行日志"。注意两个拆散的混合提交：
B8 需 `git revert aad3529 c28e302`；B9 需 revert `05f182b` 并按执行日志说明
处理 `a8a228e` 中的 B9 相关文件。

**数据回滚边界**：

- 流水线失败时的自动回滚**只发生在切换之后**（`compose down` 以后）：恢复
  `data-cold-<stamp>.tar.gz` + 重指 tag。构建/门禁/热备阶段失败时旧版本根本
  没停，数据未动，无需也不应回滚；
- 冷备恢复会**整体替换 `data/`**（DB + 文件 + 插件归档），恢复点之后新建的
  作业记录、上传文件会丢——执行前先评估，必要时手工抢救增量；
- `data/environments/` 不在备份里（盲区）：冷备恢复后 conda 环境目录可能与
  DB 记录不一致，孤儿扫描会在 30 分钟内给出报告（§4.4）；
- 手工恢复某份冷备：

```bash
tar -xzf /opt/service-hub/data-cold-<stamp>.tar.gz -C /opt/service-hub
docker compose -p service-hub --project-directory /opt/service-hub/src \
  -f compose.yaml -f /opt/service-hub/compose.override.yaml up -d
```

### 1.5 文档批轻量路径

改动仅落在 `docs/*`、`*.md`、`README*`、`LICENSE`、`.git*` 的提交走轻量路径：
只记 `releases.log`（`SUCCESS-LIGHTWEIGHT`，0 s），**不重建、不重启、零中断**。
若看到文档改动触发了全量部署，先查是否混入了非文档文件（`git diff --stat`）。

## 2. 插件运维

> 状态机：`INSTALLING → READY → ENABLED`；`ENABLED ⇄ READY`（disable/enable）；
> `READY/ENABLED → DEPRECATED`（**单向**）。只有 `ENABLED` 能承接新作业。
> 同一 `(版本, 平台, 运行时)` 的重装被唯一约束拒绝（409 `PLUGIN_BUILD_ALREADY_EXISTS`）。

### 2.1 安装 / 启用 / 禁用 / 废弃操作序列

以下 `<TOKEN>` 为具备 **publisher** 角色的会话或 API Key；`HUB=https://${HUB_HOST}:8443/api/v1`。

```bash
# ① 安装（上传 .pypkg）→ 202，返回 build_id；轮询到 READY
curl --fail-with-body -X POST -H "Authorization: Bearer <TOKEN>" \
  -F "file=@dist/my_tool-1.0.0-linux-amd64-docker.pypkg" "$HUB/plugins/install"
curl -H "Authorization: Bearer <TOKEN>" "$HUB/plugin-builds/<build_id>"

# ② 启用 → ENABLED，可承接作业
curl --fail-with-body -X POST -H "Authorization: Bearer <TOKEN>" \
  "$HUB/plugin-builds/<build_id>/enable"

# ③ 禁用 → 回 READY（有 PREPARING/RUNNING 作业时 409 PLUGIN_BUILD_IN_USE；PENDING 不拦截）
curl --fail-with-body -X POST -H "Authorization: Bearer <TOKEN>" \
  "$HUB/plugin-builds/<build_id>/disable"

# ④ 废弃（下线等待清理）→ DEPRECATED，单向，无复活端点
curl --fail-with-body -X POST -H "Authorization: Bearer <TOKEN>" \
  "$HUB/plugin-builds/<build_id>/deprecate"
```

**废弃的完整语义**：READY/ENABLED 才可废弃（否则 409
`PLUGIN_BUILD_NOT_DEPRECATABLE`）；废弃后新作业 404
`PLUGIN_BUILD_NOT_ENABLED`，在跑作业不受影响；存储与环境目录**原样保留**
（标记"待清理"，等待受守卫的删除能力 B4b 上线）。**要恢复该插件版本的服务，
只能以新版本号安装新包并启用新 Build**——同版本号槽位已不可复用。

全部动作写审计：`plugin.install` / `plugin_build.enable` / `plugin_build.disable` /
`plugin_build.deprecate`。

### 2.2 公钥登记与轮换（制品验签，B9）

**配置文件在哪**：Hub 运行配置是仓库内的 `config/hub.yaml`（构建时 `COPY` 进镜像，
容器内路径 `/app/config/hub.yaml`，`HUB_CONFIG_PATH` 指向它；可调字段样例见
`config/hub.yaml.example`）。服务器上另经 `/opt/service-hub/compose.override.yaml`
（server-local，不入库）把该配置以**单文件 bind mount** 覆盖——改配置有两条路径：

- **走仓库（推荐）**：改 `config/hub.yaml` → git 提交推送 → 自动部署重建镜像生效；
- **走服务器（快速）**：改 bind mount 的源文件（真实路径用
  `docker inspect service-hub-service-hub-1 | grep -A2 hub.yaml` 确认）→
  **必须 `docker compose restart`**——单文件 bind mount 改内容后 `up -d`
  不会重建容器（踩过的坑，见总结文档 §八 O-9）。

验签配置写在 `plugins.signature` 节：

```yaml
plugins:
  signature:
    public_keys:          # base64 公钥列表（`hub-plugin keygen` 产出 .pub 的第二行原样粘贴）
      - "<base64 公钥>"   # 多把并存：任一验过即通过
    require_signed: false # true = 未附有效签名的包 422 拒收（须至少登记 ≥1 把公钥）
```

操作要点：

- **未配置公钥（默认）= 现行为**，对上传零影响；可以先登记公钥（带签必验、
  不带签放行）观察一段时间，再切 `require_signed: true` 收紧；
- `require_signed: true` 而公钥列表为空的矛盾配置会在**启动期被拒绝**
  （fail-closed），服务起不来——调整时先把公钥补上；
- **轮换顺序：先加新钥 → 发布者用新钥签包并上传验证 → 再删旧钥**；
- 核对登记是否正确：看新安装审计 `plugin.install` detail 里的
  `signature_fingerprint` 是否等于 `.sig` 注释行的 16 hex 指纹；
- 篡改包、错误公钥、错误算法一律 422 `PLUGIN_PACKAGE_SIGNATURE_INVALID`；
  强制模式下未带签 422 `PLUGIN_PACKAGE_SIGNATURE_REQUIRED`。

### 2.3 资源限制调优（B7）

三层生效优先级：**manifest 显式声明（`execution.memory_mb`/`execution.cpus`，
可选）> 平台默认 `runner.resource_limits` > 不限制**。认领（claim）时逐次解析，
改默认值**无需迁移**存量 Build；整个节点置 `null` 即关闭平台默认。

```yaml
runner:
  resource_limits:      # 平台默认 cap；置 null 关闭
    memory_mb: 2048     # 单 Job 内存上限（MiB）
    cpus: 1.5           # 单 Job CPU 配额（核）
```

- **当前默认值的依据**：nc_to_shp 真实样本（48 MB / 25 时刻）作业峰值内存
  实测 **71.9 MiB**，2048 MB ≈ 28 倍余量——目的是防失控作业打爆共享机，
  不是贴峰值设限；
- **何时改**：出现"正常业务文件把作业顶到超限被杀"（docker 侧表现为退出码
  137、终态 FAILED 而非 TIMED_OUT）时，优先让插件在 manifest 里声明更大的
  `memory_mb`/`cpus`（只影响该插件）；确属多插件共性问题，再上调平台默认；
  内存紧张则反向下调；
- **运行时语义差异**（调参前必读）：docker 侧 `mem_limit` = `memswap_limit`
  （禁止 swap 超卖）+ `nano_cpus`（并发核数份额）；conda 侧 `RLIMIT_AS` 按
  **虚拟地址空间**计（GDAL/numpy 内存映射使其更保守、同值更容易被杀），
  `RLIMIT_CPU` 是**累计 CPU 秒预算**（= cpus × timeout），非核数份额；
- **实测作业内存峰值**（调默认值前先测量）：

```bash
# 作业运行期间在服务器执行（ancestor 过滤到插件镜像）；样本越大越接近真实峰值
docker stats --no-stream --format "{{.Name}} {{.MemUsage}} {{.CPUPerc}}" \
  --filter ancestor=<插件镜像ID>
# 插件镜像 ID 来自构建详情 API：GET /api/v1/plugin-builds/<build_key> 的 runtime_fingerprint
```

## 4. 告警接入

### 4.1 HUB_DEPLOY_WEBHOOK_URL（部署成败必达通知）

流水线在**成功与失败**两条路径上 POST 一条 JSON（5 s 超时，通知失败不影响
部署本身）。配置方法——在 systemd unit 加 Environment 行：

```bash
# 编辑 unit（服务器上实际生效的是 /etc/systemd/system/ 下的副本）
systemctl edit service-hub-deploy.service
# 加入：
#   [Service]
#   Environment=HUB_DEPLOY_WEBHOOK_URL=https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=<KEY>

systemctl daemon-reload
# oneshot unit 无需 restart；下一次 timer 触发即带新环境。验证：
systemctl show service-hub-deploy.service -p Environment
```

也可直接编辑 `/etc/systemd/system/service-hub-deploy.service` 的 `[Service]`
段追加 `Environment=` 行（与现有 `REMOTE_DIR=`/`DEPLOY_BRANCH=` 同位置），
然后同样 `daemon-reload`。

**消息体**：`{"text":"service-hub deploy SUCCESS commit=<sha>: …"}`。

### 4.2 企业微信 / 钉钉 bot 适配

- 消息体是**通用 `{"text": …}` 单字段 JSON**：Slack 兼容的中转/网关直接可接；
- **企业微信群机器人**原生 schema 是 `{"msgtype":"text","text":{"content":…}}`、
  **钉钉自定义机器人**是 `{"msgtype":"text","text":{"content":…}}`（钉钉另加
  签名/关键词校验）：二选一处理——(a) 在中间架一个 10 行的转换 relay 收
  `{"text":…}` 转成各家 schema（推荐，保留脚本零依赖）；(b) 确认所用 bot
  端点恰好兼容 `text` 字段后再直连；
- 验证：`curl -fsS -m 5 -X POST -H 'Content-Type: application/json' \
  -d '{"text":"service-hub webhook test"}' "$HUB_DEPLOY_WEBHOOK_URL"`；
- **这是 P0 告警（O-6）的最后一公里**：配置前，部署失败只存在于 journalctl
  里，无人知晓——配置与巡检同等优先级。

## 5. 事故预案

### 红线清单（任何时候都不允许，均有事故背书）

1. **禁 `docker image prune`（含 `-a`）**——hub 按 **digest** 引用插件镜像，
   悬空 ≠ 无用；prune 会打断全部插件作业（2026-09-25 事故）。空间回收只走
   插件版本管理（禁用/废弃构建 + 精确 `docker image rm`）。该红线已升级为
   门禁：`tests/deploy/test_prune_ban.py` 静态断言 `deploy/**/*.sh` 无禁词；
2. **禁手改 `/opt/service-hub/src` 任何文件**——部署检出漂移会让 `git checkout`
   拒切、timer 每 3 分钟失败一次；改动一律走 git 提交（timer 现有自动
   `git reset --hard` 自愈，红线仍然成立：手工修复会被直接丢弃）；
3. **8443 是唯一对外端口**；api/web 只绑 127.0.0.1，不得改绑 0.0.0.0；
4. **`cs-nginx` 勿动**——服务器上占用 80/443 的非本项目容器（另有
   `peaceful_cori`），归属未确认前禁止 stop/rm（O-14）；
5. compose 只认 `1.0.0-linux-amd64` 移动 tag，不得引用 commit tag。

### 处置卡①：插件作业秒败（毫秒级 FAILED，`RUNNER_FAILED`）——digest 引用镜像缺失

- **症状**：一批作业创建成功后在 ~5 ms 内失败，日志 `Runner failed`；
  `GET /plugin-builds/<build_key>` 正常（注册表记录还在）。
- **根因**：运行器按 `docker run sha256:<digest>` 引用插件镜像；镜像 tag 被重
  建/清理指向新 ID 后，DB 里记录的旧 digest 成悬空镜像，一旦被删除即全部秒败
  （2026-09-25 真实事故，由 `docker image prune -f` 引发）。
- **处置**（hub 自带安装期归档，恢复不依赖外网）：

```bash
# 1) 从该 Build 的安装期归档恢复镜像
docker load -i /opt/service-hub/data/plugins/<build_key>/image.tar.zst
# 2) 核对恢复出的镜像 ID 与构建详情 API 的 runtime_fingerprint 一致
curl -sk "https://${HUB_HOST}:8443/api/v1/plugin-builds/<build_key>" -H "Authorization: Bearer <TOKEN>"
# 3) 手工补跑一个验证作业 → SUCCESS 即恢复
```

- **验证后**：确认是 prune 类操作所为则按红线追查来源；归档缺失（conda 构建为
  `runtime/env.tar.zst`，同目录）时只能重新构建安装新版本号。

### 处置卡②：部署连续失败 / timer 反复报错——服务器检出脏

- **症状**：`journalctl -u service-hub-deploy.service` 连续报 checkout 失败或
  timer 每 3 分钟失败一次；`git -C /opt/service-hub/src status` 显示 tracked
  文件被修改（2026-09-25 17:26 实测：手工改动导致 `git checkout` 拒切）。
- **根因**：有人绕过 git 手改了部署检出内容；或检出被中途脚本改脏。
- **处置**：

```bash
cd /opt/service-hub/src
git status                                   # 1) 先看漂移内容，确认无未入库的有价值改动
git fetch origin && git reset --hard origin/main   # 2) 丢弃本地漂移，对齐远端
bash /opt/service-hub/deploy/ci/pull-deploy.sh     # 3) 手动触发一次部署验证
```

- 现行 `pull-deploy.sh` 已内置部署前漂移检测与自动 `git reset --hard`（自愈），
  本卡用于自愈之外的场景（如 untracked 冲突、检出损坏后重新 clone）。
- **验证后**：按红线第 2 条追查改动来源，把"必须改文件"的诉求转成 git 提交。

## 6. 故障速查表

| 症状 | 根因 | 处置 |
|---|---|---|
| 作业全部 ~5 ms 秒败 `RUNNER_FAILED` | digest 引用的插件镜像被删（prune 类操作 / tag 重建） | 处置卡①（`docker load` 恢复） |
| 部署后新代码没上线 | 质量门黄/红扣住（`HUB_CI_GATE=wait`），或 `already up to date` | §1.3 三处诊断；确认 Actions check-runs |
| timer 每 3 分钟失败一次 | 部署检出被手改，checkout 拒切 | 处置卡②（`git reset --hard`） |
| `another deployment holds lock` | 上一次部署仍在跑（flock），正常并发 | 等待结束即可（退出码 3 已视为成功） |
| 部署拒绝启动 | 磁盘低于 `HUB_MIN_FREE_MB`（2048 MB） | 清理冷备/旧 commit tag 之外的冗余；**不许 prune 插件镜像**（红线 1） |
| 部署失败且未自动回滚 | 冷备份缺失（自动回滚的前置） | 检查 `/opt/service-hub/data-cold-*.tar.gz`；按 §1.4 手工恢复 |
| 上传插件包 422 `PLUGIN_PACKAGE_SIGNATURE_INVALID` | 包被篡改 / 签名与登记公钥不匹配 / 算法不符 | 发布者重签（`hub-plugin sign`）或核对公钥登记（§2.2） |
| 上传插件包 422 `PLUGIN_PACKAGE_SIGNATURE_REQUIRED` | 强制验签已开启但上传未附签 | multipart 追加 `signature` 字段 |
| 服务改 `hub.yaml` 后行为没变 | 单文件 bind mount 改内容后 `up -d` 不重建 | `docker compose restart`（§2.2 踩坑） |
| 创建作业 409 `PLUGIN_CONCURRENCY_LIMIT` | 该 Build 并发闸已满（含调度触发） | 等待现有作业完成；必要时插件作者出更高 `execution.concurrency` 的新版本 |
| 作业 FAILED `PLUGIN_OUTPUT_MISSING` | 插件未产出声明的 required 文件输出 | 插件缺陷，反馈作者（使用手册 §5）；非运维问题 |
| 作业 FAILED 退出码 137 | docker 内存超限被杀（OOM） | §2.3：插件 manifest 调大 `memory_mb` 或平台默认上调；conda 侧注意 RLIMIT_AS 口径更保守 |
| 创建作业 404 `PLUGIN_BUILD_NOT_ENABLED` | 目标 Build 不存在、未启用或已 DEPRECATED | §2.1 启用流程；废弃态不可复活，装新版本 |
| 同版本重装 409 `PLUGIN_BUILD_ALREADY_EXISTS` | (版本, 平台, 运行时) 唯一约束 | 换版本号；废弃态槽位同样不可复用 |
| 审计出现 `environments_orphans_detected` | `data/environments/` 有无 Build 引用的目录（备份盲区残留/异常残留） | 只报告不删除；登记待 B4b 守卫删除；确认为垃圾且磁盘吃紧时可手工移出至暂存目录观察 |
| 登录 429 | 登录限流（阈值 5 次起） | 按 `Retry-After` 等待；用户侧问题，运维无需处理 |
| Prometheus `hub_jobs_total` 序列回落 | 30 天作业保留期删除旧行（非 counter 递增语义） | 属已知设计：短窗口 rate()/increase() 不受影响（§3） |
| 服务器 80/443 被占用 | `cs-nginx`（非本项目容器） | **勿动**（红线 4）；本项目对外只走 8443 |
