## 0. 一页速览

### 0.1 部署拓扑

```text
浏览器 ──► 127.0.0.1:8080 ──► service-hub-web 容器（Nginx + SPA，无 /data、无 Docker Socket）
                                     │ 反向代理 /api/v1/
                                     ▼
                              127.0.0.1:8000 ──► service-hub 容器
                                                  ├─ hub-api          无 Socket
                                                  ├─ conda-runner     无 Socket
                                                  ├─ docker-runner    ✔ Socket（一次性 Job）
                                                  ├─ cleaner          无 Socket
                                                  ├─ scheduler        无 Socket
                                                  └─ service-manager  ✔ Socket，127.0.0.1:8001（V3.0 常驻服务）
```

### 0.2 关键参数（照抄即可）

| 项 | 值 |
|---|---|
| 唯一必填部署变量 | `HUB_HOST_DATA_DIR`（宿主机绝对路径） |
| 数据目录默认值 | `/srv/service-hub-data` |
| 后端镜像 | `python-service-hub:1.0.0-linux-amd64` |
| Web 镜像 | `python-service-hub-web:1.0.0-linux-amd64` |
| 后端监听 | `127.0.0.1:8000`（**只绑回环**） |
| Web 监听 | `127.0.0.1:8080`（**只绑回环**） |
| 管理台入口 | `http://<服务器>:8080` → 需 SSH 隧道或宿主代理，见第 8 节 |
| 首次管理员凭据 | `<HUB_HOST_DATA_DIR>/bootstrap-admin.json`（0600） |
| 认证模式 | 默认 `required`（镜像内 `config/hub.yaml` 未写 `auth` 段 → 取默认值） |

### 0.3 数据目录结构（首次启动自动创建）

```text
<srv/service-hub-data>/
├── bootstrap-admin.json   初始管理员一次性口令（0600，改密后可删）
├── secrets/runner-token   内部 Runner 令牌，自动生成（0600）
├── db/hub.db              SQLite（WAL 模式）
├── files/                 上传的输入文件与 Job 输出
├── plugins/               已安装插件 Build
├── jobs/                  Job 工作目录与日志
├── logs/                  聚合日志
├── environments/          conda-pack 预构建环境
├── backups/               备份归档（保留最近 3 份）
└── .permissions-single-container-v1   权限迁移标记（勿删）
```

### 0.4 三条硬约束（部署前必须知道）

1. **只支持 Linux**。`platform_os` 在代码里硬编码为 `linux`，非 Linux 宿主机无法启动。
2. **端口只绑 `127.0.0.1`**。这是设计而非疏漏。对外访问必须经 SSH 隧道或宿主反向代理，不要直接改 compose 的绑定地址。
3. **离线模型**：Hub 不做隐式 `pull`。要用 V3.0 部署常驻服务、或跑 docker 运行时插件，目标镜像必须**先存在于宿主 Docker daemon**，否则返回 `422 SERVICE_IMAGE_MISSING`。

## 1. 开工前的三个决定

### 1.1 [必做] 确认服务器架构是 AMD64

```bash
uname -m          # 期望 x86_64
```

- 官方发布脚本 `deploy/release/build-release.sh` 在非 `x86_64` 上直接退出；`compose.yaml` 固定 `platform: linux/amd64`。
- ARM64 理论上可运行（配置层允许 `arm64`），但发布脚本与全部真机集成测试都按 AMD64 冻结 —— **试用阶段不要用 ARM64**，会失去验收依据。

### 1.2 [必做] 确认服务器能否访问外网

| 路径 | 条件 | 走法 |
|---|---|---|
| **A 现场构建** | 服务器能访问 PyPI 与 npm registry | 第 3.1 节 |
| **B 离线发布包** | 服务器完全离线 | 第 3.2 节（需一台联网的 Linux AMD64 中继机） |

> 注意：Web 镜像构建阶段执行 `npm ci`，**必须有网络**（或可用的内网 registry 镜像）。因此"离线服务器"只能走路径 B。

### 1.3 [必做] 确认访问方式

| 方式 | 适用 | 章节 |
|---|---|---|
| SSH 隧道 | 试用首选，零配置、零暴露 | 8.1 |
| 宿主 Nginx + TLS | 需要多人/长期访问 | 8.2 |
| 直接改 compose 绑 `0.0.0.0` | **不推荐**（会绕过全部边界设计） | —— |

## 2. 服务器准备

### 2.1 [必做] 系统基础

- [ ] Linux 内核 ≥ 4.x，磁盘剩余空间 ≥ 50 GiB（插件环境 + 数据 + 镜像）
- [ ] 内存 ≥ 4 GiB，CPU ≥ 2 核
- [ ] 时间同步正常（`timedatectl status`，定时任务与审计时间戳依赖系统时钟）
- [ ] 可用 `sudo` 的账号

### 2.2 [必做] 安装 Docker Engine 与 Compose v2

```bash
docker version --format '{{.Server.Version}}'   # 期望 24.x 及以上
docker compose version                          # 期望 v2.x
docker info >/dev/null && echo "docker OK"
```

离线服务器需预先准备 `containerd.io`、`docker-ce`、`docker-ce-cli`、`docker-compose-plugin` 的 `.deb`/`.rpm` 离线包。

### 2.3 [必做] 检查 Docker Socket 的 GID（容易踩的坑）

容器 entrypoint 会校验：**Docker Socket 的 GID 不能等于 `hub-data` 组的 GID（65532）**，相等时直接拒绝启动。

```bash
stat -c '%g' /var/run/docker.sock    # 例如 999 / 998
getent group docker                  # 确认同名组
```

- [ ] 若输出为 `65532`：必须先在宿主机改 Docker 的 socket `group`（`/etc/docker/daemon.json` 的 `"group": "docker"`），重启 Docker 后再继续。否则容器会以 `Docker socket GID conflicts with the hub-data group` 退出。

### 2.4 [必做] 创建数据目录

`HUB_HOST_DATA_DIR` 的规则（入口脚本与容器内 bootstrap 会各校验一次）：

- 必须是**绝对路径**（`/srv/...` 形式），不能是 `./data`
- 至少两级路径
- 不得为 `/`、`/srv`、`/tmp`、`/var`、`/data`

```bash
sudo install -d -m 0750 /srv/service-hub-data
```

> 为什么必须是宿主机绝对路径：docker-runner 会把这个值直接交给**宿主 Docker daemon** 作为插件容器的 bind source，相对路径会让 daemon 找不到目录。

### 2.5 [必做] 端口与防火墙

- [ ] 8000、8001、8080 **不对外开放**（本来也只绑回环，防火墙再兜一层）
- [ ] `ufw`/`firewalld` 放行 SSH（以及第 8.2 节的 443，如启用宿主代理）

```bash
sudo ss -lntp | grep -E ':(8000|8080|8001)\b'    # 期望此刻无输出（尚未启动）
```

### 2.6 [必做] 源码或发布包就位

**路径 A（现场构建）**：把仓库放到 `/srv/python-service-hub`，并切到正确分支：

```bash
cd /srv/python-service-hub
git worktree list                # 确认在 feature/v2-auth-rbac-audit
git log --oneline -1             # 期望 d4ce876
```

> **审查/部署前务必先 `git worktree list`**：本仓库有多个工作树，主工作树 `service-hub/` 落在落后的分支上，误用会部署旧代码。

**路径 B（离线包）**：拿到 `service-hub-1.0.0-linux-amd64.tar.gz` 及其 SHA256。

## 3. 获取两个镜像

### 3.1 路径 A：在服务器现场构建（需外网）

```bash
cd /srv/python-service-hub

sudo docker build --platform linux/amd64 -t python-service-hub:1.0.0-linux-amd64 .
sudo docker build --platform linux/amd64 -t python-service-hub-web:1.0.0-linux-amd64 web

sudo docker image inspect python-service-hub:1.0.0-linux-amd64 >/dev/null && echo "backend OK"
sudo docker image inspect python-service-hub-web:1.0.0-linux-amd64 >/dev/null && echo "web OK"
```

> `docker build web` 的第一步是 `npm ci`，这是唯一强依赖网络的一步。若内网有 npm 镜像，可先改 `web/Dockerfile` 的 registry 再构建。

### 3.2 路径 B：离线发布包（推荐用于生产内网）

在**联网的 Linux AMD64 中继机**上制作发布包：

```bash
./deploy/release/build-release.sh
# 产出 dist/service-hub-1.0.0-linux-amd64.tar.gz 及其 SHA256
```

传输到服务器后在解压目录内执行：

```bash
sha256sum -c SHA256SUMS          # 校验全部内容
sudo ./install.sh                # 校验 + docker load 两个镜像 + 建数据目录 + 写 .env
sudo ./start.sh                  # docker compose up -d
sudo ./status.sh
```

- [ ] `install.sh` 可重复执行：已存在的 `.env` 与数据目录不会被覆盖
- [ ] 想用非默认数据目录：`HUB_HOST_DATA_DIR=/srv/xxx sudo ./install.sh`

> **发布包不含 `config/`**。如需要改配置，见 4.2。

### 3.3 [可选] 预置一个可部署的常驻服务镜像

V3.0 的「服务」页需要目标镜像已在宿主本地：

```bash
sudo docker pull nginxdemos/hello          # 服务器有外网时
# 或离线：docker save nginxdemos/hello -o hello.tar → 拷入 → docker load -i hello.tar
```

## 4. 配置

### 4.1 镜像内默认配置（不改也能跑）

镜像内 `/app/config/hub.yaml` 只有必填项，其余全取代码默认值：

| 配置节 | 默认值 | 是否在镜像配置里显式写出 |
|---|---|---|
| `deployment.mode` | `offline` | 是 |
| `storage.root` | `/data` | 是 |
| `database.url` | `sqlite:////data/db/hub.db` | 是 |
| `uploads.max_size_bytes` | 10 GiB | 是 |
| `runner.shared_token` | 占位值，**运行时被环境变量覆盖** | 是 |
| `auth.mode` | `required` | 否（取默认） |
| `auth.login_failure_threshold` | 5 | 否 |
| `auth.login_lockout_base_seconds` / `_max_seconds` | 30 / 900 | 否 |
| `quotas.*` | 开启，1 TiB / 10000 文件 / 8 并发 Job | 否 |
| `retention.*` | 720h / 30min / 保留 3 份备份 | 否 |
| `webhooks.allow_private_networks` | `false` | 是 |
| `webhooks.allowed_hosts` | `[]` | 是 |

- [ ] **不要手工设置 `runner.shared_token`**：entrypoint 会在 `<数据目录>/secrets/runner-token` 生成高熵令牌，通过 `HUB_RUNNER_TOKEN` 注入全部子进程。手工写死会削弱边界并可能与已生成令牌冲突。

### 4.2 [必做] 需要改配置时：用 override 挂载

镜像内的配置是**构建期 COPY 进去的**，而 `compose.yaml` 没有挂载配置目录。因此改配置有两条路：

**推荐 —— 追加一个 override 文件**（compose v2 会自动读取同目录的 `compose.override.yaml`）：

```bash
sudo mkdir -p /srv/service-hub-config
sudo cp /srv/python-service-hub/config/hub.yaml.example /srv/service-hub-config/hub.yaml
sudo vi /srv/service-hub-config/hub.yaml
```

```yaml
# /srv/python-service-hub/compose.override.yaml
services:
  service-hub:
    volumes:
      - /srv/service-hub-config/hub.yaml:/app/config/hub.yaml:ro
```

```bash
sudo HUB_HOST_DATA_DIR=/srv/service-hub-data docker compose config | grep -A2 'hub.yaml'  # 确认挂载生效
sudo HUB_HOST_DATA_DIR=/srv/service-hub-data docker compose up -d                          # 重建容器
```

> 注意 `config/hub.yaml.example` 是**带完整注释的运维样例**，包含 `auth`/`quotas`/`retention` 全部字段；直接改它比只改最小值更清晰。配置模型是 `extra="forbid"`（多一个不认识的键会启动失败），所以**不要凭记忆加字段**。

常用需要调整的项：

| 场景 | 配置 |
|---|---|
| Job 回调要打到内网/本机录点 | `webhooks.allow_private_networks: true` |
| 上传上限调整 | `uploads.max_size_bytes: <字节>` |
| 关闭配额（试用图省事） | `quotas.enabled: false` |
| 放松登录限流 | `auth.login_failure_threshold` / `_lockout_max_seconds` |
| 延长输入文件保留 | `retention.input_ttl_hours` |

## 5. 首次启动与健康验证

### 5.1 [必做] 启动

```bash
cd /srv/python-service-hub
sudo HUB_HOST_DATA_DIR=/srv/service-hub-data docker compose up -d
sudo docker compose ps
```

- [ ] `service-hub` 与 `service-hub-web` 两个服务都在运行
- [ ] `service-hub-web` 因 `depends_on: service_healthy` 会**等后端健康后才启动**，属预期

### 5.2 [必做] 健康门（六个进程 + API + /data + Docker）

健康检查比"容器在跑"严格得多，它要求：6 个受管进程全部 `RUNNING`、API 返回 200、`/data` 可写、Docker Engine `ping` 通。

```bash
# 1) 容器健康状态
sudo docker inspect --format '{{.State.Health.Status}}' "$(sudo docker compose ps -q service-hub)"   # 期望 healthy

# 2) API
curl -fsS http://127.0.0.1:8000/api/v1/system/health        # 期望 {"status":"UP"}

# 3) 容器内自检（失败时会打印唯一原因行）
sudo docker exec "$(sudo docker compose ps -q service-hub)" python -m deploy.service_hub.healthcheck

# 4) 六个进程
sudo docker exec "$(sudo docker compose ps -q service-hub)" \
  supervisorctl -c /etc/service-hub/supervisord.conf status
```

第 4 条期望输出（顺序可能不同）：

```text
cleaner           RUNNING
conda-runner      RUNNING
docker-runner     RUNNING
hub-api           RUNNING
scheduler         RUNNING
service-manager   RUNNING
```

- [ ] 六行全为 `RUNNING`。任何一行不是 `RUNNING`，先看 `docker compose logs service-hub`。

### 5.3 [必做] 边界自检（这四项是本项目的安全基线）

```bash
hub="$(sudo docker compose ps -q service-hub)"
web="$(sudo docker compose ps -q service-hub-web)"

# 1) Web 容器不得有任何挂载
sudo docker inspect --format '{{json .Mounts}}' "$web"        # 期望 []

# 2) 内部协议端口必须被 Web 边界拒绝
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/internal/v1/system/health   # 期望 404

# 3) Socket 组归属：只有 docker-runner 与 service-mgr 在组内
sudo docker exec "$hub" id hub-api          | grep -o 'groups=.*'   # 不得含 socket 组
sudo docker exec "$hub" id conda-runner     | grep -o 'groups=.*'   # 不得含 socket 组
sudo docker exec "$hub" id docker-runner    | grep -o 'groups=.*'   # 应含 socket 组
sudo docker exec "$hub" id service-mgr      | grep -o 'groups=.*'   # 应含 socket 组

# 4) 端口只能在宿主机本机访问
sudo ss -lntp | grep -E ':(8000|8080)\b'    # 期望均为 127.0.0.1:...
```

- [ ] 1/2/3/4 全部符合期望

### 5.4 [必做] 首登与改密

```bash
sudo cat /srv/service-hub-data/bootstrap-admin.json          # {"username":"admin","password":"..."}
```

- [ ] 已取得初始口令
- [ ] 已登录 `http://127.0.0.1:8080`（经 SSH 隧道）
- [ ] 已按提示修改密码（该账号 `must_change_password=true`，不改密无法进入正常操作）
- [ ] 改密后 `bootstrap-admin.json` 已删除或转存到密码管理器

```bash
sudo rm /srv/service-hub-data/bootstrap-admin.json
```

### 5.5 [建议] 立即做一次备份

```bash
HUB_URL=http://127.0.0.1:8000 python3 tools/hubctl login --username admin
HUB_URL=http://127.0.0.1:8000 python3 tools/hubctl backup create
ls -lh /srv/service-hub-data/backups/
```

> `tools/hubctl` 是纯标准库脚本，宿主机只需 Python 3，无需装依赖。

## 6. 功能冒烟清单

按顺序做，前面的通过才做后面的。全部命令都可在宿主机直接执行（`hubctl` 走 8000 回环）。

### 6.1 [必做] 系统信息与指标

```bash
HUB_URL=http://127.0.0.1:8000 python3 tools/hubctl whoami          # 期望 admin
curl -fsS -H "Authorization: Bearer <token>" http://127.0.0.1:8000/api/v1/system/info
curl -fsS -H "Authorization: Bearer <token>" http://127.0.0.1:8000/api/v1/system/metrics | head -20
```

- [ ] `/system/info` 返回 `platform.os=linux`、`arch=amd64`、`deployment_mode=offline`
- [ ] `/system/metrics` 返回 Prometheus 文本（admin 专属，非 admin 应为 403）

### 6.2 [必做] 认证与角色边界

- [ ] 用错误口令连续登录 6 次：第 6 次起返回 **`429` 且带 `Retry-After`**（限流按 `(用户名, 来源地址)` 分桶，默认阈值 5、退避 30s 起、封顶 900s）
- [ ] 用正确口令登录一次，之后该桶计数清零
- [ ] 创建一个 `viewer` 账号，用它调写接口 → **403**
- [ ] 用 viewer 调 `GET /api/v1/system/metrics` → **403**
- [ ] 管理台「审计」页能看到上述登录失败与拒绝记录

### 6.3 [必做] 文件上传与下载

```bash
echo "smoke test $(date)" > /tmp/smoke.txt
HUB_URL=http://127.0.0.1:8000 python3 tools/hubctl file upload /tmp/smoke.txt
```

- [ ] 上传返回 `file_<id>`
- [ ] 管理台「文件」页能看到该文件，摘要一致
- [ ] 用同一文件再次上传，命中**秒传查重**（`GET /api/v1/files/by-sha256/<hash>`）
- [ ] 超出 `uploads.max_size_bytes` 的上传被拒（试用可不做）

### 6.4 [必做] 插件安装与 Job 执行

**前置**：需要一个 `.pypkg`。构建要求 = Linux AMD64 + Python 3.12 + 联网下载 wheels，因此：

- 服务器有外网 → 直接在服务器上构建；
- 服务器离线 → **在联网的 Linux AMD64 机器上构建后拷入**（发布包不含 `.pypkg`）。

```bash
# 在联网的 Linux AMD64 机器上（需先 pip install -e packages/hub-publisher）
cp -r templates/docker-job-plugin /tmp/example_script
cd /tmp/example_script
hub-plugin build . --runtime docker --arch amd64 --output dist
# 期望输出 .pypkg 绝对路径与 SHA256
```

拷到服务器后安装与运行：

```bash
HUB_URL=http://127.0.0.1:8000 python3 tools/hubctl plugin list
HUB_URL=http://127.0.0.1:8000 python3 tools/hubctl plugin install /srv/pkgs/example_script-1.0.0-linux-amd64-docker.pypkg

# Build 从 INSTALLING → READY 后启用
HUB_URL=http://127.0.0.1:8000 python3 tools/hubctl plugin enable <build_id>

# 建 Job
echo '{"message":"hello from server"}' > /tmp/params.json
HUB_URL=http://127.0.0.1:8000 python3 tools/hubctl job run example_script \
    --version 1.0.0 --runtime docker --params /tmp/params.json

HUB_URL=http://127.0.0.1:8000 python3 tools/hubctl job status job_<id>
HUB_URL=http://127.0.0.1:8000 python3 tools/hubctl job logs job_<id>
HUB_URL=http://127.0.0.1:8000 python3 tools/hubctl job download job_<id> --output /tmp/out
```

- [ ] Build 状态到 `READY`
- [ ] Job 到 `SUCCESS`
- [ ] 日志可见插件输出

### 8.2 [建议] 方案二：宿主 Nginx + TLS

在宿主机 Nginx 上再套一层，代理到 `127.0.0.1:8080`（不要绕过 Web 容器直连 8000，否则会丢掉 SPA 与 `/internal/v1` 的 404 拦截）：

```nginx
server {
    listen 443 ssl;
    server_name hub.example.com;

    ssl_certificate     /etc/nginx/certs/hub.crt;
    ssl_certificate_key /etc/nginx/certs/hub.key;

    client_max_body_size 10g;

    # 内部协议双保险拒绝（Web 容器内 Nginx 已返回 404）
    location ^~ /internal/v1/ { return 404; }

    location /api/v1/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # SSE 实时日志必须关闭缓冲，否则事件被攒住不下发
        proxy_buffering off;
        proxy_cache off;
        proxy_request_buffering off;
        proxy_read_timeout 3700s;
        proxy_send_timeout 3700s;
    }

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

- [ ] 已加来源网段限制（`allow`/`deny`）或至少 HTTP 认证
- [ ] 已配置证书与自动续期
- [ ] `curl -I https://hub.example.com/internal/v1/system/health` 返回 404
- [ ] **已知限制 L-1**：即便如此配置，审计日志与登录限流看到的来源地址仍可能是容器网关地址 —— 见第 11 节

## 11. 已知限制（必须向使用者交代）

| 编号 | 限制 | 影响 | 规避 |
|---|---|---|---|
| L-1 | **审计与限流的来源地址可能是容器网关地址** | `actor_ip()` 取 `X-Forwarded-For` 最右侧条目（防伪造的正确做法），但浏览器 → Web 容器内 Nginx → hub-api 这一段中，Web 容器看到的对端是 Docker 网关，于是最右侧条目恒为网关地址 | 审计 IP 仅作参考；登录限流退化为"按用户名"单维度（仍能防暴力破解，但同一账号在不同来源共享同一桶）。彻底修复需在 Web 容器 Nginx 上配置 `real_ip` 信任网关网段后重写 `$remote_addr`，或让宿主代理直连后端并自行注入可信来源头 |
| L-2 | 启动期自动迁移无降级保护 | 旧镜像回滚到新库会崩 | 回滚连同数据目录一起回滚；升级前强制备份 |
| L-3 | 镜像来源未经校验 | 管理员放置的镜像内容不由 Hub 校验 | 离线模型下由运维承担镜像信任责任 |
| L-4 | 管理员账号等价于高权限账号 | admin 可在数据目录内放置任意内容，docker-runner 亦有 Socket 权限 | 严格控制能登录管理台的人；不要与不可信用户共用实例 |
| L-5 | 单机单库 | SQLite + 单容器，无 HA、无多主机编排 | 试用与小规模内网使用；生产级高可用需另行设计 |
| L-6 | `list_files` 无 owner 过滤 | viewer 能看到其他用户上传的文件元数据（是否越权取决于「共享池 / 私有」产品语义，尚未定论） | 试用期视为团队共享池；如需租户隔离请先反馈 |
| L-7 | 服务端口只能绑回环 | `hub-svc-*` 对外提供访问需宿主机反向代理 | 属设计约束，不要试图绕过 |
| L-8 | SSE 长连接占用线程与 DB 连接 | 大量并发实时日志流会消耗后端连接 | 试用规模下无影响；不做压测结论 |
| L-9 | 列表端点固定 `limit(100)`、无分页 | 历史记录不可达 | 试用规模下无影响 |

## 12. 故障排查

| 现象 | 排查 | 原因与处理 |
|---|---|---|
| 容器一直 `unhealthy` | `docker compose logs service-hub` + 容器内 `python -m deploy.service_hub.healthcheck` | 健康门要求 6 进程 RUNNING + API 200 + /data 可写 + Docker ping 通。看自检打印的那一行原因 |
| 启动即退出：`Docker socket GID conflicts with the hub-data group` | `stat -c '%g' /var/run/docker.sock` | Socket GID 等于 65532。改 daemon.json 的 socket group（见 2.3） |
| 启动即退出：`HUB_HOST_DATA_DIR is too broad` / `must have at least two path components` | 检查 env 值 | 路径非法，按 2.4 的规则修正 |
| `HUB_HOST_DATA_DIR must be set` | `docker compose config` | Compose 变量未注入，用 `sudo HUB_HOST_DATA_DIR=... docker compose up -d` |
| 8000 或 8080 打不开 | `ss -lntp` | 只绑回环属预期；从宿主机本机访问，或建 SSH 隧道 |
| 8080 页面能开但接口 502 | `docker compose ps` | 后端未 healthy，Web 的 `depends_on: service_healthy` 仍在等 |
| `GET /api/v1/services` 返回 502 | 容器内 `supervisorctl status service-manager` | manager 未启动或令牌不一致（令牌由 entrypoint 统一注入，不要手工设置） |
| 部署服务返回 422 且报镜像缺失 | `sudo docker image inspect <image>` | 离线模型不隐式 pull，先 `docker load`/`docker pull` 到**宿主** daemon |
| 建 Job 报 `422 WEBHOOK_URL_FORBIDDEN` | 检查回调地址 | 默认拒绝内网/回环/链路本地/整型写法；需要内网回调时按 4.2 开启 `webhooks.allow_private_networks` |
| 定时任务不触发、管道不推进，但一切显示健康 | `docker compose logs service-hub \| grep TypeError` | 本缺陷已修复（`d4ce876`）；若仍出现说明部署的是旧镜像，确认 `git log --oneline -1` |
| 插件容器挂载失败 | `docker exec <hub> env \| grep HUB_HOST_DATA_DIR` | 数据路径不是宿主绝对路径 |
| `plugin install` 返回 4xx | `hubctl plugin list` | 同 id+version 已有不同 `source_sha256` 的 Build，或包损坏；核对 SHA256 |
| Job 一直 PENDING/RUNNING | `docker compose logs service-hub \| grep -i runner` | 对应运行时 Runner 未接管；先确认容器健康 |
| Docker Runner 报 permission denied | `docker exec <hub> id docker-runner` | Socket 组未注入；确认宿主 `/var/run/docker.sock` 存在并重启容器 |
| `/internal/v1` 从 8080 返回了数据 | 立即停用 | 正常必须 404。说明 Web 镜像的 Nginx 配置被改动，恢复出厂 `web/nginx.conf` 并重建镜像 |
| Web 容器出现 `/data` 或 docker.sock 挂载 | `docker inspect <web>` | 正常不应有任何挂载，检查 compose.yaml 是否被改 |
