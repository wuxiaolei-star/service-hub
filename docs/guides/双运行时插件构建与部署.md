# Python Service Hub V1 双运行时插件构建与部署指南

本文是一份可以直接照做的 Linux 运维手册。目标是在 Linux AMD64 测试服务器上部署
Service Hub，注册 `nc_to_shp` 的 Conda-Pack Build 与 Docker Build，并用同一个真实 NC
文件完成两次 Job 和语义一致性验收。

## 1. 先理解运行方式

Service Hub 不是把插件永远启动在 Hub 镜像里，也不是为每个插件暴露一个 HTTP 服务。
插件发布者先生成不可变 `.pypkg`，调用方注册 Build；每次创建 Job 时，由相应 Runner
启动一个一次性进程或容器，完成后退出。

```text
业务系统
  │ HTTPS
  ▼
宿主机 Nginx
  │ http://127.0.0.1:8000
  ▼
hub（API、SQLite、/data）
  ├─ runtime_type=conda-pack → hub-conda-runner → 预构建环境/bin/python
  └─ runtime_type=docker     → hub-docker-runner → 一次性插件容器
```

权限边界固定如下：

| 服务 | 宿主端口 | `/data` | Docker Socket | 执行业务代码 |
| --- | --- | --- | --- | --- |
| `hub` | `127.0.0.1:8000` | 读写 | 无 | 否 |
| `hub-conda-runner` | 无 | 读写 | 无 | Conda 子进程 |
| `hub-docker-runner` | 无 | 读写 | 有 | 只启动容器 |
| 插件容器 | 无 | 最小 Job bind | 无 | 是，非 root、无网络 |

Hub 只验证、登记和启动发布者提供的环境，绝不解析或编译插件业务依赖。

## 2. Linux AMD64 前置条件

测试服务器建议使用 Ubuntu 22.04/24.04 AMD64，至少准备：

- Docker Engine 24 或更高版本、Docker Compose v2；
- Git、curl、jq、openssl、ca-certificates；
- 约 30 GiB 可用磁盘；真实 NC 转换建议至少 2 CPU、8 GiB 内存；
- 构建插件的机器还需 Python 3.12、Conda/Mamba，以及访问 conda-forge、PyPI、
  `ghcr.io/osgeo/gdal` 的网络。

检查：

```bash
uname -m                         # 必须是 x86_64
docker version
docker compose version
python3.12 --version
conda --version
```

生产/测试运行 Hub 本身只需要 Docker；Python 和 Conda 是发布者构建插件包时使用的工具。
执行 Docker 命令的账号必须能访问 `/var/run/docker.sock`。该 Socket 等价于高权限入口，
所以只有 `hub-docker-runner` 挂载它，宿主机也应限制 Docker 组成员。

## 3. 构建并启动 Hub 三个镜像

以下命令使用约定目录。默认 Compose 数据源也是
`/srv/python-service-hub/data`：

```bash
sudo git clone <approved-repository-url> /srv/python-service-hub
cd /srv/python-service-hub
sudo install -d -o root -g 65532 -m 0750 /srv/python-service-hub/config
sudo install -d -m 0750 /srv/python-service-hub/data
sudo install -o root -g 65532 -m 0640 config/hub.yaml.example config/hub.yaml
```

生成高熵内部 Runner Token，保存为 Compose 的共享变量。三个服务从同一份
`.env` 读取，Hub 的环境变量覆盖 YAML 中的示例值；不要修改 Compose 模板：

```bash
RUNNER_TOKEN="$(openssl rand -hex 32)"
printf 'HUB_RUNNER_TOKEN=%s\n' "${RUNNER_TOKEN}" | sudo tee .env >/dev/null
unset RUNNER_TOKEN
sudo chmod 0600 .env
```

Hub 容器以固定 UID/GID `65532:65532` 读取配置。`config` 目录为
`root:65532 0750`，YAML 为 `root:65532 0640`；不要仅对 root:root 文件执行
`chmod 0640`。绑定的是 YAML 文件，容器内父目录 `/app/config` 由镜像创建并
允许 Hub 遍历。构建后可用下面的实际非 root 进程检查挂载配置：

```bash
sudo docker compose run --rm --no-deps hub python -c \
  'import os; from pathlib import Path; assert os.getuid()==65532; assert Path("/app/config/hub.yaml").read_text()'
```

如果仓库不位于 `/srv/python-service-hub`，必须把宿主数据目录写成绝对路径：

```bash
printf 'HUB_DATA_DIR=/absolute/path/python-service-hub-data\n' | sudo tee -a .env
sudo install -d -m 0750 /absolute/path/python-service-hub-data
```

不要把 `HUB_DATA_DIR` 写成 `./data`。Docker Runner 在容器内从 `/data` 读取协议，但启动
插件容器时，Docker daemon 必须收到宿主机绝对 bind source；相对路径和 `/` 都会被
Runner 拒绝。

构建、检查拓扑并启动：

```bash
sudo docker compose build --pull
sudo docker compose config > /tmp/python-service-hub-compose.resolved.yaml
sudo docker compose up -d --no-build
sudo docker compose ps
curl -fsS http://127.0.0.1:8000/api/v1/system/health
```

应得到 `{"status":"UP"}`。再检查：

```bash
sudo docker compose ps --format json | jq .
sudo docker compose images
```

可从 `docker compose ps` 获取实际容器名，再用 `docker inspect <容器名>` 检查
`HostConfig.Binds`。验收条件是只有 Hub 发布 `127.0.0.1:8000`，只有 Docker Runner
含 `/var/run/docker.sock`。

## 4. 发布者构建 nc_to_shp 两个包

这一步在有网络的原生 Linux AMD64 构建机执行。两种 Build 共享插件源码，但环境完全
独立，最终生成两个文件，不能把它们合并成一个包。

准备 Python 构建入口：

```bash
cd /srv/python-service-hub
python3.12 -m venv .venv-publisher
source .venv-publisher/bin/activate
python -m pip install --upgrade pip build hatchling
python -m pip install -e packages/hub-contracts zstandard
mkdir -p packages/nc-to-shp-plugin/dist
```

构建原生 AMD64 Conda-Pack 包。脚本会创建临时 Conda 环境、安装 GDAL/h5py/NumPy/
SciPy 和三个 Hub wheel，执行 `conda-pack`，再生成 `.pypkg`：

```bash
python packages/nc-to-shp-plugin/scripts/package_build.py \
  --runtime conda-pack \
  --arch amd64 \
  --output packages/nc-to-shp-plugin/dist
```

构建 AMD64 Docker 包。脚本会构建插件镜像、固定 image digest、`docker save`，再生成
`.pypkg`：

```bash
python packages/nc-to-shp-plugin/scripts/package_build.py \
  --runtime docker \
  --arch amd64 \
  --output packages/nc-to-shp-plugin/dist
```

检查产物：

```bash
ls -lh packages/nc-to-shp-plugin/dist/*.pypkg
sha256sum packages/nc-to-shp-plugin/dist/*.pypkg \
  | tee packages/nc-to-shp-plugin/dist/SHA256SUMS
```

必须存在：

```text
nc_to_shp-1.0.0-linux-amd64-conda.pypkg
nc_to_shp-1.0.0-linux-amd64-docker.pypkg
```

Hub 不会替你安装上述包内的依赖；缺依赖必须回到发布者构建阶段重新生成新版本 Build。

## 5. 注册、轮询并启用两个 Build

设置仅监听回环的 Hub 地址：

```bash
HUB_URL=http://127.0.0.1:8000
PACKAGE_DIR=/srv/python-service-hub/packages/nc-to-shp-plugin/dist
```

安装 Conda Build：

```bash
CONDA_INSTALL_JSON="$(curl -fsS \
  -F "file=@${PACKAGE_DIR}/nc_to_shp-1.0.0-linux-amd64-conda.pypkg" \
  "${HUB_URL}/api/v1/plugins/install")"
printf '%s\n' "${CONDA_INSTALL_JSON}" | jq .
CONDA_BUILD_ID="$(printf '%s' "${CONDA_INSTALL_JSON}" | jq -r .build_id)"
```

安装 Docker Build：

```bash
DOCKER_INSTALL_JSON="$(curl -fsS \
  -F "file=@${PACKAGE_DIR}/nc_to_shp-1.0.0-linux-amd64-docker.pypkg" \
  "${HUB_URL}/api/v1/plugins/install")"
printf '%s\n' "${DOCKER_INSTALL_JSON}" | jq .
DOCKER_BUILD_ID="$(printf '%s' "${DOCKER_INSTALL_JSON}" | jq -r .build_id)"
```

两个请求都返回 HTTP 202。Runner 异步安装环境，所以要分别轮询：

```bash
watch -n 2 "curl -fsS ${HUB_URL}/api/v1/plugin-builds/${CONDA_BUILD_ID} | jq ."
watch -n 2 "curl -fsS ${HUB_URL}/api/v1/plugin-builds/${DOCKER_BUILD_ID} | jq ."
```

按 `Ctrl+C` 退出 `watch`。状态为 `READY` 后分别启用：

```bash
curl -fsS -X POST \
  "${HUB_URL}/api/v1/plugin-builds/${CONDA_BUILD_ID}/enable" | jq .
curl -fsS -X POST \
  "${HUB_URL}/api/v1/plugin-builds/${DOCKER_BUILD_ID}/enable" | jq .
```

最终两个状态都应为 `ENABLED`，且 `runtime_type` 分别是 `conda-pack`、`docker`。相同
PluginVersion/平台/运行时不能覆盖安装；若要更换环境，请发布新的插件版本。

## 6. 上传 NC 并分别运行两个 Job

上传真实文件并记录 `file_id`：

```bash
NC_PATH=/absolute/path/20260828213102_生成hdf5结果详情信息.nc
FILE_JSON="$(curl -fsS -F "file=@${NC_PATH}" "${HUB_URL}/api/v1/files")"
printf '%s\n' "${FILE_JSON}" | jq .
FILE_ID="$(printf '%s' "${FILE_JSON}" | jq -r .file_id)"
```

创建 Conda Job：

```bash
CONDA_JOB_JSON="$(curl -fsS -X POST "${HUB_URL}/api/v1/jobs" \
  -H 'Content-Type: application/json' \
  -d "{\"plugin_id\":\"nc_to_shp\",\"version\":\"1.0.0\",\"runtime_type\":\"conda-pack\",\"inputs\":{\"source_nc\":\"${FILE_ID}\"},\"params\":{\"group_name\":\"1\",\"metrics\":[\"depth\",\"stage\"],\"start_time\":1,\"end_time\":20,\"target_crs\":null}}")"
CONDA_JOB_ID="$(printf '%s' "${CONDA_JOB_JSON}" | jq -r .job_id)"
printf '%s\n' "${CONDA_JOB_JSON}" | jq .
```

创建 Docker Job：

```bash
DOCKER_JOB_JSON="$(curl -fsS -X POST "${HUB_URL}/api/v1/jobs" \
  -H 'Content-Type: application/json' \
  -d "{\"plugin_id\":\"nc_to_shp\",\"version\":\"1.0.0\",\"runtime_type\":\"docker\",\"inputs\":{\"source_nc\":\"${FILE_ID}\"},\"params\":{\"group_name\":\"1\",\"metrics\":[\"depth\",\"stage\"],\"start_time\":1,\"end_time\":20,\"target_crs\":null}}")"
DOCKER_JOB_ID="$(printf '%s' "${DOCKER_JOB_JSON}" | jq -r .job_id)"
printf '%s\n' "${DOCKER_JOB_JSON}" | jq .
```

轮询状态、查看日志：

```bash
watch -n 2 "curl -fsS ${HUB_URL}/api/v1/jobs/${CONDA_JOB_ID} | jq ."
curl -fsS "${HUB_URL}/api/v1/jobs/${CONDA_JOB_ID}/logs?cursor=0&limit=500" | jq .

watch -n 2 "curl -fsS ${HUB_URL}/api/v1/jobs/${DOCKER_JOB_ID} | jq ."
curl -fsS "${HUB_URL}/api/v1/jobs/${DOCKER_JOB_ID}/logs?cursor=0&limit=500" | jq .
```

成功终态是 `SUCCESS`。失败时检查 Job 的 `error_summary`，再查看 Runner：

```bash
sudo docker compose logs --tail=300 hub-conda-runner
sudo docker compose logs --tail=300 hub-docker-runner
```

取消未完成 Job：

```bash
curl -fsS -X POST "${HUB_URL}/api/v1/jobs/${CONDA_JOB_ID}/cancel" | jq .
```

取消请求设置 `cancel_requested=true`，最终由 Runner 转为 `CANCELLED`；超过插件定义的
3600 秒则为 `TIMED_OUT`，错误码为 `JOB_TIMED_OUT`。

下载输出：

```bash
CONDA_OUTPUT_ID="$(curl -fsS \
  "${HUB_URL}/api/v1/jobs/${CONDA_JOB_ID}/outputs" | jq -r '.items[0].file_id')"
DOCKER_OUTPUT_ID="$(curl -fsS \
  "${HUB_URL}/api/v1/jobs/${DOCKER_JOB_ID}/outputs" | jq -r '.items[0].file_id')"
curl -fsSL "${HUB_URL}/api/v1/files/${CONDA_OUTPUT_ID}/download" -o conda-result.zip
curl -fsSL "${HUB_URL}/api/v1/files/${DOCKER_OUTPUT_ID}/download" -o docker-result.zip
unzip -l conda-result.zip
unzip -l docker-result.zip
```

## 7. Linux AMD64 自动验收

验收测试会自行上传 NC、安装并启用两个包、运行两个 Job、下载 ZIP，并用 OGR 按组件、
PointZ、CRS、字段、39,464 个要素、SMID、全量坐标和属性值比较。请在空白测试数据目录
上运行，避免 `1.0.0` Build 已存在导致不可变唯一键冲突。

创建只用于测试客户端和 OGR 比较器的环境：

```bash
conda create -y -n hub-accept -c conda-forge \
  python=3.12 pytest=8.3 httpx=0.28 gdal=3.10.3
conda activate hub-accept
cd /srv/python-service-hub
```

执行真实发布门：

```bash
HUB_NC_SAMPLE_PATH=/absolute/path/20260828213102_生成hdf5结果详情信息.nc \
HUB_PLUGIN_PACKAGE_DIR=/srv/python-service-hub/packages/nc-to-shp-plugin/dist \
HUB_BASE_URL=http://127.0.0.1:8000 \
python -m pytest -m integration tests/integration/test_dual_runtime_nc_to_shp.py -v
```

未设置 `HUB_NC_SAMPLE_PATH` 时测试明确跳过；Windows 或非 AMD64 主机也明确跳过，不能
用 Windows Docker Desktop 的结果代替 Linux AMD64 发布验收。

## 8. 离线构建和搬运

在有网络的 Linux AMD64 构建机完成第 3、4 节，然后生成一个保持目录结构的离线包：

```bash
cd /srv/python-service-hub
sudo docker compose build --pull
RELEASE_PARENT="$(mktemp -d)"
RELEASE_DIR="${RELEASE_PARENT}/python-service-hub-release-amd64"
install -d "${RELEASE_DIR}/config" "${RELEASE_DIR}/deploy/nginx" \
  "${RELEASE_DIR}/plugins"
sudo docker save \
  python-service-hub:0.1.0-linux-amd64 \
  python-service-hub-conda-runner:0.1.0-linux-amd64 \
  python-service-hub-docker-runner:0.1.0-linux-amd64 \
  -o "${RELEASE_DIR}/python-service-hub-images-0.1.0-linux-amd64.tar"
cp compose.yaml "${RELEASE_DIR}/"
cp config/hub.yaml.example "${RELEASE_DIR}/config/"
cp deploy/nginx/python-service-hub.conf.example "${RELEASE_DIR}/deploy/nginx/"
cp packages/nc-to-shp-plugin/dist/*.pypkg "${RELEASE_DIR}/plugins/"
(cd "${RELEASE_DIR}" && sha256sum \
  python-service-hub-images-0.1.0-linux-amd64.tar plugins/*.pypkg > SHA256SUMS)
tar -C "${RELEASE_PARENT}" -czf ./python-service-hub-release-amd64.tar.gz \
  python-service-hub-release-amd64
```

搬运清单：

```text
python-service-hub-release-amd64.tar.gz
```

离线服务器先校验，再导入并启动；Token 应在目标机现场生成：

```bash
sudo install -d -m 0750 /srv/python-service-hub
sudo tar -xzf python-service-hub-release-amd64.tar.gz \
  -C /srv/python-service-hub --strip-components=1
cd /srv/python-service-hub
sha256sum -c SHA256SUMS
sudo docker load -i python-service-hub-images-0.1.0-linux-amd64.tar
sudo install -d -m 0750 /srv/python-service-hub/data
sudo install -d -o root -g 65532 -m 0750 config
sudo install -o root -g 65532 -m 0640 config/hub.yaml.example config/hub.yaml
# 按第 3 节在目标机生成新的 .env，不搬运构建机 .env，不替换 compose.yaml
sudo docker compose up -d --no-build
```

Docker 插件镜像已经封装在 Docker `.pypkg` 内，注册后由 Docker Runner 离线导入，目标
服务器不需要访问镜像仓库。

## 9. Nginx、网络与无认证边界

V1 不做 API Key、JWT 或用户权限。不得把 Compose 端口改成 `0.0.0.0:8000`。宿主机
Nginx 负责 TLS 和来源地址白名单，防火墙只允许可信调用系统访问 443。示例：

```bash
sudo cp deploy/nginx/python-service-hub.conf.example \
  /etc/nginx/conf.d/python-service-hub.conf
# 修改域名、证书路径和 allow 网段
sudo nginx -t
sudo systemctl reload nginx
```

必须同时拒绝 `/internal/v1` 和 `/internal/v1/`，它们只供 Compose 内两个 Runner 使用。
Nginx 的 `client_max_body_size` 当前为 10 GiB，代理读取/发送超时为 3700 秒。

## 10. 备份与恢复

持久状态全部位于配置的宿主数据目录：

```text
/srv/python-service-hub/data/db/hub.db
/srv/python-service-hub/data/files/
/srv/python-service-hub/data/plugins/
/srv/python-service-hub/data/environments/
/srv/python-service-hub/data/jobs/
```

SQLite 与文件必须是同一个一致性快照。最稳妥的 V1 方案是短暂停机后整体备份：

```bash
cd /srv/python-service-hub
HUB_DATA_ROOT=/srv/python-service-hub/data  # 如 .env 修改过 HUB_DATA_DIR，这里必须填同一绝对路径
# 使用 Runner 镜像中相同的 owner 计算函数；尾部 /、重复 / 和 /./ 会统一规范化。
HUB_OWNER="$(sudo docker compose run --rm --no-deps -T --entrypoint python \
  hub-docker-runner -m hub_runner.docker_executor "${HUB_DATA_ROOT}")" || exit 1
test -n "${HUB_OWNER}" || exit 1

# 先停两个 Runner。Docker Runner 的 SIGTERM 处理会清理属于本 Hub 的一次性插件容器。
sudo docker compose stop -t 30 hub-conda-runner hub-docker-runner

# 后备保险仍只按本 Hub 的精确 owner 标签停止/删除，绝不处理其他容器。
for container_id in $(sudo docker ps -aq \
  --filter "label=io.python-service-hub.owner=${HUB_OWNER}"); do
  sudo docker stop -t 10 "${container_id}" || true
  sudo docker rm -f "${container_id}" || true
done
test -z "$(sudo docker ps -aq \
  --filter "label=io.python-service-hub.owner=${HUB_OWNER}")" || exit 1

sudo docker compose stop hub
sudo tar --xattrs --acls -C /srv/python-service-hub \
  -czf /secure-backup/python-service-hub-$(date +%F-%H%M%S).tar.gz \
  data config/hub.yaml compose.yaml
sudo docker compose start
```

备份含内部 Token，应限制权限并加密。恢复时先停止三服务，把 `data/`、配置和 Compose
恢复到原绝对位置，检查所有者/权限，再启动。不要执行 `docker compose down --volumes`，
也不要只复制正在写入的 `hub.db`。

## 11. 后续迁移 Linux ARM64

业务源码不变，但 AMD64 Hub 镜像、Conda 环境和 Docker 插件镜像都不能搬到 ARM64 直接
运行。应生成全新的 ARM64 产物。

Hub 三镜像可在配置好 Buildx/QEMU 的构建机生成：

```bash
docker buildx build --platform linux/arm64 --load \
  -t python-service-hub:0.1.0-linux-arm64 -f Dockerfile .
docker buildx build --platform linux/arm64 --load \
  -t python-service-hub-conda-runner:0.1.0-linux-arm64 \
  -f deploy/runner/Dockerfile.conda-runner .
docker buildx build --platform linux/arm64 --load \
  -t python-service-hub-docker-runner:0.1.0-linux-arm64 \
  -f deploy/runner/Dockerfile.docker-runner .
```

Conda-Pack Build 必须在原生 Linux ARM64 构建机执行：

```bash
python packages/nc-to-shp-plugin/scripts/package_build.py \
  --runtime conda-pack --arch arm64 --output packages/nc-to-shp-plugin/dist
python packages/nc-to-shp-plugin/scripts/package_build.py \
  --runtime docker --arch arm64 --output packages/nc-to-shp-plugin/dist
```

复制 Compose 为 ARM64 版本并把三个镜像标签的 `linux-amd64` 改为 `linux-arm64`、三个
`platform` 的 `linux/amd64` 改为 `linux/arm64`。Hub 默认会把原生 `aarch64/arm64`
规范化为 `arm64`；离线部署时仍建议在 `config/hub.yaml` 根节点显式声明：

```yaml
platform_arch: arm64
```

配置文件修改后继续保持 `root:65532 0640`。启动后可安装
`build.json.target.arch=arm64` 的 Build，AMD64 Build 会被拒绝。按第 8 节导出、校验、离线导入，再在
真实 ARM64 服务器重新执行安装和双运行时验收。不要修改 `plugin.yaml` 写死平台；平台
只属于每个 `build.json`。

## 12. 常见故障定位

- Build 长期 `INSTALLING`：检查对应 Runner 日志、Token 是否与 `config/hub.yaml` 一致。
- Docker Job 找不到输入：确认 `HUB_DATA_DIR` 是宿主机绝对路径，并且三个服务挂载同一路径。
- Conda Build `FAILED`：发布包的环境可能不是在相同 Linux CPU 架构原生构建。
- Docker Build digest 不匹配：禁止重新标记或篡改包内镜像归档，重新发布新插件版本。
- Job 返回 `PLUGIN_BUILD_NOT_ENABLED`：对应 `runtime_type` 的 Build 尚未 `ENABLED`，Hub
  不会自动回退到另一运行时。
- OGR/PROJ 错误：插件环境内 GDAL 和 PROJ 数据版本不匹配；Hub 不会现场修复依赖。
