## 一、是否存在重大潜在隐患 —— **是，有 1 条高危链 + 4 条中危**

### H-1（最高优先）V3.0 服务部署面缺乏输入约束，admin 权限可直达宿主机 root

**证据**（`deploy/service_hub/service_manager_service.py`）：

| 约束点 | 现状 | 位置 |
|---|---|---|
| 挂载来源 | `_to_docker_volumes` 对 `mount["source"]` **零校验**，可挂宿主机 `/`、`/var/run/docker.sock`，默认 `rw` | :66-72 |
| 运行用户 | `user_label` 默认 `"65532:65532"` 但**可传 `"0:0"`**，`containers.run(user=...)` 直接生效 | :30, :108 |
| 宿主端口 | `_to_docker_ports` 强制 `127.0.0.1` ✅ 但 **host 端口无范围限制**，可抢占宿主机 8000/8080/22 等任意端口 | :61-63 |
| 镜像名 | `spec.image` 任意字符串，无本地存在性/来源校验 | :25 |

**攻击链**：登录无速率限制（D-5）→ 爆破/钓鱼拿到 admin → 一次 `POST /api/v1/services`（挂载 `docker.sock` 或以 `user_label="0:0"` + 挂宿主机根目录）→ **宿主机任意代码执行（root）**。整条链在当前代码上无任何一环被阻断。

**定性**：当前信任模型是"admin 完全可信"（单团队离线部署），且所有边界端口都绑 `127.0.0.1`（compose.yaml:9,22），这缓解了外部直达。但该能力**未在文档声明边界**，且与项目"降权运行、Socket 最小授权"的整体安全哲学相悖。admin 一旦失陷即全盘失陷，无纵深防御。

**建议修复**（`service_manager_service.py` + `routers/services.py` 各加校验，约 40 行）：
1. `user_label` 强制非 root：拒绝 uid=0 或整体禁用该字段；
2. 挂载来源白名单：仅允许 `$HUB_HOST_DATA_DIR` 前缀，显式拒绝 `docker.sock` 与 `/etc`、`/root` 等敏感路径；
3. host 端口范围限制（如 10000-61000，避开 8000/8001/8080/22）；
4. 镜像名格式校验 + 部署前本地存在性检查。

### H-2 SQLite 未启用 WAL/busy_timeout（= 前轮 D-6）

5 个进程并发写同一库文件（hub-api、cleaner、scheduler、两个 runner），默认 rollback journal + busy_timeout=0 → 写冲突直接抛 `database is locked` 冒泡为 500。**这是生产环境最可能随机触发的故障**。修复三行（`db.py:15` 加 `timeout=30`，connect 事件加 `PRAGMA journal_mode=WAL` + `busy_timeout=30000`）。

### H-3 上传配额三重缝隙（= 前轮 D-1）

`files.py:78` Content-Length 缺失时默认 `"0"` 预检失效（chunked 绕过）；`:85` 补检时文件已落盘、记录已 commit（超配额仍持久化 + 孤儿文件）；`quotas.py` 先查后写无锁（并发突破全局配额）。10GB 上限 × 无限流 = 可先写满磁盘再收到 409。

### H-4 SSE 日志流的长连接资源占用

`routers/logs_stream.py:31-84`：同步生成器 + `time.sleep(1)` 轮询，每个 SSE 连接占用一个线程池线程 + 长持一个 DB session（上限 300s）。并发多个日志页 + 默认线程池/连接池容量 → **池耗尽，阻塞所有同步路由**（包括登录）。单机少量用户可接受，多用户浏览时会成为资源瓶颈。

### H-5 lifespan 每次启动执行 `alembic upgrade head`（= 前轮 D-7）

无并发锁（多 worker 快速重启时并发迁移窗口）、无版本高位检测（**回滚部署旧镜像直接崩**，容器反复重启）。建议迁移移至 entrypoint 一次性执行。

## 二、是否存在重大漏洞 —— **无 0day 级，2 项中危 + 2 项低危**

### V-1（中危）Webhook 回调 SSRF

**证据**：`services/webhooks.py:25-35`（`enqueue_callback` 对 URL **零校验**直接入库）+ `:134-142`（`_post_json` 用 urllib POST 任意 URL）+ `routers/jobs.py:62-68`（operator 角色即可注册 callback）。

**攻击面**：scheduler 进程在容器网络内以服务身份 POST 任意 URL —— 可探测/触达 `127.0.0.1:8001`（service-manager，需 token 会 401）、宿主机网关、内网其他服务、云 metadata 地址。回显（status_code、error 文本）写入审计，**审计仅 admin 可读**（`routers/audit.py:15`），故对非 admin 是盲 SSRF，信息泄露价值有限，但**内网端口/服务探测**与**以 Hub 身份触发内网 POST 副作用**成立。

**缓解环境因素**：离线部署、边界全绑 127.0.0.1。
**建议**：URL 校验（拒绝私网/回环/链路本地地址段，或域名白名单），校验放在 `enqueue_callback` 入口。

### V-2（中危，取决于部署语义）文件横向越权（= 前轮 D-2）

`list_files` 无 owner 过滤（`files.py:100-111`）+ 下载/元数据端点只认 file_key 不校验归属（`:218`, `:245`）→ 任何 viewer 可列举并下载**所有用户**的文件。file_key 是 UUID4 不可枚举，但列表端点直接把全量 key 暴露给了 viewer。**若产品语义是"团队共享文件池"则属设计如此，需文档确认；若是私有空间则是实打实的 IDOR**。

### V-3（低危，一行修复）service-manager token 比较非常量时间

`service_manager_service.py:39` 用 `!=` 比较 Bearer token，而同一代码库的 `internal_runner.py:46` 用 `hmac.compare_digest`。该 token 恰恰持有 Docker 控制权（部署容器/挂载）。回环网络上时序攻击难度高，但双标应统一。

### V-4（低危）登录无失败限流（= 前轮 D-5）

`routers/auth.py` 仅审计 `login_failed`，无计数/退避/锁定。它同时是 H-1 攻击链的第一环。另两个相关小项：改密码后旧会话不吊销（`change_password` 不清 SessionRecord）；`secure` cookie 标志仅在 https 请求下生效（当前 http 部署恒为 False——离线 127.0.0.1 可接受，若日后套 TLS 代理需复核 `request.url.scheme` 判断）。

## 三、可优化的地方 —— 上轮 O-1~O-7 全部有效，本轮新增 5 项

**沿上轮清单（略，见《架构审查-缺陷与优化清单.md》）**：O-1 nginx 安全响应头、O-2 同步 session 混 async 路由、O-3 孤儿上传目录无清理、O-4 超限先写后判、O-5 supervisord startretries 未显式、O-6 bootstrap 重复建引擎、O-7 runner token 常驻环境变量。以及列表分页（D-3）、`list_jobs` N+1（D-4）、文档不一致（D-9）。

**本轮新增**：

1. **审计 IP 恒为代理地址**：`dependencies_auth.py:82-84` 与 `routers/auth.py:43-44` 都用 `request.client.host`，经 nginx 代理后所有审计行 IP 都是 web 容器地址。应信任并解析 `X-Forwarded-For`（nginx 已正确设置该头，`web/nginx.conf:41`，服务端却弃之不用）。
2. **create_service 部署失败后定义残留**：`routers/services.py:79-84` 部署抛错时 `desired_state="STOPPED"` 但记录保留——用户看到创建失败，重试同名却 409 `SERVICE_NAME_TAKEN`，须先 DELETE 才能重建。要么失败即回滚插入，要么在 409 信息中提示"存在失败定义，请先删除"。
3. **服务日志 viewer 可读**：`get_service_logs`（`services.py:147-162`）无角色下限（路由级仅 viewer）。服务容器日志可能含敏感信息，建议提到 admin，与"部署/操作 admin-only"保持一致。
4. **scheduler 定时精度**：`scheduler_service.py:64` 固定 30s 轮询，`schedules` 的 `next_run_at` 实际触发延迟最多 30s。对当前场景够用，若未来有分钟级敏感的调度需求需调整。
5. **cleaner 只扫 DB 过期记录**：`RetentionSweeper` 依赖 file_records 行驱动删除，上轮 O-3 指出的"落盘后未入库"孤儿目录（`uploads/<key>/` 无对应行）不会被清理——两轮结论合并为同一个改进项：cleaner 增加对物孤儿目录的扫描。

## 四、总体结论

**架构健康度：良好偏上。** 部署接线（进程、用户、Socket 组、健康检查、端口绑定）经两轮核实全部正确；认证实现（argon2id、摘要落库、角色矩阵）和内部协议（compare_digest、状态机）质量高于同类项目平均水平；上轮的两条 P0 误报已确认不存在。

**但有一条必须立即处理的隐患链**：H-1（服务部署面无约束）× V-4（登录无限流）组合 = admin 失陷即宿主机失陷，无纵深防御。这不影响当前"可信单团队离线"部署的安全运转，但一旦账号泄露或未来开放给更大范围用户，就是最短路径的全盘沦陷。建议在下一个版本完成 H-1 的四项输入约束 + D-5 限流 + H-2 WAL，三件事合计改动量约百行，可将系统从"依赖 admin 可信"提升到"admin 失陷仍有边界"。

**修复优先级（合并两轮）**：
1. **立即**：H-1 输入约束、H-2 WAL 三行、V-3 compare_digest 一行
2. **本版本**：H-3 配额、V-1 SSRF 白名单、V-4 限流、V-2 归属校验（先确认产品语义）
3. **随版本**：H-5 迁移时机、D-3 分页、D-4 N+1、D-9 文档、审计 IP
4. **可排期**：H-4 SSE 资源、O 系列全部、本轮新增 5 项
