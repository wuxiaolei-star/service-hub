### 2.4 交付链路

```
git push → GitHub Actions（质量门：密钥扫描/后端/前端/镜像构建）
                                  ↓（仅记录，不触碰服务器）
服务器 systemd timer（每 3 min）→ pull-deploy.sh 比对远端 tip
                                  ↓ 有差异
        checkout → 质量门(可选) → 双备份 → build.sh → compose up
                                  ↓
        健康检查(20 次×10 s) → 走查 → 记录 releases.log + 备份轮换

                       自动回滚（冷备恢复 + 重建 + 重启）
```

## 三、本轮发现并已修复的问题

| # | 问题 | 根因 | 修复 |
|---|---|---|---|
| 1 | 质量门"失败"但 pytest 没跑 | 镜像 `ENTRYPOINT=service-hub-entrypoint` 先自举，缺 `HUB_HOST_DATA_DIR` 直接崩 | `docker run --entrypoint bash` |
| 2 | 用例 `test_nested_dockerfiles_...` FileNotFoundError | 运行时镜像不含 `git`，用例依赖 `git check-attr` | 加缺失即跳过（Actions 上有 git，保护仍在） |
| 3 | "备份失败并回滚"（实际容器没停） | `compose.yaml` 用 `${HUB_HOST_DATA_DIR:?}`，流水线没 export | pipeline 补 `export HUB_HOST_DATA_DIR` |
| 4 | 改了流水线却仍在跑旧逻辑 | bash 按字节偏移读运行中的脚本，checkout 后新旧混杂 | `pull-deploy.sh` 先 checkout 再 exec |
| 5 | **自动部署全程失败**（`status=1/FAILURE`） | `set -u` 下 `PIPELINE_ARGS` 未定义即退出；手动跑都带了该变量所以没暴露 | 改 `${PIPELINE_ARGS:-}` |
| 6 | 改一篇文档就触发 10 分钟全量部署 + 1~2 分钟中断 | 未区分改动范围 | 新增轻量路径：改动仅落在 `docs/*`、`*.md`、`README*`、`LICENSE`、`.git*` 时只记录发布不重建（主镜像 Dockerfile **不 COPY 这些路径**，故镜像内容等价） |

| 7 | 轻量路径对中文文档不生效（仍走 10 分钟全量） | git 默认把非 ASCII 路径输出为八进制转义（`"docs/guides/\347\263\273...md"`），匹配不上 `docs/*` | `git diff` 加 `-c core.quotePath=false` |
| 8 | 定时器与手动部署重叠时 systemd 记 `Failed unit` | 并发锁按失败码退出（1），实际是"已有部署在跑"的正常情况 | pipeline 锁冲突退 3；pull-deploy 收到 3 视为空操作；单元加 `SuccessExitStatus=0 2 3` |

> 第 5 条是最严重的一条：修复前 timer 每次触发都以失败告终，CD 实际处于"装好但不工作"的状态。
> 第 6 条同时刷新了 `$REMOTE_DIR/deploy/ci/` 稳定副本——timer 执行的是它，否则脚本修复要等下次 `install-poller.sh` 才生效。
> 第 7、8 条是在修复后首次自动部署时暴露的：前者让轻量路径形同虚设，后者制造假故障告警。

## 四、仍然存在、需要优化的问题

### P0 — 建议近期做（收益高、风险低）

| # | 问题 | 影响 | 建议方案 | 涉及位置 |
|---|---|---|---|---|
| **O-1** | 镜像 tag 固定为 `python-service-hub:1.0.0-linux-amd64`，不含版本信息 | 回滚只能"用**当前**源码重建旧镜像"，代码回滚不精确，且耗时 4.5~9 min | 构建时按 commit 打 tag（`...:1.0.0-<sha>`）并保留 `previous` tag；回滚改为切 tag，不必重建 | `build.sh`、`deploy/ci/deploy-pipeline.sh` |
| **O-2** | 服务器侧质量门默认开启，每次部署固定 8 min | timer 部署总时长 ~10 min，中断窗口被拉长 | 默认 `--skip-gate`（质量门交给 Actions），保留开关；或在 Actions 通过后才打部署标记 | `deploy/ci/deploy-pipeline.sh` |
| **O-3** | 插件包每次都重新打包（即使源码未变） | 约 144 s/次 的无效开销 | 按内容哈希复用：`sha256(源码摘要 + 基础镜像 digest)` 命中即跳过 | `hub_publisher/`（原 P0-3） |
| **O-4** | 三个 Dockerfile 未用 BuildKit 缓存挂载 | 冷/温构建都慢 | `RUN --mount=type=cache` 缓存 apt/pip/npm，配 `DOCKER_BUILDKIT=1` | `Dockerfile`、`web/Dockerfile`、插件 Dockerfile（原 P0-6） |
| **O-5** | 线上同时存在 `nc_to_shp` 1.0.0 与 1.0.1 两份构建，1.0.0 仍是 ENABLED | 约 1 GB 镜像 + 一份 staging 数据；有误用旧版本风险 | 确认无调度引用后禁用并清理 1.0.0 构建，同时删掉 2 条 disabled 调度 | 线上 registry API（原 P2-3） |
| **O-6** | 部署失败/成功**无任何通知** | timer 失败只写在 journalctl，无人知晓 | 流水线结束回调站内 webhook 或邮件（失败必须告警） | `deploy/ci/deploy-pipeline.sh` |
| **O-7** | GitHub Actions 首跑结果未确认 | 质量门是否真绿未知 | 你看一眼 Actions 页，红了我照日志修 | — |

## 六、下一步建议（需你拍板的三件事）

1. **是否现在做 O-1 + O-2**（镜像按 commit 打 tag、质量门交给 Actions）——
   这两项把自动部署从"能跑"变成"好用"，改动集中在 `build.sh` 与流水线脚本，风险低，
   但 O-1 会改变镜像 tag，需要一次真实部署验证。
2. **提供一份真实业务 NC 样本**（O-8）——合成样本只能证明链路通，不能证明业务正确。
3. **顺手看一眼 GitHub Actions 首跑结果**（O-7）——私有仓库日志我这边看不到。

其余 P0 项（O-3/O-4/O-5/O-6）可按上表顺序推进，都是独立改动、互不依赖。
