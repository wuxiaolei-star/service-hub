# 服务说明 · Python Service Hub V2.1

> 本文档描述 V2.1 版本交付时系统的整体状态。V2.0 的完整说明见
> [服务说明-V2.0](服务说明-V2.0.md)；本文仅详述 V2.1 的增量与最终形态。

## 1. 版本定位

V2.1 在 V2.0（单容器双运行时 + Web 管理台 + 认证/RBAC/审计）之上交付**资源治理与
可观测**能力：多用户共用 Hub 时，存储与并发被配额约束，过期输入文件自动清理，
运维可通过 Prometheus 指标观测容量与活动，并具备一条命令的离线备份能力。

协议、既有 API 字段、部署形态（两个 Compose 服务）与"数据目录是唯一持久化点"
的原则全部不变。

## 2. V2.1 新增能力

### 2.1 配额（上传与建 Job 执行点）

| 项 | 全局默认（hub.yaml `quotas`） | 用户覆盖 |
| --- | --- | --- |
| 总存储字节 | `max_total_bytes`（默认 1TiB） | `users.quota_total_bytes` |
| 文件数 | `max_file_count`（10000） | `users.quota_file_count` |
| 并发 Job | `max_concurrent_jobs`（8） | `users.quota_concurrent_jobs` |

- 执行点：`POST /files`（写入 `owner_user_id` 后校验字节/文件数，预检用 Content-Length
  快速失败，落盘后精确复核并排除自身）、`POST /jobs`（按用户非终态 Job 计数）；
- 超限响应：409 `QUOTA_EXCEEDED`，`details={quota, used, limit}`；
- 豁免：admin 角色与认证关闭模式；`quotas.enabled=false` 全部直通；
- API Key  actor 无用户归属，仅受全局字节限制；Job 记录 `owner_user_id`
  （迁移 0004，file 与 job 两表同批）。

### 2.2 文件生命周期清理（cleaner 进程）

- supervisord 第四个受管进程 `[program:cleaner]`（hub-api 用户），与 hub-api/
  conda-runner/docker-runner 一起纳入健康检查必需清单；
- 每 `sweep_interval_minutes`（默认 30 分钟）扫描一次：删除 `role=INPUT`、创建时间
  超过 `input_ttl_hours`（默认 720h）且**未被任何 Job 引用**的文件（记录 + 磁盘负载）；
  `role=OUTPUT` 永不清理；每轮上限 500 个；删除写入审计（actor=system/cleaner）；
- SIGTERM 优雅退出（完成当前轮次）。

### 2.3 指标端点

`GET /api/v1/system/metrics`（admin，Prometheus 文本 0.0.4，无新增依赖）：

~~~text
hub_jobs_total{plugin="...",runtime="...",status="..."}（counter，B8 起）
hub_job_duration_seconds（histogram，B8 起）
hub_jobs_active                hub_files_total
hub_files_bytes_total          hub_plugin_builds_total{status="..."}
hub_users_total                hub_sessions_active
hub_api_keys_active            hub_audit_entries_total
hub_quota_global_bytes_total   hub_uptime_seconds
~~~

> B8 说明：`hub_jobs_total` 由 gauge（仅 status 标签）改为 counter，标签扩展为
> `plugin`/`runtime`/`status`，取值为当前 Job 行数（30 天保留期内对短窗口
> `rate()` 等效单调）；`hub_job_duration_seconds` 为数据库推导的 histogram
> （count/sum 覆盖保留期内已完成作业）。

### 2.4 离线备份

- `POST /api/v1/system/backup`（admin）或 `hubctl backup create`：
  SQLite `backup()` API 在线快照主库 → 打包 `<data>/backups/backup-<UTC时间戳>.tar.gz`
  （含 hub.db、uploads/、plugins/、jobs/ 等；排除 backups/、environments/、logs/；
  成员确定性排序，`.partial` 原子落盘）→ 自动修剪仅保留最近 `backup_keep`（3）份；
- 每次备份写审计（action=`system.backup`）；响应含 file_name/size_bytes；
- `hubctl backup restore --file <路径>`：打印人工恢复步骤清单（停止 compose → 解包 →
  权限 → 重启，禁止 `down -v`），V2.1 不自动执行破坏性操作。

### 2.5 管理台展示

- 用户管理页新增"用量"列（存储字节 + 文件数，逐行懒加载）；
- 系统页新增"运行指标"卡（15 秒轮询：文件总数/存储/活动任务/用户数/活跃会话；
  非 admin 收到 403 时整块隐藏）。

## 3. 部署与配置增量

hub.yaml 新增两节（strict，extra=forbid）：

~~~yaml
quotas:
  enabled: true
  max_total_bytes: 1099511627776
  max_file_count: 10000
  max_concurrent_jobs: 8
retention:
  input_ttl_hours: 720
  sweep_interval_minutes: 30
  backup_keep: 3
~~~

数据目录新增 `backups/`；容器内 supervisord 由三进程变四进程（hub-api、
conda-runner、docker-runner、cleaner），healthcheck 同步要求四进程 RUNNING。

## 4. 质量与验收状态

- 开发机门禁（V2.1 完成时）：python 非集成 **599+ passed**（含配额强制 6、保留清理 5、
  用量 2、指标 3、备份 6 等新增用例）、ruff/mypy strict 通过、web 139 passed +
  typecheck/lint/build 通过、`docker compose config` 通过；
- Linux AMD64 验收（含 cleaner 进程状态、TTL 真实清理、备份完整性、指标抓取样例）
  清单已并入 `docs/reports/single-container-linux-amd64-acceptance.md`。

## 5. 已知限制与后续路线

- 并发 Job 配额按用户计，API Key 创建的 Job 暂无归属（仅全局字节受限）；
- 备份为单机目录内产物，异地容灾需运维拷贝；
- 后续版本路线见 `docs/design/路线图-V2.0至V3.0.md`：V2.2 Webhook 回调/定时任务/
  线性管道，V2.3 插件仓库/分片上传/SSE，V3.0 长期运行 Docker 服务。
