> 本文档描述 V3.0 交付时系统的整体状态。基础与历史增量见
> [服务说明-V2.0](服务说明-V2.0.md)、[服务说明-V2.1](服务说明-V2.1.md)、
> [服务说明-V2.2](服务说明-V2.2.md)、[服务说明-V2.3](服务说明-V2.3.md)；
> 本文仅详述 V3.0 的增量与最终形态。

## 1. 版本定位

V2.x 的插件都是**一次性**任务：一个 Job 拉起一次进程/容器，结束即回收。V3.0 在
不改变这条既有生命周期的前提下，新增**长期运行的 Docker 服务**能力：管理员可以在
Service Hub 内注册、部署、启动、停止、重启、删除一个常驻容器，并查看它的日志。

一句话概括边界：**Job 仍然是一次性的；服务是常驻的；两者互不替代。**

V3.0 的核心安全约束是 Hub API 依然**不接触 Docker Socket**——它把经过鉴权和审计的
期望状态转发给同容器内的 `service-manager` 子进程，由后者独占 Docker Socket 执行。

## 2. V3.0 新增能力

### 2.1 长期运行服务（ServiceDefinition + 生命周期 API）

新增 `service_defs` 表（Alembic `0006_service_defs`），保存名称、镜像、端口映射、
环境变量、挂载、启动命令、容器名与期望状态。对外 API：

| 方法 | 路径 | 最低角色 | 说明 |
|---|---|---|---|
| GET | `/api/v1/services` | viewer | 列出定义 + manager 上报的实时状态 |
| GET | `/api/v1/services/{name}/logs` | viewer | 有界日志尾部（`tail` 1–1000，默认 200，纯文本） |
| POST | `/api/v1/services` | admin | 创建并部署，返回 201 |
| PUT | `/api/v1/services/{name}` | admin | 替换配置与同名容器（幂等） |
| POST | `/api/v1/services/{name}/start\|stop\|restart` | admin | 生命周期动作 |
| DELETE | `/api/v1/services/{name}` | admin | 先删容器再删定义 |

行为约定：

- 服务名必须匹配 `^[a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?$`（K8s 风格 DNS 标签），
  重名创建返回 `409 SERVICE_NAME_TAKEN`；`PUT` 不允许改名字（`422 SERVICE_NAME_IMMUTABLE`）；
- 容器名固定为 `hub-svc-<name>`，重启策略 `unless-stopped`，运行身份必须是**非 root 的
  数字 `uid:gid` 对**（默认 `65532:65532`）；`0:0`、`root:root` 等写法一律 `422`；
- 端口只允许绑定宿主机 `127.0.0.1`，且 **host 端口限定在 1024–65535** 并避开 Hub 自身
  占用（8000 hub-api / 8001 service-manager / 8080 Web），命中保留端口返回 `422`；
- 挂载来源**必须位于宿主机数据目录之内**（白名单根取自 `HUB_DOCKER_HOST_DATA_ROOT`，
  由 entrypoint 从唯一的必填部署变量 `HUB_HOST_DATA_DIR` 派生，二者同值；白名单目录本身
  也不可挂载），目标必须是绝对路径且不含 `..`；`/etc`、`/var/run/docker.sock` 等一律
  `422 SERVICE_MOUNT_FORBIDDEN`；
- 镜像必须**已存在于宿主机本地**：离线部署模型下不做隐式 `pull`，未知镜像返回
  `422 SERVICE_IMAGE_MISSING`，需运维先 `docker load`/`docker import`；
- 部署与更新都是**替换同名容器**的幂等操作；一旦 manager 调用失败，定义会被回写为
  `STOPPED` 并提交，**绝不把数据库标记成 RUNNING**；
- 上述端口/用户/挂载约束在 **API 层（Pydantic + 路由）与 service-manager 层各校验一次**，
  后者作为纵深防御，即使未来出现绕过公开 API 的调用方也不能突破容器边界；
- 所有写操作（create/update/start/stop/restart/delete）都写审计表；公开返回值不回显
  环境变量等敏感输入。

### 2.2 service-manager 与 Docker Socket 隔离

新增 supervisord 程序 `service-manager`（运行身份 `service-mgr`），监听容器内回环
`127.0.0.1:8001`，接口为 `/ping`、`POST /deploy`、
`POST /{name}/start|stop|restart`、`DELETE /{name}`、`GET /{name}/status|logs`。
它使用与 Runner 共享的内部令牌（`Authorization: Bearer $HUB_RUNNER_TOKEN`）校验调用方，
令牌缺失或不匹配一律 `401`。

镜像内的 Socket 访问者只有两个，且只有两个：

| 进程 | 运行身份 | 访问 Docker Socket | 用途 |
|---|---|---:|---|
| hub-api | hub-api | 否 | 业务 API、鉴权、审计 |
| conda-runner | conda-runner | 否 | conda-pack 一次性 Job |
| docker-runner | docker-runner | 是 | docker 一次性 Job |
| cleaner / scheduler | hub-api | 否 | TTL 清理、定时任务 |
| **service-manager** | **service-mgr** | **是** | **V3.0 长期运行服务** |

`docker-entrypoint.sh` 在启动时按 Socket 的真实 GID 建组，只把 `docker-runner` 与
`service-mgr` 加入该组；`hub-api` 与 `conda-runner` 始终不在组内。

该令牌的比较使用常量时间实现（`hmac.compare_digest`），与 Hub 内部 Runner 协议
（`routers/internal_runner.py`）保持一致，避免通过响应时序推断令牌内容。

### 2.3 管理台「服务」页

React 管理台新增 `/services` 页面（侧边栏「服务」）：

- 列表展示名称、镜像、期望状态（RUNNING/STOPPED）与实际状态、健康、操作列；
- 「部署服务」弹窗：名称、镜像、端口映射（可增删多行）、环境变量（每行 `k=v`）、
  挂载（每行 `source:target[:ro]`）、启动命令（逗号分隔，可空）；
- **格式校验在前端完成**：环境变量缺少 `=` 或挂载缺少 `source:target` 时不发请求，
  直接在弹窗内以 `role="alert"` 提示；
- 生命周期按钮按实际状态呈现：未运行显示「启动」，运行中显示「停止」「重启」；
- **删除只对 admin 可见**，且需要 Popconfirm 二次确认；
- 「日志」打开弹窗，可调整尾部行数（默认 200）并刷新；
- `service-manager` 不可用时，网关返回 502，页面统一显示为「service-manager 不可用」，
  而不是原始代理报错；
- 前端不保存任何 Docker 凭据，只调用 Hub API。

## 3. 质量与验收状态

- 开发机门禁（V3.0 完成时）：python 非集成套件全绿、ruff 与 mypy strict 通过；
  web 全量 vitest + typecheck + lint + build 通过；`docker compose config --quiet` 通过；
- service-manager、Hub 服务 API、入口脚本隔离均有单元测试覆盖（令牌校验、回环端口、
  容器命名、替换同名容器、状态/日志映射、Socket 组归属）；
- Linux AMD64 真机验收步骤与检查项见
  [V3.0-部署验收清单](V3.0-部署验收清单.md)。

## 4. 已知限制与后续路线

- V3.0 不实现镜像仓库策略、多主机编排、服务发现或健康探针编排；**镜像来源仍由管理员
  承担信任责任**（虽然镜像必须先存在于本地，但其内容未经 Hub 校验）；
- 服务容器不参与插件 Runner 协议，Job 与服务之间没有自动联动；
- 端口映射只允许 `127.0.0.1`，对外暴露仍需运维在宿主机侧配置反向代理；
- 宿主 Docker Socket 本身就是高权限接口，`service-manager` 是唯一为其降权的守护进程。
  端口/用户/挂载/镜像四项约束已消除「一次调用即取得宿主 root」的最短路径，但**管理员
  仍可在数据目录内放置任意内容**，且 `docker-runner` 的一次性 Job 同样具备 Socket 权限——
  仍应假设管理员账号是高权限账号，并限制谁能登录管理台；
- 登录端点目前**没有失败限流**，暴力破解只受审计记录约束，下一版本需补齐。
