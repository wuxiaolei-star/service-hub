- **G7③ docker 执行器**：`containers.run` 传 `mem_limit="{memory_mb}m"`、
  `memswap_limit` 同值（禁止 swap 超卖）、`nano_cpus=int(cpus*1e9)`；claim 无 cap
  时不传任何资源参数（行为与 B7 前一致）。传递链对照 image_digest 逐跳落地：
  `plugin_versions.manifest_json(execution)` → 认领 payload `RunnerBuildClaim`
  （+`memory_mb`/`cpus`）→ runner 服务 `_job_from_payload` → `RunnerJob` →
  `containers.run`。
- **G7④ conda 执行器（明示语义差异）**：`preexec_fn` 注入 `resource.setrlimit`，
  `RLIMIT_AS` = `memory_mb`，`RLIMIT_CPU` = `cpus` × `timeout` 秒（近似语义）。
  代码与指南均已注明：`RLIMIT_AS` 按虚拟地址空间计，GDAL/numpy 原生内存映射使其
  比 docker `mem_limit`（cgroup 常驻口径）更保守；`RLIMIT_CPU` 是累计 CPU 秒预算，
  非并发核数份额。POSIX 专属：Windows 开发机与"无 cap"路径均返回 None，行为不变；
  `resource` 模块在父进程 fork 前解析，规避 fork 后 import。
- **G7⑤ OOMKill 语义测试（R6）**：docker 用例钉住 StatusCode 137 → `FAILED`
  （非 `TIMED_OUT`，exit_code=137，container 已清理）；server 用例断言三类优先级

### B9 —— 本批（2026-09-25）

- **G9① 算法与依赖选型**：Ed25519（`cryptography`，pyca）。两者均非既有依赖
  （uv.lock/venv 均无），选 `cryptography` 而非 PyNaCl：pyca 标准、社区审计密度高、
  linux amd64/arm64 与 Windows 均有官方 wheel，API 直接支持 raw 序列化。
  **hub-server 侧为必备依赖**（非可选）：服务端一旦配置公钥就必须具备验签能力，
  可选化会引入"配置了公钥却验不了"的 fail-open 风险，成本仅一个 ~4MB wheel；
  **hub-publisher 侧为可选依赖组** `signing`（任务书指定），构建/校验/dev 流程
  不拖二进制 wheel，CLI 缺依赖时报错给出 `pip install 'python-hub-publisher[signing]'`。
- **G9② 签名对象与格式**：签**域分隔的包 sha256 摘要**而非整包——cryptography 的
  `sign()` 需整包进内存，而 `.pypkg` 上限 12GiB；摘要本就在流式上传时计算。
  域分隔前缀 `hub-plugin-package:v1:` 防摘要签名被当作其他协议的 32 字节消息签名重放。
  `.sig` 文档为自描述四行文本（algorithm/key_fingerprint/package_sha256/signature，
  minisign 式 untrusted comment 头）：算法仅认 `ed25519`（未知算法 fail-closed），
  未知字段忽略（前向兼容），重复字段拒绝；fingerprint 与 package_sha256 两行是给人看的
  注解，服务端一律以自身重算的摘要与配置公钥为准（注解说谎只会导致验签失败，无法绕过）。
  线格式（签名消息构造 + 文档渲染/解析）放 `python_hub_contracts.signing`——签名与验签
  必须字节级一致，contracts 正是发布者↔服务端的共享契约层，杜绝两侧漂移。
- **G9③ 验证流程（可轮换、渐进过渡、默认零变化）**：`plugins.signature.public_keys`
  （base64 公钥列表，任一验过即通过，轮换先加后删）+ `require_signed`（默认 False）。
  行为矩阵：未配置公钥=完全现行为（附签也忽略）；配置公钥→带签必验、验失败 422
  `PLUGIN_PACKAGE_SIGNATURE_INVALID`（含格式/算法/对不上任何钥）、不带签放行；
  `require_signed=true`→不带签 422 `PLUGIN_PACKAGE_SIGNATURE_REQUIRED`。
  **矛盾配置在启动期拒绝**：require_signed=true 而 public_keys 为空是"要求全员签名
  却不信任任何钥匙"，settings 校验直接拒绝启动（fail-closed），而非静默放行或拒收一切。
  服务层兜底同语义（直接调用传 require_signed 且无钥 → 422）。
- **G9④ 落点与流水线顺序**：`verify_and_install` 增加可选 `signature`/`public_keys`/
  `require_signed` 参数；验签在**外层 checksum 门之后、zstd 解压之前**——签名失败是最廉价的
  拒绝点，不给未信任内容花解压 CPU（测试钉死：篡改包同时破坏 zstd 帧，断言得
  SIGNATURE_INVALID 而非 INVALID）。安装端点 multipart 增加可选第二字段 `signature`
  （UploadFile，`.sig` 文件或文本表单字段均可），64KB 上限先于读取生效；安装审计
  `plugin.install` detail 新增 `signature_fingerprint`（验过哪把公钥，None=未验）。
- **G9⑤ 发布侧命令**：`hub-plugin keygen [--out-prefix]`（产出 `<prefix>.sec`/`.pub`
  双行文本，0600 尽力而为——Windows 忽略 POSIX 位，输出提示离线保管；拒绝覆盖已存在
  密钥文件）+ `hub-plugin sign <pkg> [--key] [--out]`（流式 sha256 → Ed25519 →
