# 服务演进路线图（V2.0 → V3.0）

> 基线：V1 单容器双运行时 + Web 管理台（`feature/service-hub-web-console` 分支）。
> V3.0 为暂定终版本。本文只定方向、范围与决策点；每版启动时再按
> `docs/superpowers/specs` + `docs/superpowers/plans` 流程编写详细设计与实施计划。

## 总原则（贯穿所有版本）

1. 协议向后兼容：plugin.yaml、Job Runtime Protocol、Runner Event Protocol 只增不改；
2. 数据目录（`HUB_HOST_DATA_DIR`）仍是唯一持久化点，离线单机交付定位在 V3 之前不松动；
3. 每版独立交付、独立验收（非集成质量门 + Linux AMD64 集成验收 + 发布包更新）；
4. Web 管理台与 hubctl 同步演进，不出现"只有 API 没有界面"或反之的功能缺口。

## 版本总览

| 版本 | 主题 | 核心交付 | 依赖 |
| --- | --- | --- | --- |
| V2.0 | 信任与治理 | 登录认证、RBAC 四角色、审计日志、M2M API Key | 无 |
| V2.1 | 资源治理与可观测 | 配额、文件生命周期清理、`/metrics`、备份自动化 | 用户主体存在（V2.0） |
| V2.2 | 自动化闭环 | Webhook 回调、定时任务、线性管道 | V2.0；管道复用文件体系 |
| V2.3 | 平台体验 | 插件仓库（Hub-to-Hub）、分片/秒传上传、SSE 实时日志 | V2.0（仓库走 M2M Key） |
| V3.0 | 长期运行 Docker 服务 | 服务运行时、生命周期 API、端口注册、服务管理页 | V2.0；建议在 V2.1–V2.3 之后 |

## V2.0 —— 信任与治理

**目标**：让"谁在操作"成为系统一等概念，是全部后续治理功能的地基。

- 数据模型：`users`（角色字段）、`api_keys`、`audit_logs`；密码哈希依赖烘焙进离线镜像；
- 认证：不透明 token（随机 256 位、哈希存库、可撤销），登录签发；hubctl 走 `HUB_TOKEN` + `login` 子命令；
- RBAC 四角色：viewer / operator / publisher / admin，按现有 router 逐端点标注；
- M2M：服务账号 + API Key，与人类账号同表不同类型；
- 审计：中间件统一打点，管理台只读审计页；
- Web：登录页、401 拦截、用户菜单、用户管理页；
- 引导：首次启动生成初始 admin 凭据（模式与 `HUB_RUNNER_TOKEN` 一致）；
- 兼容：`HUB_AUTH_MODE=off` 显式关闭用于存量部署平滑过渡；`/internal/v1` 继续走 Runner Token 不受影响。

规模：实施计划约 8–10 个任务，四版中最重。

## V2.1 —— 资源治理与可观测

- 配额：用户/全局两级（总存储、文件数、并发 Job），执行点为上传与建 Job，超限返回结构化错误；
- 文件生命周期：Job 输入文件 TTL、被输出引用的文件受保护、低频清理循环；
- `/metrics`：Prometheus 格式（Job 计数/状态分布、Runner 队列深度、API 延迟、磁盘使用）；
- 备份自动化：`hubctl backup create|restore`（SQLite backup API + 文件复制）+ cron 文档。

规模：约 5–6 个任务。

## V2.2 —— 自动化闭环

- Webhook 回调：Job 可选 callback（URL + 签名密钥），终态时 POST，投递日志 + 有限重试；
- 定时任务：`schedules` 表 + 触发器，错过触发点补跑一次；
- 线性管道：有序 Job 模板链，上一步输出 file_id 自动注入下一步输入，失败即停；不做 DAG。

规模：约 5–6 个任务。

## V2.3 —— 平台体验

- 插件仓库：基于已存 Build 元数据补只读 registry 端点 + hubctl `registry sync`（Hub-to-Hub，走 M2M Key）；
- 上传增强：分片/断点续传 + SHA256 秒传查重；
- SSE 实时推送：任务状态与日志准实时（与 Nginx `proxy_buffering off` 兼容）。

规模：约 5–6 个任务。

## V3.0 —— 长期运行 Docker 服务（定位升级）

**目标**：Hub 从"一次性任务调度器"升级为可托管常驻插件服务（推理服务、查询服务、瓦片服务等）的轻量应用平台。

- 插件形态：plugin.yaml 扩展服务声明（镜像、端口、健康检查、资源限制），与一次性 Job 包共存；
- 生命周期 API：start/stop/restart/升级/删除，经 Docker SDK 管理**兄弟容器**（无需 Docker-in-Docker）；
- 安全边界：常驻服务容器**绝不挂载 Docker Socket**，只读挂载所需数据子目录；
- 端口与网络：宿主回环端口分配表（SQLite），服务间 Docker 网络隔离；
- 自愈：容器 restart 策略 + Hub 层 liveness 探测；
- 管理台新增"服务"页（列表/启停/日志/版本），hubctl 增加 `service` 子命令；
- 形态约束：V3 先支持"单服务单容器"，不做 compose 编排与服务发现。

规模：独立大版本，实施计划预计 10+ 任务，需先行专项设计评审。

## 待决策点（随版本启动时逐项确认）

| # | 决策点 | 归属 | 候选方向 |
| --- | --- | --- | --- |
| 1 | 初始 admin 引导方式 | V2.0 | 数据目录受限文件（推荐，对齐 Runner Token）/ 环境变量 |
| 2 | 清理循环与调度器的进程形态 | V2.1/V2.2 | supervisord 独立进程（推荐，崩溃隔离）/ API 进程内线程 |
| 3 | 服务对外暴露方式 | V3.0 | 统一经 Hub/Nginx 路径代理 `/svc/{name}/`（推荐，保持单入口）/ 每服务独立回环端口 |
| 4 | 认证后端扩展预留 | V2.0 | 本地口令优先，认证层做成可替换，后续接 LDAP/OIDC |
| 5 | 定时任务补跑策略 | V2.2 | 补跑一次（推荐）/ 跳过 / 全部追补 |
